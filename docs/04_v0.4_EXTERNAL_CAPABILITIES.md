# Hacocoon v0.4 - External Capabilities Specification

Status: Draft for implementation  
Requires: v0.3 Security Framework and Git acceptance gate

## 1. One-sentence definition

Hacocoon v0.4 adds a Provider-oriented **Capability realization layer** so ordinary tools can use external services through the safest provider-native mechanism: brokered protocol, brokered operation, or short-lived delegated identity.

The optional term **Capability Broker** refers only to routing/materialization of an already authorized capability. It is not the authorization authority; the Security Framework remains authoritative.

## 2. Capability plugin design correction

Hacocoon must not become a Manager full of wrappers such as:

```text
haco-packer
haco-terraform
haco-aws
haco-every-future-tool
```

The Manager controls **capabilities and trust boundaries**, not every command-line tool.

For example, Packer, Terraform, AWS CLI, boto3, and the AWS Java SDK should all consume the same AWS identity capability rather than require five Hacocoon command proxies.

## 3. Goals

1. Define a stable Provider interface over the v0.3 Security Framework.
2. Support multiple realization strategies.
3. Keep long-lived/parent credentials outside Sessions.
4. Permit short-lived scoped credentials only when provider-native delegation makes this safe enough and auditable.
5. Implement a GitHub Operation Provider for selected `gh` workflows without exposing a raw token.
6. Implement an AWS identity Provider using short-lived role credentials.
7. Make standard AWS clients consume the delegated credential chain with minimal/no Hacocoon-specific wrappers.
8. Validate AWS CLI and SDKs; validate Packer/Terraform through the same integration.
9. Separate credential capability from network reachability.
10. Introduce reusable network profiles.
11. Make registry integration fit the same model.
12. Preserve all v0.3 Git behavior as a Provider using `brokered-protocol`.

## 4. Non-goals

- parse arbitrary CLI argument strings and somehow guarantee safety;
- inject a broad `GH_TOKEN` into the Session;
- proxy every AWS API call through Manager after a short-lived AWS identity is granted;
- universal HTTPS MITM;
- full DLP for files inside `/workspace`;
- support every `gh` subcommand in v0.4.

Unsupported operations are acceptable and must fail clearly.

## 5. Provider model

Conceptual Go interface:

```go
type Strategy string

const (
    DelegatedCredential Strategy = "delegated-credential"
    BrokeredProtocol     Strategy = "brokered-protocol"
    BrokeredOperation    Strategy = "brokered-operation"
    DirectNetwork        Strategy = "direct-network"
)

type Provider interface {
    Name() string
    Strategies() []Strategy
    Normalize(ctx context.Context, req RawRequest) (CapabilityRequest, error)
    Materialize(ctx context.Context, grant Grant) (MaterializedGrant, error)
    Revoke(ctx context.Context, grant Grant) error
}
```

The concrete interface may evolve, but keep these concerns separate:

1. normalize an external intent;
2. authorize through common IAM;
3. realize the approved capability;
4. revoke/cleanup when supported.

## 5.1 Plugin packaging in v0.4

v0.4 is the first release that proves a provider can be packaged outside the Manager binary when useful.

Supported modes:

```text
builtin  -> official implementation compiled into Manager
process  -> external executable using hacocoon-plugin-v1 control protocol
profile  -> declarative configuration, no executable code
```

The public extension model does not use Go `plugin.so`.

A process plugin is loaded only from an explicit manifest in a Manager-controlled path. PATH scanning and Session-provided plugin executables are forbidden.

Process-plugin startup performs a version/type/namespace handshake. The child environment is allowlisted and does not inherit unrelated Manager credentials by default.

At least one v0.4 provider should run through the process-plugin path as a POC, but official providers are not forced out-of-process merely to satisfy architecture purity.

## 5.2 Provider authority limit

A provider is trusted to correctly normalize operations inside its configured namespace, but its authority is scoped:

- it does not evaluate Capability Policy;
- it cannot mint a Grant;
- it receives only configured credential handles/provider resources;
- it cannot read the generic Manager DB or another provider's credential source;
- Security Framework records authoritative security audit/correlation; Core records only generic lifecycle correlation where needed.

See `00A_PLUGIN_ARCHITECTURE.md` for the full manifest and process model.

## 6. Capability kinds

The shared model should be able to represent:

| Kind | Example | Enforcement |
|---|---|---|
| identity | AWS role | short-lived credential + provider IAM |
| operation | GitHub PR create | Manager broker |
| protocol | Git push / OCI push | protocol gateway/broker |
| network | AWS API / package mirror | network policy |
| filesystem | workspace / inputs | Incus mount isolation |
| port | preview route | port/gateway layer |
| device | GUI/GPU/audio | Incus device/lease (v0.5) |

Not every kind needs full implementation in v0.4; the schema must not force all Providers into the same mechanism.

## 7. Credential principle

Historical wording such as "credential never enters Session" is refined to:

> Long-lived and parent credentials never enter the Session. A short-lived, purpose-limited provider credential may be issued into the Session only as the realization of an authorized Grant, with provider-native scope and expiry.

This is necessary for SDK/tool ecosystems where delegation is the standard safe integration point.

## 8. AWS Provider

### 8.0 Scope boundary: AWS access is not EC2 runtime

This release implements Session access to AWS through delegated capability. It does **not** implement EC2 instance lifecycle, Hacocoon deployment on EC2, AMI/EBS runtime mapping, or `runtime.ec2`; those are v0.7. Standard AWS clients in the local Session are the v0.4 acceptance target.


### 8.1 Desired user experience

Inside the Session:

```bash
aws sts get-caller-identity
terraform plan
packer init .
packer build .
```

Hacocoon should not require `haco packer ...` or run Packer in the Manager.

### 8.2 Parent identity

Parent authentication remains outside the Session and may come from:

- host AWS profile;
- SSO-derived credentials;
- another external credential provider;
- an EC2/host identity when intentionally configured.

The Manager uses the parent identity to obtain a narrower role/temporary credential, typically with STS AssumeRole or another provider-native delegation path.

### 8.3 Standard container credential endpoint

Preferred v0.4 design:

```text
AWS client in Session
  ↓ HTTP GET using standard AWS container credential provider
Session-local credential endpoint / proxy
  ↓ authenticated per-Session IPC
Manager AWS Provider
  ↓ Security Framework: ALLOW / ASK / DENY for identity acquisition
STS / provider-native role delegation
  ↓
short-lived credential response
```

Expose standard environment expected by AWS SDKs/tools, for example:

```text
AWS_CONTAINER_CREDENTIALS_FULL_URI=http://127.0.0.1:<session-endpoint>/credentials
AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE=/run/hacocoon/aws-token
AWS_EC2_METADATA_DISABLED=true
```

The authorization token file is Session-scoped and is **not** an AWS parent credential. It authenticates access to the Hacocoon credential endpoint.

Official AWS SDK documentation currently lists the container credential provider and `AWS_CONTAINER_CREDENTIALS_FULL_URI` as supported by AWS CLI v2 and major SDKs including Java, Python/Boto3, Go, JavaScript, .NET, PHP, Ruby, Rust, C++, and Kotlin.

### 8.4 AWS IAM division of responsibility

The Hacocoon Security Framework decides whether the Session may acquire a role/identity capability.

AWS IAM decides what that issued role may do at API-call granularity.

```text
Effective permission = Hacocoon Grant ∩ issued role policy ∩ AWS-side constraints
```

Do not attempt to re-authorize every AWS API call in Hacocoon once a delegated credential is issued.

### 8.5 Example Hacocoon policy

```yaml
policies:
  - name: dev-image-builder
    effect: allow
    actions: [capability.aws.identity.acquire]
    resources:
      - aws-role://123456789012/hacocoon-image-builder
    conditions:
      network_profile: aws-build

  - name: production-role
    effect: ask
    actions: [capability.aws.identity.acquire]
    resources:
      - aws-role://123456789012/production-*
```

### 8.6 Packer and Terraform

Packer and Terraform remain Session-installed developer tools.

The acceptance target is that their AWS integrations consume the same standard credential path used by AWS CLI/SDKs.

This must be treated as a real compatibility POC, not assumed from theory. In particular:

- verify the current Packer Amazon plugin follows a credential chain compatible with the endpoint mechanism used by Hacocoon;
- verify credential refresh during long builds;
- verify `packer init` plugin download has the required network profile;
- verify Terraform AWS provider behavior similarly.

Current HashiCorp documentation confirms the Amazon Packer plugin uses AWS authentication methods and can assume roles, but the Hacocoon release gate should explicitly test the chosen standard container-credential path rather than relying on undocumented behavior.

## 9. GitHub Provider and safe `gh`

### 9.1 Why no raw `GH_TOKEN`

GitHub CLI accepts `GH_TOKEN`/`GITHUB_TOKEN`. A broad Manager token copied into the Session would become an escape hatch that permits arbitrary GitHub API operations outside Hacocoon normalization and policy.

Therefore v0.4 does not use raw host token injection as the standard GitHub integration.

### 9.2 `gh` shim

Session may expose `gh` through a Hacocoon-safe shim/adapter for a supported operation set.

Examples:

| User command | Hacocoon path |
|---|---|
| `gh repo clone` | normalize repo -> Git Provider clone/read path |
| `gh pr create` | GitHub Operation Provider -> canonical PR create request |
| `gh issue create` | GitHub Operation Provider |
| `gh workflow run` | GitHub Operation Provider, policy-controlled |
| `gh release create` | GitHub Operation Provider, policy-controlled |
| `gh auth token` | unavailable/denied |
| `gh api ...` | unsupported by default; no raw escape hatch |

The supported set may start smaller. Safety and clear error behavior are more important than fake compatibility.

### 9.3 Brokered operation

Do not execute a raw string such as `gh <untrusted argv>` in Manager with a token.

Instead:

```text
shim request
  ↓
parse/normalize supported operation
  ↓
CapabilityRequest
  ↓
Security Framework / approval
  ↓
GitHub Provider SDK/API call using Manager auth
```

## 10. Registry Provider

Registry integration may use different strategies depending on the registry:

- local read-through cache for private image pull;
- short-lived registry token if safely delegable;
- protocol broker for push to protected registries.

The old v0.2-style read-only local registry remains valid as a simple Provider/cache implementation, but v0.4 should place it behind the provider-neutral model.

## 11. Network profiles

Credential permission and network reachability are independent axes.

Example:

```yaml
network_profiles:
  aws-build:
    allow:
      - aws-api
      - hashicorp-plugin-release
      - project-package-mirror
    conditional:
      - ec2-instance-ssh
      - ssm
    deny:
      - cloud-metadata
      - manager-private-network
```

A Session may possess an AWS role but still be unable to reach an endpoint if the network profile denies it, and vice versa.

## 12. Filesystem zones

Recommended standard zones:

| Zone | Mode | Meaning |
|---|---|---|
| `/workspace` | rw | repository/build/generated files |
| `/inputs` | ro | explicitly attached reference data |
| `/tmp` | rw ephemeral | temporary work |
| host HOME | absent | never default-mounted |
| `~/.ssh` | absent | no host SSH keys |
| `~/.aws` | absent | no parent AWS credentials |
| Manager state | absent | no control DB/sockets except dedicated IPC |

Hacocoon cannot prove that a secret intentionally copied into `/workspace` will never be uploaded to an allowed destination. That is outside the core v0.4 DLP model.

## 13. Grant lifecycle

Delegated credentials require stronger lifecycle handling:

```text
grant requested
  -> allowed/approved
  -> materialized
  -> active
  -> refreshed if policy permits
  -> expired/revoked
```

Requirements:

- expiry recorded;
- credential value not stored in generic audit/Grant tables;
- Session deletion revokes/invalidates active realizations where possible;
- refresh cannot silently widen role/resource scope;
- stale provider responses fail closed or retry safely.

## 14. CLI additions

Examples:

```bash
haco grants
haco grant revoke <id>
haco providers
haco provider status aws
haco audit --provider aws
```

Provider-specific configuration belongs in config, not in an explosion of permanent top-level CLI commands.

## 15. Implementation order

### Phase 1 - Provider interface refactor

1. Freeze the `CapabilityProvider` contract from v0.3.
2. Add plugin descriptors and capability namespace ownership.
3. Add external manifest parser and protocol-version validation.
4. Add process-plugin launcher with an allowlisted environment.
5. Add contract tests shared by builtin and process providers.


1. adapt Git Provider to `brokered-protocol`;
2. formalize `MaterializedGrant` variants;
3. grant expiry/revoke hooks;
4. preserve v0.3 regression suite.

### Phase 2 - Session Agent credential endpoint

1. per-Session loopback endpoint;
2. authorization token file;
3. Manager IPC bridge;
4. cross-Session isolation;
5. no-secret logging.

### Phase 3 - AWS identity POC

1. parent credential source interface;
2. STS/AssumeRole;
3. AWS CLI v2;
4. Boto3;
5. Java SDK;
6. refresh/expiry.

### Phase 4 - Packer/Terraform POC

1. Packer Amazon plugin;
2. Terraform AWS provider;
3. network requirements;
4. long-running refresh.

Do not declare general AWS integration complete until these compatibility tests pass or the unsupported cases are clearly scoped.

### Phase 5 - GitHub Operation Provider

1. safe shim framework;
2. `gh repo clone` bridge;
3. one or more write operations such as PR create;
4. `gh auth token`/raw API escape tests.

### Phase 6 - Registry and network profiles

1. provider-neutral registry path;
2. network-profile model;
3. metadata endpoint block;
4. egress/audit hardening.

Plugin acceptance additions:

- `haco plugin list/show/doctor` reports builtin and process providers.
- a disabled/unknown provider namespace fails closed.
- Session-controlled directories cannot replace a configured plugin executable.
- one provider cannot obtain another provider's credential handle through the generic plugin API.
- process-plugin crash does not convert a pending/failed operation into success or approval.
- at least one provider implementation passes the same CapabilityProvider contract tests in builtin and/or process mode.

## 16. Acceptance criteria

- v0.3 Git push policy and approval remain unchanged from the user perspective;
- Provider strategies are explicit and provider-neutral;
- AWS CLI v2 can obtain a short-lived scoped identity without host `~/.aws` being mounted into the Session;
- at least one major SDK (Boto3 and/or Java SDK) uses the same integration;
- parent AWS/SSO credentials remain outside the Session;
- role acquisition can be `ALLOW / ASK / DENY`;
- credential expiry/refresh is tested;
- Packer and Terraform compatibility with the selected standard credential path is validated as a release gate or explicitly documented unsupported limitation;
- Manager does not require Packer/Terraform/AWS CLI merely to authorize them;
- supported `gh` write operations are normalized and policy-controlled;
- `gh auth token` cannot reveal Manager credentials;
- raw `gh api` is not a bypass;
- Network Policy and Capability Policy can independently deny an operation;
- deleting a Session cleans its IPC and active Grants/Leases.

## 17. Current external implementation references

Use official references when implementing and re-check them at implementation time because tool behavior changes:

- AWS SDKs and Tools - Container credential provider: `AWS_CONTAINER_CREDENTIALS_FULL_URI`, authorization token/file, and SDK/tool support matrix.
- GitHub CLI manual - `GH_TOKEN` / `GITHUB_TOKEN` precedence and behavior.
- HashiCorp Packer Amazon integration and plugin installation/authentication documentation.

These are implementation references, not dependencies that Hacocoon Core should hardcode.
