# v0.11 Sandbox Resource Limits

**Status:** roadmap/design contract  
**Compatibility:** pre-1.0; interfaces, defaults, and provider mappings may change incompatibly.  
**Implementation:** pending.

## Goal

v0.11 adds explicit resource budgets for Hacocoon Environments so permissive coding agents and developer tools can consume CPU, memory, processes, and local root-storage only within operator-selected bounds.

The security model becomes:

```text
VS Code / coding agent / tool
            |
            v
      Environment
  broad local freedom
  within resource budget
            |
     ---- boundary ----
            |
        Hacocoon
  Policy / Capability / Audit
            |
   GitHub / AWS / Host
```

Resource limits are not capabilities. A capability controls authority across a trust boundary; a resource budget limits consumption inside an Environment.

```text
Capability:  "May this Environment ask Hacocoon to push to GitHub?"
Resource:    "How much CPU/RAM/PIDs/root storage may this Environment consume?"
```

## Why this belongs in Hacocoon

Hacocoon intentionally allows coding agents to be permissive inside an isolated Environment. Isolation alone does not prevent an Environment from exhausting shared host resources.

Examples include:

- runaway compiler or test processes consuming all CPU;
- an accidental process fork storm exhausting PID capacity;
- memory pressure causing host-wide swapping or OOM behavior;
- package managers, caches, build outputs, or logs filling the Environment root disk;
- many parallel agent Environments collectively overwhelming a workstation.

The host remains trusted and must retain control over how much shared capacity an untrusted Environment can consume.

## Scope

The first v0.11 slice should support explicit limits for:

- CPU;
- memory;
- process/PID count;
- Environment root-storage size where the selected provider can enforce it safely.

Conceptual creation input:

```text
EnvironmentSpec
  Name
  Workspace
  AccessMode
  ResourceBudget
```

Example user interaction:

```bash
haco create \
  --cpu 4 \
  --memory 8GiB \
  --pids 1024 \
  --root-size 40GiB \
  --workspace . dev
```

The exact flag names and configuration schema are pre-1.0 and are not frozen by this document.

## Resource budget model

Hacocoon should expose provider-neutral resource concepts and keep backend-native keys behind adapters.

Conceptually:

```go
type ResourceBudget struct {
    CPU      CPUResourceLimit
    Memory   ByteLimit
    PIDs     ProcessLimit
    RootDisk ByteLimit
}
```

This is illustrative rather than a required Go API.

The Core/domain contract must not expose Incus-native configuration names such as `limits.cpu` as public architecture. The Incus adapter may map the Hacocoon resource budget to those backend-native settings internally.

## Defaults

v0.11 must distinguish deliberately configured limits from accidental unlimited execution.

The implementation should support deterministic precedence, conceptually:

```text
CLI override
    > project configuration
    > user/global default
    > Hacocoon default budget
```

A missing value must have one documented meaning. Do not let provider defaults silently decide security-relevant resource behavior.

During pre-1.0 development, Hacocoon may initially preserve compatibility with an explicit `unlimited` value where necessary, but omission and unlimited authority must not be conflated accidentally.

## Provider boundary

Resource enforcement belongs to the Environment provider adapter.

The common lifecycle remains provider-neutral:

```text
Workspace
   |
EnvironmentSpec + ResourceBudget
   |
Environment provider
   +-- runtime.incus
   +-- runtime.ec2 (experimental)
```

A provider should report which resource dimensions it can enforce.

Conceptually:

```text
ProviderResourceCapabilities
  cpu: supported
  memory: supported
  pids: supported
  root_disk: supported
```

If the user explicitly requests a limit that the selected provider cannot enforce, creation must fail closed rather than silently ignore the requested limit.

## Incus mapping

For the default Incus provider, v0.11 may map provider-neutral limits to Incus configuration internally.

Examples may include backend-native controls equivalent to:

```text
CPU quota / CPU count
memory limit
process limit
root disk size
```

The precise Incus commands and keys remain adapter details and may change with supported Incus versions.

Resource settings must be applied before the Environment is made available to the client/agent. A create flow must not expose a briefly-unlimited running Environment and then apply limits afterward.

Preferred shape:

```text
resolve Workspace
  -> acquire WorkspaceLease
  -> validate ResourceBudget
  -> create stopped provider Environment
  -> apply resource limits
  -> attach Workspace
  -> start Environment
  -> verify requested limits where practical
  -> persist Environment metadata
```

Partial failure must use the existing cleanup/recovery discipline and must not leave a running unlimited Environment when the requested constrained Environment failed to materialize.

## Persistence and identity

An Environment must record the effective resource budget that was selected at creation time.

Changing a default later must not silently change the budget of an existing Environment.

Conceptually:

```text
2026-08-29
  default memory = 8 GiB
  create Environment A

2026-08-30
  default memory = 12 GiB
  create Environment B

Environment A remains 8 GiB
Environment B uses 12 GiB
```

Persisted resource metadata is also needed for diagnostics, reconciliation, and future recovery behavior.

## Runtime mutation

The first v0.11 slice should prefer creation-time budgets over arbitrary live mutation.

Changing CPU or memory limits on a running Environment can have provider-specific semantics and failure modes. Live resizing is therefore not required for the first gate.

A future update command may be added only after the ownership, persistence, rollback, and provider semantics are explicit.

## Workspace storage is separate

The mounted Workspace is host-owned state and is not the same thing as the Environment root filesystem.

```text
Host Workspace
    |
    +-- mounted at /workspace

Environment root filesystem
    |
    +-- OS
    +-- packages
    +-- caches
    +-- logs
```

`--root-size` must not be represented as a promise to limit the size of an arbitrary host Workspace mount.

Workspace growth remains a property of the underlying host filesystem/worktree unless a separate storage feature explicitly owns and constrains it.

## Parallel-agent safety

v0.10 can allocate one Environment per independently routable coding-agent session. v0.11 composes with that broker rather than replacing it.

```text
Agent session A -> Environment A -> ResourceBudget A
Agent session B -> Environment B -> ResourceBudget B
Agent session C -> Environment C -> ResourceBudget C
```

Per-Environment limits prevent one agent from consuming unbounded resources, but they do not by themselves solve aggregate host capacity.

A future admission-control feature may reject creation when the sum of requested budgets exceeds an operator-defined host allocation. Aggregate scheduling/admission is intentionally outside the first v0.11 slice.

## Resource exhaustion behavior

Exceeding a resource budget is expected sandbox behavior, not automatically a Hacocoon control-plane failure.

Examples:

- an allocation may fail inside the guest when memory is exhausted;
- a process creation may fail at the PID limit;
- writes may fail when root storage is full;
- CPU-bound work may be throttled rather than terminated.

Hacocoon should expose enough status/diagnostic information to explain that a resource limit was configured, without pretending it can always identify the exact guest process that triggered a provider/kernel-level limit.

## Status and diagnostics

The existing status/inspection path should be extended so operators can see the effective budget.

Example conceptual output:

```text
Name: dev
State: running
Workspace: /home/user/src/project
Access: rw
Provider: runtime.incus
Resources:
  CPU: 4
  Memory: 8 GiB
  PIDs: 1024
  Root disk: 40 GiB
```

Machine-readable output should expose stable Hacocoon resource concepts rather than backend-native key names.

## Policy relationship

Resource limits are not Hacocoon `CapabilityRequest`s.

Do not route normal CPU/memory/PID/root-size selection through the v0.4 capability service merely because it contains security-relevant policy.

The distinction is:

```text
Environment configuration
  -> defines sandbox shape and resource ceiling

Capability policy
  -> mediates privileged operations across the sandbox boundary
```

An operator may eventually restrict which budgets a caller is allowed to request, but such admission policy is separate from the runtime resource model itself.

## Base-image relationship

v0.11 composes with v0.9 Bases.

```text
Base revision
      |
      v
Environment + ResourceBudget
```

A Base controls guest filesystem/runtime contents. It must not be able to raise, disable, or rewrite host-selected resource limits through image metadata.

Custom Base contents remain untrusted input.

## Agent-host relationship

v0.11 also composes with v0.10 agent-session binding.

The trusted broker may request an Environment with a configured budget, but the coding agent inside that Environment must not receive authority to raise its own host-enforced limits through Hacocoon or Incus control-plane access.

## Failure and recovery semantics

Resource configuration participates in normal Environment creation recovery.

Relevant failures include:

- invalid resource values;
- unsupported provider resource dimension;
- provider rejects a limit;
- resource configuration succeeds but Workspace attachment fails;
- resource configuration succeeds but start fails;
- Environment starts but persistence fails;
- process crashes between provider creation and state commit.

The implementation must preserve the existing preference for explicit recovery over unsafe guessing.

When creation cannot prove that the requested limits were applied correctly, it must not report successful constrained creation.

Cleanup should prefer leaking a clearly identifiable stopped resource over silently releasing ownership metadata for a potentially running Environment.

## Validation

Resource values must be parsed and validated by Hacocoon before provider execution.

At minimum:

- reject zero/negative limits where they do not have an explicit documented meaning;
- reject integer overflow and absurd byte-size conversions;
- reject ambiguous unit formats;
- reject trailing garbage;
- place practical upper bounds on inputs where needed to prevent provider/CLI abuse;
- preserve exact operator intent in persisted effective values.

Provider command construction must continue to use argv-style execution rather than shell interpolation.

## Acceptance gate

Repository acceptance for the first v0.11 implementation requires:

- provider-neutral resource budget representation;
- explicit CPU limit support for Incus;
- explicit memory limit support for Incus;
- explicit process/PID limit support for Incus;
- root-storage limit support where the selected Incus storage path can enforce it safely, otherwise an explicit unsupported result;
- deterministic default/override resolution;
- persistence of the effective creation-time budget;
- status/machine-readable inspection of the effective budget;
- requested-but-unsupported limits fail closed;
- resource settings are applied before client/agent access;
- partial create failure follows existing cleanup/recovery semantics;
- WorkspaceLease safety remains unchanged;
- v0.9 Base selection, when implemented, cannot raise resource limits;
- v0.10 agent-session binding cannot grant agents resource-control authority;
- unit tests for parsing, precedence, persistence, unsupported-provider behavior, and failure cleanup;
- race, vet, build, docs consistency, and maintained host-independent integration tests green.

Environment-dependent acceptance requires a real supported Incus host and should verify:

- CPU restriction is visible/enforced by Incus;
- memory restriction is visible/enforced;
- PID restriction is visible/enforced;
- root-size enforcement where supported;
- an agent cannot use normal Environment access to raise those limits;
- deletion/recreation preserves the expected Workspace and resource ownership semantics.

## Non-goals

The first v0.11 slice does not add:

- AI scheduling or model budgets;
- task/DAG orchestration;
- aggregate cluster/workstation scheduling;
- automatic overcommit calculations;
- live autoscaling based on load;
- Kubernetes-style request/limit scheduling semantics;
- host Workspace quota management;
- arbitrary Incus configuration passthrough;
- a capability for coding agents to raise their own limits;
- Base-image metadata that can modify host resource authority.

## Future follow-ons

Once creation-time resource budgets are reliable, later work may add:

- aggregate host admission control;
- named resource profiles such as `small`, `default`, and `large`;
- per-project default budgets;
- live resize with explicit provider semantics;
- resource-usage observation and warnings;
- idle Environment stop/suspend policies;
- cleanup/reconciliation for stale Environments;
- checkpoint/restore support that preserves resource metadata.

These are separate follow-ons and are not automatically part of the v0.11 acceptance gate.

## One-sentence definition

> **v0.11 gives each Hacocoon Environment an explicit host-enforced resource budget so permissive developer tools and coding agents can run freely inside the sandbox without consuming unbounded shared host capacity.**
