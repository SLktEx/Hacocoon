# Hacocoon v0.2 - Developer Workspace Specification

Status: Draft for implementation  
Requires: v0.1 Local Foundation acceptance gate

## 1. One-sentence definition

Hacocoon v0.2 turns the reliable disposable Linux Session into a practical development workspace: repositories, repeatable setup, VS Code/SSH access, local previews, and a thin coding-agent lifecycle.

## 2. Goals

1. Create a Session from a repository without placing host Git credentials in the Session.
2. Maintain a Manager-side repository cache to avoid unnecessary reclones.
3. Give each Session an isolated writable workspace and Git metadata boundary.
4. Support User Base customization through ordinary scripts rather than a new environment DSL.
5. Support project-specific `.hacocoon/setup.sh`.
6. Provide stable SSH access and a VS Code Desktop adapter.
7. Forward a Session-local port to Windows localhost without making it public.
8. Run at least one CLI coding agent inside the Session through a thin profile/lifecycle interface.
9. Expose user-facing snapshot/clone/restore workflows for disposable development.
10. Optionally support Manager-synchronized private OCI images through a local read path.

## 3. Non-goals

v0.2 does not yet promise:

- policy-enforced Git push;
- Security Framework capability policy/approval;
- safe `gh` API mutation;
- AWS delegated credentials;
- remote Internet-facing Gateway (v0.7);
- local Web IDE/Web interaction as a required path (v0.6);
- native GUI/IntelliJ (v0.5).

A Session still must not receive host long-lived credentials. Git write safety becomes a formal enforced boundary in v0.3.

## 4. Architecture

```text
Windows
  |
  +-- VS Code Desktop
  +-- Browser localhost preview
  |
  v
WSL Hacocoon Manager [TRUSTED]
  |
  +-- repo cache / ingress credentials
  +-- workspace preparation
  +-- port forwarding
  +-- Incus
         |
         v
      Session [UNTRUSTED]
         +-- /workspace
         +-- sshd
         +-- git (no host credential)
         +-- Codex/agent
         +-- systemd
         +-- nerdctl
```

## 4.1 Plugin boundaries added in v0.2

v0.2 adds convenience integration interfaces without making workspace semantics abstract for abstraction's sake.

```text
AccessProvider
  -> access.ssh
  -> VS Code launcher uses the SSH access result

AgentAdapter
  -> agent.codex

Runtime contract
  -> runtime.incus (from v0.1)
```

Repository cache, worktree ownership, and project setup remain Hacocoon workspace services. They are not turned into a new plugin family until a real alternative implementation exists.

VS Code-specific launch behavior must not enter Session Core, and Codex-specific command flags must stay in `AgentAdapter`/profile code.

## 5. Repository model

### 5.1 Manager owns authenticated ingress

For a private repository:

```bash
haco new https://github.com/example/project.git
```

Conceptual flow:

1. Parse/canonicalize repository identity.
2. Manager checks its repo cache.
3. Manager performs clone/fetch using Manager-side authentication.
4. Manager creates a Session-specific repository/workspace representation.
5. Workspace is mounted at `/workspace`.
6. Session starts.
7. Project setup runs.

The Session never needs the host PAT, SSH private key, or credential-helper database.

### 5.2 Repository cache

Manager layout example:

```text
/var/lib/hacocoon/
  repos/
    cache/<repo-id>.git
  workspaces/
    <session-id>/
```

A single authenticated cache may service multiple Sessions, but untrusted Sessions must not receive writable access to Manager-owned cache metadata.

### 5.3 Session Git isolation

Do not mount a Manager bare repository or unrelated worktree metadata read-write into the Session.

Acceptable implementations include:

- a Session-specific shadow clone created efficiently from the local cache;
- a Session-specific Git directory plus worktree with Manager-owned cache protected from write access.

The important invariant is that Session root cannot mutate the authoritative Manager cache or another Session's refs/hooks/config.

### 5.4 Git push in v0.2

v0.2 does not expose Manager credentials to make push work.

Expected default outcome when the Session tries to push to a private remote before v0.3:

- push fails clearly because no credential is available; or
- an experimental future broker path is disabled unless explicitly enabled for testing.

Do not add a temporary raw-token workaround just to make v0.2 push convenient.

## 6. User Base and project setup

### 6.1 User Base

Users may build reusable development bases using a normal script:

```text
~/.config/hacocoon/images/java-dev/
  build.sh
  metadata.yaml   # minimal metadata only
```

The script may install:

- language runtimes;
- build tools;
- CLI utilities;
- coding agents;
- common packages.

Hacocoon must not invent an Ansible/Nix/Dev Container replacement DSL.

### 6.2 Project setup

Repository convention:

```text
.hacocoon/
  setup.sh
```

Execution rules:

- runs inside the Session after `/workspace` is ready;
- runs with Session-local privileges according to the Session user model;
- has no access to Manager credentials merely because it is setup code;
- failure leaves the Session in an inspectable `setup-error`/error state rather than silently deleting evidence.

## 7. SSH access

v0.2 introduces a stable SessionAccess concept.

```text
SessionAccess
  ssh
  local_ports[]
```

Required CLI:

```bash
haco ssh <session>
```

The SSH key/token used to access the Session is a Hacocoon Session access mechanism, not a GitHub/cloud credential. It should be Session-scoped and revocable when the Session is deleted.

## 8. VS Code Desktop adapter

Hacocoon keeps the UI outside the core.

Required command:

```bash
haco code <session>
```

Behavior:

1. start Session if needed;
2. resolve stable SSH endpoint;
3. wait for sshd readiness;
4. launch VS Code Remote SSH or equivalent supported adapter;
5. open `/workspace`.

No VS Code-specific field should become mandatory in generic Session state.

## 9. Local port preview

Required:

```bash
haco port <session> 3000
haco ports <session>
```

Default flow:

```text
Windows browser
  http://127.0.0.1:<allocated>
       ↓
WSL Hacocoon local forwarder
       ↓
Session:<guest-port>
       ↓
optional nested nerdctl-published service
```

Rules:

- bind to localhost by default;
- each Session can map the same guest port to a different host port;
- do not assume or inspect the nested application-container topology;
- no automatic public/LAN exposure.

## 10. Agent lifecycle

v0.2 proves Hacocoon can host coding agents, but does not build a chat UI.

Concept:

```bash
haco agent run <session> --profile codex --task "fix failing tests"
haco agent status <session>
haco agent logs <session>
haco agent stop <session>
```

An `AgentProfile` maps Hacocoon lifecycle operations to an installed agent command.

Example profile fields:

```yaml
name: codex
command: codex
working_directory: /workspace
completion: process-exit
```

Agent-specific flags belong in the profile adapter. The core tracks process lifecycle, not the agent's conversation model.

At v0.2, if the agent reaches an unavailable external privilege such as private Git push, it may fail and report the limitation. Waiting-for-approval semantics are added in v0.3.

## 11. Snapshot / clone / restore

User-facing disposable-workspace operations now become part of the product.

Conceptual CLI:

```bash
haco snapshot <session> [name]
haco restore <session> <snapshot>
haco clone <session> <new-name>
```

Requirements:

- root and workspace semantics are documented separately;
- dirty user work is not silently destroyed by default;
- clones receive new Session IDs and SSH identities;
- no clone shares writable Git metadata with the source Session.

## 12. Local registry option

This is useful for private development images but is not the core release blocker.

Target flow:

```text
Manager credential
  ↓
explicit sync/pull
  ↓
Hacocoon local registry/cache
  ↓ read-only/default-pull path
Session nerdctl pull
```

A Session does not receive the upstream private registry password just to pull a cached image.

Provider-neutral registry authorization and push are v0.4 concerns.

## 13. Network baseline

v0.2 needs ordinary Internet access for package installation and code/documentation research.

Mandatory isolation:

- block direct access to Manager-only control endpoints;
- block host/cloud metadata credential endpoints when applicable;
- do not expose host credential stores through filesystem mounts.

Fine-grained reusable capability-specific network profiles arrive with the external Capability Provider layer in v0.4. If the historical domain allowlist code already works, it may remain as an optional restricted profile, but it must not block v0.2 completion.

## 14. CLI additions

From v0.1, add:

```bash
haco new <repo-url> [--base <name>]
haco sync <session-or-repo>
haco ssh <session>
haco code <session>
haco port <session> <port>
haco ports <session>
haco snapshot <session> [name]
haco restore <session> <snapshot>
haco clone <session> <new-name>
haco agent run|status|logs|stop ...
```

Optional:

```bash
haco base build <name>
haco registry sync <image>
```

## 15. State additions

Add tables/records such as:

```text
repositories
workspaces
snapshots
session_access
local_port_forwards
agent_runs
```

Do not store upstream raw credentials in these records.

## 16. Migration from historical v0.1

Move/reuse old code as follows:

| Historical code | v0.2 treatment |
|---|---|
| private repo clone | reuse after ensuring Manager-only credential path |
| shadow repository/worktree logic | reuse/simplify, enforce Session isolation |
| VS Code Remote SSH | move behind access adapter |
| port forwarding | make localhost-only default and Session-scoped |
| local registry | optional feature, do not block core release |
| domain allowlist | optional/restricted profile; full policy integration later |
| push/publish approval | do not finalize here; move to v0.3 Security Framework |

## 17. Implementation order

### Phase 1 - Repository ingress

1. canonical repo identity;
2. Manager repo cache;
3. private clone/fetch using Manager auth;
4. Session-specific workspace creation;
5. repo cleanup/refcount behavior.

### Phase 2 - Setup and bases

1. User Base build script;
2. `.hacocoon/setup.sh`;
3. setup status/logging;
4. sample Java/Go/general bases.

### Phase 3 - Access

1. Session-scoped SSH identity/endpoint;
2. `haco ssh`;
3. `haco code`;
4. localhost port forward.

### Phase 4 - Disposable UX

1. snapshots;
2. restore;
3. clone;
4. dirty-work safeguards.

### Phase 5 - Agent

1. `AgentProfile`;
2. run/status/logs/stop;
3. at least one Codex end-to-end test.

### Phase 6 - Optional registry/restricted-network polish

Do not delay v0.2 if these optional items are the only remaining work.

Plugin acceptance additions:

- SSH/VS Code access is obtained through an `AccessProvider` seam rather than direct client logic in Session lifecycle.
- Codex execution is selected through an `AgentAdapter`/profile; Core does not parse Codex-specific options.
- replacing the AgentAdapter with a fake adapter does not change Session lifecycle or repository code.

## 18. Acceptance criteria

- a private repository can be used to create a Session without host Git credentials appearing inside the Session;
- two Sessions from the same repo have independent writable workspace/Git metadata;
- `.hacocoon/setup.sh` runs and its failure is diagnosable;
- a reusable User Base can avoid reinstalling common tools for every Session;
- `haco ssh` reaches the correct Session;
- `haco code` opens the same `/workspace` state visible to the shell/agent;
- a development server on Session port 3000 can be opened from Windows through a localhost-only forward;
- two Sessions can both expose guest 3000 using different host ports;
- snapshot/restore/clone do not silently destroy dirty user work;
- at least one coding agent can run inside the Session and edit/test the workspace;
- the Session still has no Manager GitHub/AWS/SSH parent credentials;
- safe Git push is **not** claimed until v0.3.
