# v0.11 — Base Images & Custom Environments

Status: **roadmap design contract; implementation not yet introduced on `main`.**

This document defines the Base-image work as the v0.11 roadmap gate. `BASE_IMAGES.md` remains the detailed design companion; this file defines the minimum v0.11 contract and acceptance boundary.

## Goal

Allow an Environment to start from a selectable Hacocoon **Base** without exposing Incus image aliases, remotes, or fingerprints as Core/public architecture.

The intended layering is:

```text
Official Base
    |
    v
User Base (optional)
    |
    v
Project Setup
    |
    v
Environment
```

An Environment records one immutable Base revision at creation time. Updating a logical Base affects only future Environment creation.

## Public/domain model

The user-facing/domain vocabulary is:

```text
Base name
Base revision
Environment
```

The Incus adapter may resolve a Base revision to an Incus image fingerprint internally, but Incus aliases/fingerprints must not become required Core concepts.

Conceptually:

```text
my-dev
  -> immutable Base revision
  -> Incus fingerprint
  -> Environment
```

The immutable revision is the Environment's reproducibility anchor.

## Initial v0.11 scope

The first implementation slice must support:

1. a default Base for Incus Environment creation;
2. explicit Base selection when creating an Environment;
3. deterministic resolution of a logical Base name to one immutable revision;
4. persisted Base identity on the Environment record;
5. list/inspect functionality sufficient to diagnose available Bases and resolved revisions;
6. reuse of existing Incus images through an adapter-owned mapping/import path;
7. safe handling of Base deletion and concurrent create/update/remove operations;
8. tests that prove mutable aliases cannot silently retarget an existing Environment.

The exact CLI and configuration remain pre-1.0 and may change while the implementation is validated.

A likely CLI shape is:

```text
haco image list
haco image inspect <name>
haco create --base <name> --workspace <path> <environment>
```

The detailed proposal also discusses `haco image build`, import, history, rollback, and GC. Those are not required to land in the first v0.11 implementation slice unless the reference/lifecycle semantics are implemented safely.

## Base selection

If selection exists at several levels, precedence must be deterministic:

```text
CLI --base
    > project configuration
    > user/global default
    > Hacocoon default
```

The selected logical name is resolved once at Environment creation time and the immutable revision is persisted.

Changing a default or moving a logical Base name later must not change an existing Environment.

## Official and User Bases

### Official Base

An Official Base is a Hacocoon-maintained or recommended starting point.

Example logical name:

```text
haco/ubuntu-26.04
```

The concrete Incus remote/alias used to acquire it is an adapter implementation detail, not a compatibility promise.

### User Base

A User Base is an operator/user-owned reusable starting point.

Examples:

```text
my-dev
go-dev
cuda-dev
```

The initial v0.11 implementation may register/reuse existing Incus images before introducing a richer Hacocoon-owned build pipeline.

## Environment immutability rule

The central v0.11 contract is:

> A Hacocoon Environment is created from one immutable Base revision. Updating a logical Base affects future Environment creation only.

Example:

```text
my-dev -> revision A
Environment 1 -> revision A

update my-dev -> revision B

Environment 1 -> revision A
Environment 2 -> revision B
```

There is no v0.11 operation that replaces the Base underneath an already-created Environment.

Recreate the Environment to move to another Base revision.

## Incus boundary

Incus remains the first/default Environment implementation.

The adapter may internally keep a mapping such as:

```text
Hacocoon Base revision
        |
        v
Incus image fingerprint
```

The following must stay outside Core except for explicit diagnostics or Incus-specific administration:

- Incus image aliases;
- Incus remotes;
- Incus fingerprints;
- native import/publish mechanics.

This preserves room for later Environment providers to map a Base to their own immutable starting-point mechanism without making Core an Incus image manager.

## Security contract

A Base controls guest filesystem/runtime contents. It does **not** grant host-side authority.

Selecting or importing a Base must not implicitly add:

- host filesystem mounts;
- Incus devices;
- privileged-container mode;
- Linux capabilities;
- host network reachability;
- GitHub/AWS/cloud credentials;
- SSH private keys;
- registry credentials;
- Hacocoon daemon/control-plane authority.

Those remain controlled by the Environment / Policy / Capability boundary.

Custom Bases are treated as potentially hostile.

## Build/import trust boundary

If custom build/import is implemented during v0.11, arbitrary image contents and build steps must not execute directly with Hacocoon host authority.

Preferred model:

```text
Host
  |
  +-- Hacocoon / Incus authority
  |
  +-- isolated builder Environment
          |
          +-- build/import processing
          +-- produce immutable image
          +-- register Base revision
```

Local archives must be handled as untrusted data. Path traversal, unsafe symlink following, malformed metadata, resource exhaustion, and partial-import cleanup must be considered explicitly.

Host credentials must not be implicitly injected into image builds.

## Deletion and reference safety

Removing a logical Base name and deleting physical image data are different operations.

A Base revision must not be physically removed while a running or recoverable Environment still depends on it.

When Hacocoon cannot prove that deletion is safe, it should prefer retaining storage over silently destroying a dependency required for recovery/reproducibility.

Concurrent operations such as these must be handled intentionally:

```text
create --base my-dev  vs update my-dev
create --base my-dev  vs remove my-dev
gc                    vs create --base my-dev
```

Environment creation must obtain a stable revision reference before that revision can become deletion/GC eligible.

## Project Setup boundary

Repository/workspace-specific setup should remain distinct from a reusable Base.

```text
Base
  common OS/runtime/tooling
        |
        v
Project Setup
  workspace-specific dependency/setup work
        |
        v
Environment
```

The exact project-setup schema is not frozen by v0.11.

## Explicit non-goals

v0.11 does not require:

- changing the Base of an existing Environment in place;
- transparent migration of existing Environments to newer Base revisions;
- exposing the full Incus image API through `haco`;
- running arbitrary image-build commands directly on the host;
- snapshotting arbitrary live Environments into reusable Bases;
- baking reusable credentials into images;
- a provider-generic image framework before another implementation actually requires it;
- freezing CLI/configuration compatibility before 1.0.

## Acceptance

The v0.11 implementation gate is complete when the maintained test/acceptance path can demonstrate at least:

1. two selectable Bases resolve to different immutable starting revisions;
2. an Environment created from Base revision A continues to identify/use A after the logical Base moves to revision B;
3. a newly created Environment resolves the new revision B;
4. Incus aliases/fingerprints are not required by Core/public Environment contracts;
5. unsafe deletion of a referenced revision is rejected or deferred;
6. concurrent create/update/remove behavior does not create a dangling Environment reference;
7. a custom/untrusted Base cannot expand host-side privilege merely through image metadata;
8. existing v0.1-v0.10 implemented/integration boundaries remain intact.

Real-Incus image lifecycle acceptance must still be reported separately from fake/process/unit tests when the current execution environment cannot run a real supported Incus host.

## Relationship to earlier gates

v0.8 introduced the thin `haco-vscode` Client Adapter. v0.9 added the trusted per-agent Environment broker. v0.10 is the active Remote Agent Host Adapter integration gate.

v0.11 changes what starting filesystem/runtime Base an Environment may be created from; it does not move image selection/build ownership into VS Code or any AI/orchestrator UI.

The intended path remains:

```text
VS Code / another client
        |
 thin Client Adapter
        |
    Hacocoon
        |
 Base -> Environment
```
