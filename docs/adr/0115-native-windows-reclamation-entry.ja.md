# ADR 0115: Windows側のクライアントから新しい容量回収を開始する

日本語 | [English](0115-native-windows-reclamation-entry.md)

状態: ソース候補の方針として採用。Windows実行および導入済み環境の受入確認は未完了。

## 根拠と決定

通常のHost経路はLinuxからWindowsへの相互運用を経由する。現在のWindows実行では、
直接のJobが離脱を許可しない状態でプロセス作成エラー5を確認した。起動条件の不整合は
示すが、すべての祖先Jobや失敗したカーネル操作の特定ではない。ワーカーの離脱要件や
WSL・runnerのJob設定は変更しない。

受入端末には別の所有問題もある。明示的な終了処理を抑えてもpywinpty・ConPTYの破棄は
無信号とは限らない。パイプに置き換えると[ADR 0066](0066-wsl-login-bootstrap-routing.md)により
通常のHostではなくPhysical HostのBashへ入る。いずれも修復や結果不明の再試行の根拠にはならない。

明示的に起動するWindows公開クライアント`haco-reclaim.exe`を追加する。
`haco-tunnel.exe`と同様にクライアントを分離し、固定した内部用`haco-wsl.exe`を
準備・ワーカーの主体として残す。[ADR 0048](0048-storage-reclamation-identity.md)の
公開入口を拡張するが、正規の記録・登録・変更・確認の権限は置き換えない。
既存のLinuxコマンドは起動失敗後に自動で切り替えない。

## 権限と新規準備

明示した配布名から保存済み登録・Windows所有者が一致する一つの登録を選ぶ。
選択はWSL起動、キー作成、新規登録、稼働中ディスクの固定をしない。
名前は選択用であり変更権限ではない。状態表示もWSLやディスク固定なしに保存結果を読む。

準備は既存の継続処理・起動予約、ディスクと祖先の固定、登録確認を保持する。
現在の記録が未完了、不正、読取不能ならWSLプロセスより前に拒否する。
失敗・中断結果の明示的確認要件は、変更しない正規の`beginVersion`に残す。

GUIDに結び付いた固定の読み取り専用探索には、作成時からWindows子孫を所有する
[ADR 0110](0110-private-windows-process-ownership.ja.md)の仕組みを使う。
変更ワーカーはそのJobへ入れない。成功出力だけでは足りず、必要な親終了成功と
両方の識別子を登録に照合し、Windows Jobの構成員の不在を確認してから操作を保存する。
RPCのCloseが捨てた終了確認エラーも明示的に保持する。終了確認が不明なら操作を作らず、
helper終了まで予約を保持する。

Windows JobはLinuxプロセスの不在を証明しない。固定したrootの識別子読み取りは
成功前に終了し、controllerも固定した識別子読み取り終了後に返答する。
残るLinux stdio bridgeには、この操作での再試行・WSL起動・変更処理がない。
その終了処理とWSLサービスは導入済み環境での検証を要する。
正確なdistro停止とVHDX切断確認は圧縮の条件のままである。

その後だけ新しいversion 2の操作意図を生成・永続化・再読取する。
準備側のガードを解放してから、変更しないワーカーが自分のガードと固定を取り直す。
今回返された新しいIDだけを一度起動し、状態表示や前の呼出しのIDで代用しない。
不明な結果の後に再確認・再実行・記録削除・代替起動は行わない。

## 終了させないクライアント監視

固定した常設helper、所有記録、祖先パスを固定する。明示的な標準handle、最小限の環境、
上限付きの応答を使う。作成前に非ブロッキングのpipe読み取りを設定できなければ拒否する。
公開クライアントはPTYを所有せず、worker用のkill-on-close Jobを追加しない。

準備・起動の可能性がある後のキャンセル、時間切れ、pipe切断、不正応答、非ゼロ終了は
証拠が残り得る失敗である。観測handleを閉じても終了を要求せず、不在の証明にもしない。
worker終了、再試行、WSL再入場、自動再確認、代替起動はない。
読み取り専用の探索Jobは意図的にキャンセル・終了確認できるが、切り離したworkerは除外する。
外側のJob、runner・console・OSの終了は別の危険であり、任意の状況での生存保証ではない。

## 梱包と採用しない案

amd64/arm64のクライアントを個別にchecksum確認し、helper登録とは別の利用者・登録単位の
領域に配置する。PATH、昇格、service、予定task、認証情報、常設接続先は追加しない。
workerモードのない別バイナリに起動処理を移さず、helper自身の`_continue`を使う。

内部コマンドの公開代用、汎用復旧broker、WMI・COM経由の回避、Job制約緩和、WSL降格、
library改変、参照漏れ、destructor抑制、EOF・PID・受付を完了扱いする案は採らない。
パイプ経路を通常のHost受入と同じものに扱わない。

## 検証範囲

ローカルmock・梱包・クロスコンパイルはソース上の証拠だけである。
frontendのWindows模擬fixtureは明示的opt-inとfail-fastを要する。専用コマンドは
frontendと専用プロセスの両fixture群をfail-fastと指定PASS確認付きで実行する。
対象は作成時から専用Jobが所有する固定self-testプロセス、専用console、通常の一時ファイルだけである。
テスト用の終了・後始末を実変更workerへ適用しない。指定テストのPASSを要求し、
skipや欠落を成功にしない。

pipe・console・handle、起動元の離脱条件、Windows子孫終了、Linux終了、導入済みの
新規操作は別途受入を要する。reparse、pipe設定失敗注入、キャンセル前の起動ゼロの
独立証明、arm64実行は未確認である。実際の成功には完了記録、正確なworker不在、
データ保持、Host再開が必要である。

既存PRのworkflowには実際の容量回収が含まれる。ソース検査だけでPRやその経路を
起動しない。別途レビュー・承認した模擬専用branch/workflowで既存gateと履歴を変更せず
構成要素を検証できるが、安全な実回収CIの確立にはならない。
