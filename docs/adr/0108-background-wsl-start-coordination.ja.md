# ADR 0108: バックグラウンドのWSL起動と容量回収を調整する

日本語 | [English](0108-background-wsl-start-coordination.md)

状態: 実装候補で採用。導入済み環境での確認は別途必要。

## 根拠と判断

#707のc0843ed4、Windows job104622907624では、容量回収の停止要求後にWSLの
起動・hostプロセスが消え、23.8秒後に通知由来の起動2件が戻った。ディスクは接続中で
圧縮を拒否した。これはHacocoonのバックグラウンド起動との競合を示すが、全失敗の
原因とは限らない。#708では新規起動を観測せずhostプロセスが残った。

Windowsの共通処理へカーネル名の排他を集める。容量回収は既存のユーザーSID・正確な
登録GUIDの排他に加え、SID・distribution名の起動排他を、本人の導入識別確認から
Linux discard、停止、圧縮、再開まで保持する。通知の初期接続・回答用接続は同じ
起動排他を取得し、期限付きの読み取り接続確認が終わるまで保持する。失敗時は子を
終了・回収してから排他を解放する。競合時にはWSLを起動せず拒否し、回答の待機・
自動再送もしない。後の明示的な操作で新しい確認を開始できる。

名前はWindowsの大文字小文字を区別しない照合に合わせて小文字化しハッシュ化する。
この名前の排他は起動調整だけに使う。ディスク所有権、導入識別、本人承認、停止権限
の代わりにはならない。正確な登録・導入識別・ファイル固定・切断確認は必須のまま。
別のdistributionは別の起動排他を使い、共通処理はCoreの外へ置く。

## Windows APIの契約と限界

[CreateMutexExW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexexw)
は既存オブジェクトの場合もハンドルを返しERROR_ALREADY_EXISTSを示す。競合側は
そのハンドルを閉じて拒否する。別種のオブジェクトとの衝突やAPIエラーも拒否する。
新規の非継承ハンドルを閉じるまで予約を保持し、スレッドに属するmutex所有権は使わない。
現在ユーザー・SystemのACLとユーザー別Global名は既存の回収排他と同じ仕組み。
先取りで妨害はできても、変更権限は得られない。資格情報やguest権限は追加しない。

協調対象はHacocoon通知の起動。直接のWSL操作、外部エディタ、既存セッションによる
接続は残り得るため、その場合の圧縮拒否は維持する。排他は一時的で、クラッシュ後の
未完了・失敗は既存の永続記録で保持する。自動再試行、強制切断、他WSLの停止、
圧縮待ち期限の延長は追加しない。

## 採らない方法と確認

事前確認だけでは起動と競合し、Start直後の解放では遅れて起動する子と競合する。
本人の回答まで排他を保持すると容量回収を長時間妨げる。名前だけでのディスク変更は
所有契約に反する。全通知・エディタの強制終了や試験設定の変更で製品の競合を隠さない。

実Windowsの回帰では、別プロセスとの排他、大小文字、別distribution、競合後の解放、
解放後の通常接続、準備失敗時の後片付けを確認する。導入済みの容量回収と通知の利用は
別の実機結果として記録する。
