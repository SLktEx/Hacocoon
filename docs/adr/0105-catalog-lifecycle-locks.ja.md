# ADR 0105: ライフサイクルのロックをカタログと同じ場所で管理する

日本語 | [English](0105-catalog-lifecycle-locks.md)

状態: 採用

## 問題と決定

導入済み環境で、別の実効ユーザーが `/tmp/hacocoon-environment-locks` を所有し、
Env作成がプロバイダー呼び出し前に失敗した。共通の一時ファイル名では、無関係な
ローカル作業によって管理サービスが止まる。一時領域が分離されている場合には、
逆に同じカタログに対する排他制御が分かれてしまう。

共通のEnv状態管理に `LockLifecycle` を必須の操作として追加する。Workspace側は
既存のEnv→Workspaceの取得順序を保ち、プロバイダーの処理完了までロックを保持する。
短時間のカタログ更新ロックとは分ける。一時領域へ暗黙に戻る処理は設けない。

Linux／WSLではカタログと同じディレクトリの `lifecycle-locks` に配置する。
状態ディレクトリは実効ユーザー所有で、group／otherの書き込みを拒否する。
シンボリックリンクをたどらずに開いて固定し、所有者専用の子ディレクトリと、
所有者専用・通常ファイル・リンク数1のロックファイルを相対記述子操作で開く。
所有者・種類・権限が不正なら拒否する。キーにはカタログ名、種別、対象の識別子を
含める。同じカタログを使う別の状態管理オブジェクトやプロセスも、一時領域に
依存せず排他を共有する。キャンセル時に解放するのはロック取得処理だけであり、
Workspaceのリースやプロバイダー資源を解放しない。

変更した管理サービスは通常のインストール・再起動手順で導入する。同じカタログを
旧版と新版の管理サービスで同時操作しない。既存の共通一時領域は採用・変更・削除
しない。Linux以外の構成要素試験はプロセス内ロックを維持し、Windows上で直接動く
管理サービスの対応を主張しない。

## 不採用案と検証

不明な一時ディレクトリの所有者や権限の変更は、別の処理の状態を取り込んでしまう。
公開された名前にユーザーIDを追加するだけでも、名前の先取りは残る。プロセス内
だけのロックではプロセス間の排他を失う。状態管理インターフェースで任意にすると、
将来の実装が排他を省略できる。

使用できない共通一時ファイル名、別のカタログオブジェクト、一時領域の異なる子
プロセス、キャンセル、独立した対象、書き込み可能なディレクトリ、シンボリック
リンク、ハードリンクの拒否を回帰試験で確認する。導入済み環境の結果と失敗は
[受入証拠](../status/acceptance-evidence.md)に記録する。
