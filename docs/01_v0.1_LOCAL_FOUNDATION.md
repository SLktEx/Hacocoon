# Hacocoon v0.1 - Local Foundation Specification

Status: Authoritative draft for implementation  
Date: 2026-08-29  
Requires: `00_REBASELINE_AND_ROADMAP.md`, `00A_PLUGIN_ARCHITECTURE.md`  
Primary target: Windows 11 + WSL2 + Ubuntu 26.04

## 1. One-sentence goal

> v0.1 proves that a tiny Hacocoon Core can create, inspect, start, stop, execute in and destroy a local disposable Linux Session using replaceable Runtime and Storage implementations, while the managed local storage lifecycle is capable of safe growth and planned shrink/compaction without making Btrfs/QCOW2 part of Core.

v0.1 is not a repository, Git security, AWS, IDE, Web UI or EC2 release.

## 2. Shipping architecture

```text
haco
 |
 v
Core
 Session model / lifecycle / state / composition
 |
 +---------------------------+
 |                           |
 v                           v
Runtime contract          Storage contract
 |                           |
 v                           v
runtime.incus            storage.btrfs
                             |
                 +-----------+-----------+
                 |                       |
                 v                       v
             Btrfs logic            block backend
                                    local image
                                    qcow2 preferred*
                                    raw sparse fallback
```

`*` QCOW2 is preferred only when the supported host can provide a reliable block attachment path (for example qemu-nbd). Backend choice is a Storage/Block implementation concern, never Core state semantics.

## 3. Scope

### Mandatory Core
- stable `SessionID`, `SessionSpec`, desired/observed state;
- lifecycle orchestration and reconciliation;
- module composition/bootstrap;
- minimal persistent state;
- typed errors and cleanup ordering;
- `haco init`, `doctor`, lifecycle routing.

### Mandatory Runtime
- `runtime.incus` probe/create/start/stop/delete/inspect/exec;
- unprivileged system container;
- systemd;
- containerd + nerdctl nested workload;
- no Incus control socket inside Session.

### Mandatory Storage behavior
- provider-neutral Storage contract;
- local managed storage ensure/inspect/delete;
- usage/health reporting;
- grow;
- safe shrink orchestration with preflight and refusal when unsafe;
- compaction/reclaim workflow where backend supports it;
- recovery from partial attach/mount/create state;
- Btrfs-specific code outside Core;
- image/QEMU/loop/NBD-specific code outside Core.

### Deferred
- repo/worktree/VS Code/SSH/agent: v0.2;
- Security/Grant/Git push: v0.3;
- GitHub/AWS delegated capability/Registry: v0.4;
- WSLg/IntelliJ: v0.5;
- Web UI/Browser Notification/code-server: v0.6;
- remote Linux/EC2/EBS/Gateway: v0.7.

## 4. Core boundary

Core may know:

```text
SessionID
SessionSpec
runtime_module + opaque runtime_ref
storage_module + opaque storage_ref
desired_state / observed_state
operation/correlation IDs
```

Core must not know:

```text
incus CLI/API structs
Btrfs subvolume/device paths
mkfs.btrfs / balance / filesystem resize
qemu-img / qemu-nbd
losetup / truncate
EBS volume IDs or AWS SDK types
```

Concrete provider references may be stored in module-owned state behind opaque IDs.

## 5. Runtime contract

Illustrative only:

```go
type Runtime interface {
    Probe(context.Context) (Capabilities, error)
    Create(context.Context, RuntimeSessionSpec) (RuntimeSession, error)
    Start(context.Context, RuntimeSessionID) error
    Stop(context.Context, RuntimeSessionID) error
    Delete(context.Context, RuntimeSessionID) error
    Exec(context.Context, RuntimeSessionID, ExecRequest) (ExecResult, error)
    Inspect(context.Context, RuntimeSessionID) (RuntimeState, error)
}
```

Do not leak the complete Incus client across this boundary.

## 6. Storage and BlockStore seams

The public Core-facing seam is `Storage`. A narrow local block-image seam is permitted *inside* `storage.btrfs` because QCOW2 and sparse raw are two real implementations needed by the supported local profile.

This inner seam is intentionally private to the local storage implementation in v0.1. Do **not** add EBS/cloud methods or a universal block API to v0.1 merely for future symmetry.

```text
Core -> Storage
          |
          v
   storage.btrfs
       |         |
       |         +-> Btrfs filesystem lifecycle
       |
       +-> BlockStore
             block.local-qcow2
             block.local-raw
```

Illustrative contracts:

```go
type Storage interface {
    Probe(context.Context) (StorageCapabilities, error)
    Ensure(context.Context, StorageSpec) (StorageHandle, error)
    Inspect(context.Context, StorageHandle) (StorageState, error)
    Delete(context.Context, StorageHandle) error
}

type ResizableStorage interface {
    Grow(context.Context, StorageHandle, Size) error
    PlanShrink(context.Context, StorageHandle, Size) (ShrinkPlan, error)
    Shrink(context.Context, StorageHandle, ShrinkPlan) error
    Compact(context.Context, StorageHandle) error
}
```

Keep optional operations narrow. Do not make every future Storage implementation pretend to support shrink.

## 7. Local managed-image backends

### 7.1 QCOW2 target backend

When host probe proves qemu-nbd/QEMU support is reliable:

```text
qcow2 file
  -> qemu-nbd block attachment
  -> Btrfs
  -> Incus storage pool/source
```

The Storage module owns attachment identity and reconnection. Core must not persist `/dev/nbdN` as stable product identity.

### 7.2 Sparse raw fallback

A sparse raw/loop image may remain supported for hosts where QCOW2 block attachment is unavailable or unreliable.

The same Storage contract and shrink planning rules apply. Backend-specific commands remain below the Storage boundary.

### 7.3 Why not use Incus-managed loop size as the only lifecycle

Incus supports growing loop-backed Btrfs pools, but its ordinary managed loop pool path is grow-only from the user-facing storage configuration. Hacocoon needs an explicit lifecycle that can reason about filesystem shrink/compaction before changing the backing image. Therefore Hacocoon-managed storage must not blindly issue an outer truncate/resize.

## 8. Grow algorithm

Growth order is outer-to-inner:

```text
1. acquire exclusive storage operation lease
2. health/precondition check
3. grow backing block/image
4. reconnect/rescan block device if needed
5. grow Btrfs filesystem to new maximum
6. inspect and verify capacity
7. release operation lease
```

A failure after outer grow is recoverable by retrying the inner filesystem grow; it must not create a second storage object blindly.

## 9. Shrink algorithm

Shrink is destructive if ordered incorrectly. Hacocoon must implement **inner-to-outer** shrink.

```text
1. require all Sessions using the storage pool to be stopped/quiesced
2. acquire exclusive storage operation lease
3. inspect Btrfs usage, device size and minimum feasible device size
4. validate requested target + configured safety margin
5. if allocation layout blocks target, run targeted balance/compaction only as needed
6. re-check minimum feasible size
7. shrink Btrfs filesystem/device usage to target
8. stop/unmount the Incus pool and detach backend
9. shrink or replace the outer backing image
10. reconnect/mount/re-enable pool
11. verify Btrfs health, reported size and Incus visibility
12. release operation lease
```

Never shrink/truncate the outer image before the filesystem reports a successful smaller size.

### 9.1 Balance policy

Do not run an unfiltered full balance by default. Balance can be IO/CPU intensive and itself needs free workspace. Prefer progressively targeted `usage=` filters and re-check minimum device size after each step.

If compaction cannot reach the requested target safely, **refuse the shrink** and report the minimum currently feasible target plus the reason. Do not guess.

### 9.2 QCOW2 outer shrink

Only after Btrfs shrink and detach succeed may the QCOW2 virtual size be reduced. The implementation must use the backend's explicit shrink acknowledgement and then run an image consistency check before reconnecting.

Safer default when host free space allows:

```text
shrink filesystem -> create/convert verified replacement image -> atomic swap metadata/path -> retain/delete old after verification
```

In-place outer shrink should be treated as a higher-risk backend operation and must not be the only recovery path.

### 9.3 Raw image outer shrink

Only after Btrfs reports a smaller device boundary may the raw backing file/loop limit be reduced. Detach the loop device before changing the file boundary, then reconnect and verify.

## 10. Compact vs shrink

Expose different semantics:

```text
haco storage compact
  reclaim physical host space where backend supports it
  logical capacity may stay unchanged

haco storage shrink --to <size>
  reduce logical capacity after Btrfs preflight/relocation
```

Do not overload `shrink` to mean merely sparse-file reclamation.

## 11. Storage operation state machine

Persist enough module-owned state to recover:

```text
ready
planning-grow
resizing-outer-grow
resizing-fs-grow
planning-shrink
compacting-fs
resizing-fs-shrink
replacing-or-shrinking-outer
verifying
error-recoverable
```

Core only needs generic operation/correlation state; provider-specific step details stay in the Storage module.

A crash on restart must run inspection/reconciliation before any destructive continuation.

## 13. Host initialization

`haco init` is idempotent:

1. detect WSL/Linux capabilities;
2. probe Incus;
3. probe available local block backend(s);
4. probe Btrfs tools/features;
5. choose configured/supported local storage composition;
6. ensure storage and Incus pool/profile;
7. ensure base image;
8. persist stable module selections and opaque references.

## 16. State and reconciliation

Minimal Core schema for the v0.1 local composition:

```text
sessions:
  id/name
  runtime_module/runtime_ref
  storage_module/storage_ref
  desired_state/observed_state
  created_at/updated_at
```

Storage-specific DB/state may track image backend, image stable ID, attach state, filesystem identity, resize operation and verification status.

After a crash: inspect persisted refs -> ask modules for observed state -> reconcile. Never infer provider truth solely from filenames or `/dev/nbdN` numbers.

## 17. Security posture in v0.1

- Session is untrusted.
- host/Manager HOME is absent;
- host SSH/AWS/GitHub credentials are absent;
- Incus socket is absent;
- local block control devices/interfaces are not exposed to Session;
- no future feature may weaken these invariants for convenience.

Generic external Capability authorization arrives in v0.3.

## 18. Tests

### Core unit tests
Use fake Runtime and Storage; no Incus/Btrfs/QEMU requirement.

Required failure cases: storage ensure fails; runtime create fails after storage creation; partial delete; retry; observed/desired mismatch; unknown module ID.

### Runtime tests
Probe/create/start/stop/exec/delete, failed-create cleanup, isolation profile, nested systemd/nerdctl smoke.

### Storage tests
- missing tools/backend probe;
- ensure idempotence;
- attach/reconnect recovery;
- usage/health inspect;
- grow then filesystem growth;
- non-destructive shrink plan;
- target below feasible minimum is refused;
- balance/compaction failure is recoverable/refused, never outer-truncated;
- filesystem shrink succeeds before outer shrink call is observable in test doubles;
- simulated crash between filesystem shrink and outer replacement is reconcilable;
- backend consistency verification;
- cleanup.

## 19. Acceptance gate

v0.1 is complete only when:

1. Core lifecycle tests pass with fake Runtime/Storage and without Incus/Btrfs/QEMU installed.
2. Incus implementation is isolated under runtime module boundary.
3. Btrfs/image/loop/NBD/QEMU details are isolated under Storage/Block backend boundaries.
4. `haco init` is idempotent on supported local profile.
5. `haco doctor` reports Core/Runtime/Storage separately.
6. empty Session creation does not require a repository.
7. systemd and nested nerdctl work.
8. start/stop/delete are repeatable and cleanup is retryable.
9. storage grow is verified end-to-end.
10. shrink planning is safe and non-destructive.
11. one supported local backend proves a safe shrink flow or explicitly refuses unsupported shrink without data loss.
12. no outer-image shrink is executed before filesystem shrink success.
13. host credentials, Incus control socket and block-control interfaces are absent from Session.
14. v0.2+ features are not required to pass the gate.
