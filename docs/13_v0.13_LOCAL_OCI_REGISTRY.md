# v0.13 — Local OCI Registry

Status: **planned next milestone after v0.12; not yet implemented on `main`.**

This document records the intended v0.13 direction. It is a roadmap/design contract, not a claim that the feature already exists and not a pre-1.0 compatibility guarantee.

## Goal

Add a Hacocoon-managed **local OCI registry/cache gateway** that is shared by local Incus Environments using `containerd` / `nerdctl`.

For Hacocoon-managed local Environments, OCI image pulls should be **transparently routed through the Hacocoon Local Registry by default**. A user or coding agent should keep using ordinary image references such as `nginx`, `docker.io/library/nginx:latest`, or another configured upstream registry without having to know the Hacocoon registry address or rewrite commands manually.

The registry is intended to reduce repeated upstream image downloads, work cleanly with restricted-network Environments, and provide a controlled image-distribution boundary without giving coding agents host credentials or Incus/Hacocoon control-plane authority.

```text
nerdctl pull nginx
nerdctl pull docker.io/library/postgres:18
nerdctl pull ghcr.io/example/tool:1.2
        |
        | transparent containerd registry routing
        v
+-------------------------------+
| Hacocoon Local Registry       |
| / OCI cache gateway           |
| host-owned, local-only        |
+---------------+---------------+
                |
        trusted upstream path
                |
        +-------+--------+
        |                |
        v                v
    Docker Hub       other allowed
    anonymous        OCI registries
    when possible
```

Multiple independent Environments should converge on the same local cached blob set instead of independently downloading identical upstream blobs.

## Mandatory transparent routing

Transparent routing is part of the v0.13 acceptance contract, not an optional optimization.

Hacocoon should configure the Environment-side `containerd` registry resolver during Environment/bootstrap setup so that normal `nerdctl pull` operations use Hacocoon-managed registry endpoints automatically.

Expected user experience:

```bash
nerdctl pull nginx
nerdctl pull ubuntu:24.04
nerdctl pull docker.io/library/redis:latest
```

The user should **not** need to write a Hacocoon-specific registry prefix such as:

```bash
# Not the intended normal workflow.
nerdctl pull hacocoon-registry.local/docker.io/library/nginx:latest
```

For upstreams that can be consumed anonymously, especially public Docker Hub images, the Environment does not need upstream credentials. Hacocoon should fetch/cache those images through the trusted registry gateway using anonymous upstream access when supported.

If an upstream requires authentication, credentials remain on the trusted Hacocoon side and must not be copied into arbitrary Environments merely to make transparent pulling work.

## No silent direct-registry bypass

A Hacocoon-managed Environment must not silently bypass the local registry/cache gateway when Hacocoon intends registry mediation to be enforced.

Conceptually:

```text
Environment containerd
      |
      +----> Hacocoon Local Registry ----> allowed upstream
      |
      X----> registry-1.docker.io directly
      X----> ghcr.io directly
      X----> arbitrary registry directly
```

Implementation may use containerd registry-host configuration, Hacocoon network policy, or both. The important contract is behavioral: if the local registry is the required mediation path, failure of that path must produce an explicit pull failure rather than an unrestricted direct-Internet fallback.

This also means a compromised coding agent should not be able to obtain direct upstream registry access merely by changing an image name or invoking `nerdctl` differently.

## Upstream coverage

The first implementation should support at minimum:

1. Docker Hub public/anonymous pulls;
2. explicitly configured additional OCI registries;
3. a path for authenticated upstream registries where credentials remain on the trusted side.

The exact implementation is intentionally not frozen. A single OCI Distribution pull-through cache may be insufficient to represent every upstream registry, so Hacocoon may use multiple per-upstream cache backends, a registry gateway, or another adapter-owned implementation while preserving one transparent Environment-side experience.

Unknown or unapproved registry hosts should fail closed when registry mediation is enforced rather than silently becoming unrestricted outbound destinations.

## Why this is a separate milestone

Hacocoon v0.11 Base images and v0.13 OCI images solve different problems.

- **v0.11 Base**: the immutable starting filesystem/runtime revision used to create an Environment.
- **v0.13 Local OCI Registry**: container/workload images consumed *inside* an already-created Environment by `containerd` / `nerdctl`.

The local registry must not turn the Hacocoon Core model into a Docker/OCI orchestration system. OCI-registry mechanics remain an adapter/host-service concern.

## Intended first slice

The initial v0.13 implementation should provide:

1. a Hacocoon-owned local OCI registry/cache gateway;
2. local Incus Environment reachability to that registry without exposing it publicly by default;
3. automatic Environment-side `containerd` registry configuration so ordinary `nerdctl pull` operations route through Hacocoon without command rewriting;
4. Docker Hub public/anonymous pull-through behavior by default;
5. host-side upstream fetch/cache behavior so the same upstream blobs do not need to be downloaded from the Internet independently by every Environment;
6. fail-closed behavior for direct-registry bypass when Hacocoon mediation is required;
7. content-addressed image handling and digest-aware resolution where practical;
8. lifecycle/bootstrap integration suitable for the normal local Incus Hacocoon installation;
9. clear failure behavior when the local registry is unavailable or an image/upstream is not permitted;
10. tests using fake/local registries plus real-Incus acceptance as a separate host-dependent gate.

The exact CLI/configuration surface is intentionally not frozen yet.

## Network and trust boundary

The local registry is infrastructure owned by the trusted Hacocoon side.

By default it should be reachable only from the Hacocoon host and Hacocoon-managed local Environment network. It must not become an unauthenticated Internet-facing registry as a side effect of installation.

```text
coding agent
    |
 nerdctl pull
    |
    v
containerd resolver
    |
    v
Hacocoon Local Registry
    |
 trusted host-side policy/configuration
    |
    v
allowed upstream OCI source
```

An Environment must not receive broad host registry credentials merely because it can pull from the local registry.

Upstream Docker Hub/GHCR/private-registry credentials, when required, belong on the trusted side and must not be copied into arbitrary Environments unless an explicit capability contract says otherwise.

## Push behavior

The first slice should optimize for **pull/cache/mirror use**.

Environment-originated arbitrary `push` into the shared registry is not required for the first implementation. If push is added later, it must have an explicit ownership/policy model so one compromised Environment cannot overwrite or poison image names consumed by other Environments.

Mutable tags must not be treated as immutable identity. Where correctness or trust depends on exact content, Hacocoon should resolve/use a digest rather than trusting a moving tag.

## Security requirements

The v0.13 implementation must preserve the existing authority boundaries:

- no Docker/containerd host socket exposed to coding agents;
- no Incus admin socket or Hacocoon control-plane authority exposed to Environments;
- no silent export of upstream registry credentials into guests;
- no public listen address by default;
- ordinary Environment-side pulls route through the Hacocoon registry/cache gateway automatically;
- no silent direct-upstream fallback when registry mediation is required;
- unknown/unapproved registry hosts fail closed under enforced mediation;
- no trust in a mutable tag when an immutable digest is required;
- registry metadata and image names are untrusted input and must be validated at command/configuration boundaries;
- registry failure must not silently cause an unrestricted direct-Internet fallback when the Environment is supposed to be network restricted;
- cleanup/GC must not delete blobs still required by active or recoverable references when Hacocoon cannot prove deletion is safe.

## Network-restricted Environments

A primary use case is an Environment that cannot freely access public registries but can reach the Hacocoon local registry.

```text
Internet
   X
   |
Environment ----> Hacocoon Local Registry ----> trusted upstream path
```

This lets an agent use normal `nerdctl pull` workflows without granting the Environment unrestricted outbound network access.

The registry mediation path must be installed/configured by Hacocoon as part of the Environment/runtime setup rather than depending on every project or agent to configure it correctly.

## Storage expectations

The local registry should avoid downloading identical OCI blobs from upstream once per Environment.

For example, if ten Environments execute:

```bash
nerdctl pull docker.io/library/ubuntu:24.04
```

Hacocoon should aim for one upstream blob download into the shared local cache, after which subsequent Environments obtain the same blobs locally.

This does **not** promise that every Environment's unpacked `containerd` snapshot storage will be globally deduplicated. Registry blob sharing and per-Environment runtime snapshot storage are separate concerns.

A later storage optimization may use Btrfs/COW or another safe shared-content mechanism to reduce duplication of unpacked runtime layers, but v0.13 must not weaken Environment isolation merely to deduplicate bytes.

Registry GC and retention should prefer leaking storage over deleting content whose safety cannot be proven.

## Non-goals of the first slice

- replacing the v0.11 Incus Base-image model;
- becoming a general Docker/Kubernetes orchestrator;
- exposing a public multi-tenant registry service;
- giving agents host `containerd`, Docker, Incus, or Hacocoon control sockets;
- requiring users to manually prefix ordinary image names with a Hacocoon registry hostname;
- automatic arbitrary Environment-to-registry push;
- full image signing/notary/SBOM policy in the first slice;
- promising global deduplication of unpacked runtime filesystems;
- silently bypassing Hacocoon network policy when the registry is unavailable;
- freezing registry CLI/configuration compatibility before 1.0.

## Acceptance target

v0.13 should not be considered implemented merely because a registry process can start.

Repository-level acceptance should cover at least:

- deterministic local registry bootstrap/configuration;
- default non-public exposure;
- a fresh Hacocoon Environment automatically receiving the required `containerd` registry routing configuration;
- `nerdctl pull nginx` resolving through the local Hacocoon registry without a Hacocoon-specific image prefix;
- Docker Hub public/anonymous image pulls using the local cache path;
- successful pull from two independent fake/local Environments through one shared registry;
- reuse of previously fetched registry blobs without requiring a second upstream download;
- authenticated-upstream credentials, when used, remaining absent from Environment-visible configuration/state;
- malformed image references rejected safely;
- unknown/unapproved upstream registries failing closed in enforced mode;
- registry outage failing explicitly instead of falling back directly to the upstream registry;
- restricted-network mode not silently falling back to unrestricted direct upstream access;
- existing v0.1-v0.12 Environment, Policy/Capability, Base, resource-budget, and agent-boundary tests remaining intact.

Real Incus + real `containerd` / `nerdctl` + Docker Hub + additional real upstream-registry acceptance remains a separate supported-host gate.

## Relationship to v0.11 and v0.12

v0.11 decides **what immutable Base revision creates the Environment**.

v0.12 decides **what CPU/memory/PID/root-storage budget the Environment may consume**.

v0.13 adds **how OCI workload images are distributed efficiently and safely to the runtime inside that Environment**.

```text
v0.11 Base revision
        |
        v
   Environment
        |
   v0.12 limits
        |
        v
containerd / nerdctl
        |
   transparent routing
        |
        v
v0.13 Local OCI Registry
        |
        v
allowed upstream OCI registries
```

> **v0.13 is planned to make Hacocoon's local OCI registry/cache gateway the transparent default path for ordinary `nerdctl` pulls in local Incus Environments, including anonymous Docker Hub pulls, without requiring image-name rewriting and without permitting silent direct-upstream bypass.**
