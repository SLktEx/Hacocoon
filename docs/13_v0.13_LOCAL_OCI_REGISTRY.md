# v0.13 — OCI Distribution Strategy

Status: **direct upstream pulls are the default direction; a Hacocoon-managed Local Registry is optional and not required by OCI Seed.**

This document supersedes the earlier assumption that v0.13 must transparently force every Environment-side `nerdctl pull` through a Hacocoon Local Registry.

The current design keeps normal nerdctl/containerd behavior unless an operator explicitly enables additional OCI infrastructure.

## Default behavior

For ordinary Hacocoon Environments:

```text
Environment
    |
    | nerdctl pull docker.io/library/nginx:latest
    v
configured upstream registry
```

The Environment may directly reach Docker Hub, GHCR, a private registry, or another explicitly permitted registry according to Hacocoon network policy.

Hacocoon does not require a special image prefix and does not require a local proxy merely to preserve normal `nerdctl pull` behavior.

## Authentication

Public registries can use their normal anonymous flow.

Authenticated registries remain an authority boundary:

- Host credentials must not be silently copied into coding Environments.
- Environment-owned credentials may use nerdctl/Docker-compatible credential configuration.
- A future Hacocoon credential-helper/broker plugin may provide scoped or short-lived credentials while the image data path still goes directly to the upstream registry.
- Seed acquisition uses trusted Host-side credentials independently of Environment credentials.

A Local Registry must not be introduced solely because authentication exists if a narrower credential-broker mechanism is sufficient.

## Relationship to OCI Seed

OCI Seed is independent of a Registry.

```text
upstream registry
      |
      | trusted Host-side pull
      v
Host seed namespace/cache
      |
 OCI export / stream
      v
Offline Seed Builder
      |
 immutable Seed
      |
 Incus/Btrfs COW
      v
Environment
```

The Seed Builder does not require network access to any registry. See [`13A_v0.13_OCI_SEED_AND_COW.md`](13A_v0.13_OCI_SEED_AND_COW.md).

## When a Local Registry may still be useful

An operator may choose a Local Registry/proxy when measurements show a real benefit, for example:

- many independent Environments repeatedly pull the same large non-seeded images;
- upstream bandwidth/rate limits are a problem;
- a centralized OCI policy/audit point is required;
- an installation intentionally restricts Environment Internet access but still wants an internal distribution endpoint.

In that mode the Registry is an optional adapter/infrastructure service, not a Hacocoon Core concept.

## Requirements if enabled

If Hacocoon later manages or integrates a Local Registry/proxy, it must preserve these rules:

- use an existing OCI Distribution-compatible implementation rather than inventing a new registry protocol implementation without necessity;
- do not expose it publicly by default;
- keep upstream credentials on the trusted side when proxying authenticated registries;
- do not silently turn Registry failure into unrestricted direct-Internet fallback when an operator explicitly configured mandatory mediation;
- do not give coding agents arbitrary push authority into shared names by default;
- treat tags as mutable and use digests when immutable identity matters;
- make GC conservative when referenced content cannot be proven safe to delete.

## Non-goals

The default v0.13 path does not require:

- transparent rewriting of all registry traffic;
- a Hacocoon-specific registry hostname in image references;
- a Hacocoon-written registry server;
- a Registry for OCI Seed construction;
- copying Host registry credentials into Environments;
- globally deduplicating every Environment's writable containerd state.

## Decision summary

```text
Default:
  Seed/common images   -> OCI Seed + Incus/Btrfs COW
  Seed miss            -> ordinary nerdctl pull to upstream
  private auth         -> Environment credential or scoped credential broker

Optional later:
  repeated pull cost   -> Local Registry/proxy if measurements justify it
```

> **v0.13 no longer treats a Local Registry as mandatory infrastructure. Normal Environment pulls remain normal upstream pulls; OCI Seed handles common-image storage optimization, and a Registry can be added later only where it provides measurable value.**
