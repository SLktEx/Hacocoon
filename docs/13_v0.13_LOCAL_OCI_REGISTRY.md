# v0.13 — Optional OCI Plugin Distribution Strategy

Status: **direct upstream pulls are the default for OCI-enabled profiles; a Hacocoon-managed Local Registry is optional and not required by Core or OCI Seed.**

This document applies only when the optional OCI plugin/profile is in use. Hacocoon Core does not require `containerd`, `nerdctl`, Docker, an OCI registry, or any OCI distribution path.

The design avoids forcing every Environment-side container pull through Hacocoon infrastructure. The selected OCI plugin profile keeps its normal client/runtime behavior unless an operator explicitly enables additional OCI infrastructure.

## Default behavior

For the project-maintained nerdctl profile, ordinary behavior is:

```text
OCI-plugin-enabled Environment
    |
    | nerdctl pull docker.io/library/nginx:latest
    v
configured upstream registry
```

For a Docker CLI profile, the equivalent ordinary `docker pull` behavior applies.

The Environment may directly reach Docker Hub, GHCR, a private registry, or another explicitly permitted registry according to Hacocoon network policy.

Hacocoon Core does not require a special image prefix, local proxy, container CLI, or registry endpoint.

## Authentication

Public registries can use their normal anonymous flow.

Authenticated registries remain an authority boundary:

- Host credentials must not be silently copied into coding Environments.
- Environment-owned credentials may use the selected OCI profile's standard credential configuration.
- A future credential-helper/broker plugin may provide scoped or short-lived credentials while the image data path still goes directly to the upstream registry.
- Optional OCI Seed acquisition uses trusted Host-side credentials independently of Environment credentials.

A Local Registry must not be introduced solely because authentication exists if a narrower credential-broker mechanism is sufficient.

## Relationship to OCI Seed

OCI Seed is itself an optional OCI-plugin optimization and is independent of a Registry.

```text
upstream registry
      |
      | trusted OCI-plugin Host acquisition
      v
plugin Host seed cache
      |
 OCI export / stream
      v
Offline Seed Builder
      |
 immutable Seed
      |
 provider/Btrfs COW where available
      v
Environment
```

The Seed Builder does not require network access to any registry. See [`13A_v0.13_OCI_SEED_AND_COW.md`](13A_v0.13_OCI_SEED_AND_COW.md).

## When a Local Registry may still be useful

An operator may choose a Local Registry/proxy when measurements show a real benefit, for example:

- many OCI-enabled Environments repeatedly pull the same large non-seeded images;
- upstream bandwidth/rate limits are a problem;
- a centralized OCI policy/audit point is required;
- an installation intentionally restricts Environment Internet access but still wants an internal distribution endpoint.

In that mode the Registry is an optional OCI-plugin adapter/infrastructure service, not a Hacocoon Core concept.

## Requirements if enabled

If the OCI plugin later manages or integrates a Local Registry/proxy, it must preserve these rules:

- use an existing OCI Distribution-compatible implementation rather than inventing a new registry protocol implementation without necessity;
- do not expose it publicly by default;
- keep upstream credentials on the trusted side when proxying authenticated registries;
- **No silent direct-registry bypass**: do not turn Registry failure into unrestricted direct-Internet fallback when an operator explicitly configured mandatory mediation;
- do not give coding agents arbitrary push authority into shared names by default;
- treat tags as mutable and use digests when immutable identity matters;
- make GC conservative when referenced content cannot be proven safe to delete.

## Non-goals

Neither Core nor the default OCI-plugin path requires:

- transparent rewriting of all registry traffic;
- a Hacocoon-specific registry hostname in image references;
- a Hacocoon-written registry server;
- a Registry for OCI Seed construction;
- copying Host registry credentials into Environments;
- globally deduplicating every Environment's writable containerd state;
- installing nerdctl or Docker merely because Hacocoon Core is installed.

## Decision summary

```text
Core:
  OCI tooling           -> absent unless explicitly enabled

Optional nerdctl profile:
  Seed/common images    -> optional OCI Seed + provider/Btrfs COW
  Seed miss             -> ordinary nerdctl pull to upstream

Optional Docker profile:
  Seed miss             -> ordinary Docker CLI pull to upstream

Private auth:
  Environment credential or scoped credential broker

Optional later:
  repeated pull cost    -> Local Registry/proxy if measurements justify it
```

> **OCI distribution is plugin-owned. Hacocoon Core has no registry or container-runtime requirement; OCI-enabled profiles keep ordinary upstream behavior unless an operator explicitly chooses mediation.**
