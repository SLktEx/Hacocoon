# v0.13 — Local OCI Registry

Status: **planned next milestone after v0.12; not yet implemented on `main`.**

This document records the intended v0.13 direction. It is a roadmap/design contract, not a claim that the feature already exists and not a pre-1.0 compatibility guarantee.

## Goal

Add a Hacocoon-managed **local OCI registry** that can be shared by local Incus Environments using `containerd` / `nerdctl`.

The registry is intended to reduce repeated upstream image downloads, work cleanly with restricted-network Environments, and provide a controlled image-distribution boundary without giving coding agents host credentials or Incus/Hacocoon control-plane authority.

```text
upstream OCI registry
        |
        | trusted host-side fetch / mirror path
        v
+--------------------------+
| Hacocoon Local Registry  |
| host-owned, local-only   |
+------------+-------------+
             |
      +------+------+------+
      |             |      |
      v             v      v
 Incus Env A   Incus Env B   Incus Env C
 containerd    containerd    containerd
 nerdctl       nerdctl       nerdctl
```

## Why this is a separate milestone

Hacocoon v0.11 Base images and v0.13 OCI images solve different problems.

- **v0.11 Base**: the immutable starting filesystem/runtime revision used to create an Environment.
- **v0.13 Local OCI Registry**: container/workload images consumed *inside* an already-created Environment by `containerd` / `nerdctl`.

The local registry must not turn the Hacocoon Core model into a Docker/OCI orchestration system. OCI-registry mechanics remain an adapter/host-service concern.

## Intended first slice

The initial v0.13 implementation should provide:

1. a Hacocoon-owned local OCI Distribution-compatible registry service;
2. local Incus Environment reachability to that registry without exposing it publicly by default;
3. `containerd` / `nerdctl` configuration so Environments can pull through the local registry;
4. host-side upstream fetch or mirror behavior so the same upstream blobs do not need to be downloaded from the Internet independently by every Environment;
5. content-addressed image handling and digest-aware resolution where practical;
6. lifecycle/bootstrap integration suitable for the normal local Incus Hacocoon installation;
7. clear failure behavior when the local registry is unavailable or an image is not permitted;
8. tests using a fake/local registry plus real-Incus acceptance as a separate host-dependent gate.

The exact CLI/configuration surface is intentionally not frozen yet.

## Network and trust boundary

The local registry is infrastructure owned by the trusted Hacocoon side.

By default it should be reachable only from the Hacocoon host and Hacocoon-managed local Environment network. It must not become an unauthenticated Internet-facing registry as a side effect of installation.

```text
coding agent
    |
 nerdctl pull
    |
    v
Hacocoon Local Registry
    |
 trusted host-side policy/configuration
    |
    v
allowed upstream OCI source
```

An Environment must not receive broad host registry credentials merely because it can pull from the local registry.

Upstream Docker Hub/GHCR/private-registry credentials, when later supported, belong on the trusted side and must not be copied into arbitrary Environments unless an explicit capability contract says otherwise.

## Push behavior

The first slice should optimize for **pull/cache/mirror use**.

Environment-originated arbitrary `push` into the shared registry is not required for the first implementation. If push is added later, it must have an explicit ownership/policy model so one compromised Environment cannot overwrite or poison image names consumed by other Environments.

Mutable tags must not be treated as immutable identity. Where correctness or trust depends on exact content, Hacocoon should resolve/use a digest rather than trusting a moving tag.

## Security requirements

The v0.13 implementation must preserve the existing authority boundaries:

- no Docker/containerd host socket exposed to coding agents;
- no Incus admin socket or Hacocoon control-plane authority exposed to Environments;
- no silent export of upstream registry credentials into guests;
- no public listen address by default;
- no trust in a mutable tag when an immutable digest is required;
- registry metadata and image names are untrusted input and must be validated at command/configuration boundaries;
- registry failure must not silently cause an unrestricted direct-Internet fallback when the Environment is supposed to be network restricted;
- cleanup/GC must not delete blobs still required by active or recoverable references when Hacocoon cannot prove deletion is safe.

## Network-restricted Environments

A primary use case is an Environment that cannot freely access public registries but can reach the Hacocoon local registry.

```text
Internet
   X
   |
Environment ----> Hacocoon Local Registry ----> trusted upstream path
```

This lets an agent use normal `nerdctl pull`-style workflows without granting the Environment unrestricted outbound network access.

The exact integration with Hacocoon network policy/capability controls will be defined during implementation; v0.13 must fail closed rather than bypass an existing network restriction.

## Storage expectations

The local registry should avoid downloading identical OCI blobs from upstream once per Environment.

This does **not** promise that every Environment's unpacked `containerd` snapshot storage will be globally deduplicated. Registry blob sharing and per-Environment runtime snapshot storage are separate concerns.

Registry GC and retention should prefer leaking storage over deleting content whose safety cannot be proven.

## Non-goals of the first slice

- replacing the v0.11 Incus Base-image model;
- becoming a general Docker/Kubernetes orchestrator;
- exposing a public multi-tenant registry service;
- giving agents host `containerd`, Docker, Incus, or Hacocoon control sockets;
- automatic arbitrary Environment-to-registry push;
- full image signing/notary/SBOM policy in the first slice;
- promising global deduplication of unpacked runtime filesystems;
- silently bypassing Hacocoon network policy when the registry is unavailable;
- freezing registry CLI/configuration compatibility before 1.0.

## Acceptance target

v0.13 should not be considered implemented merely because a registry process can start.

Repository-level acceptance should cover at least:

- deterministic local registry bootstrap/configuration;
- default non-public exposure;
- successful pull from two independent fake/local Environments through one shared registry;
- reuse of previously fetched registry blobs without requiring a second upstream download;
- no upstream credential material in Environment-visible configuration/state;
- malformed image references rejected safely;
- registry outage fails explicitly;
- restricted-network mode does not silently fall back to unrestricted direct upstream access;
- existing v0.1-v0.12 Environment, Policy/Capability, Base, resource-budget, and agent-boundary tests remain intact.

Real Incus + real `containerd` / `nerdctl` + real upstream-registry acceptance remains a separate supported-host gate.

## Relationship to v0.11 and v0.12

v0.11 decides **what immutable Base revision creates the Environment**.

v0.12 decides **what CPU/memory/PID/root-storage budget the Environment may consume**.

v0.13 adds **how OCI workload images are distributed efficiently and safely to the runtime inside that Environment**.

```text
v0.11 Base revision
        |
        v
   Environment
        |
   v0.12 limits
        |
        v
containerd / nerdctl
        |
        v
v0.13 Local OCI Registry
```

> **v0.13 is planned to add a Hacocoon-managed, local-only-by-default OCI registry shared by local Incus Environments, with pull/mirror use as the first slice and without weakening Hacocoon's existing credential, network, or control-plane boundaries.**
