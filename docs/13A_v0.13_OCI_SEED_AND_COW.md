# v0.13A — OCI Seed, Usage Telemetry & Btrfs/COW Optimization

Status: **usage telemetry/recommendation first slice implemented; Seed build/publish remains planned.**

This document defines Hacocoon's OCI Seed direction. The storage goal is to preload commonly used OCI images into an immutable Incus-derived Seed so future Environments can share unchanged physical blocks through the storage driver's normal copy-on-write path.

A Local Registry is **not required** for this design. Ordinary Environment-side `nerdctl pull` remains a normal direct pull to the configured upstream registry unless an operator separately chooses to deploy a registry/proxy.

OCI/container images are deliberately separated from Hacocoon/Incus Base images in the CLI. Base lifecycle uses `haco base ...`; OCI/containerd/nerdctl-specific operations use the optional `haco plugin oci ...` namespace.

## Goals

1. Keep ordinary `nerdctl` behavior inside Environments.
2. Learn which OCI images are actually common enough to deserve Seed space.
3. Keep Seed selection operator-controlled rather than automatically mutating Bases from agent activity.
4. Perform all networked Seed acquisition on the trusted Host side.
5. Keep the Seed Builder fully offline, ideally with no NIC at all.
6. Publish an immutable Seed only after containerd has been stopped cleanly.
7. Use Incus/storage-driver clone semantics so Btrfs can share unchanged Seed-derived blocks without sharing writable containerd state.

```text
ordinary Environment use

Environment
    |
    | nerdctl pull
    v
Docker Hub / GHCR / private registry

Seed construction

        |
        | trusted Host only
        v
Hacocoon Host seed namespace/cache
        |

        |
        v
Offline Seed Builder
(no NIC, no registry access)
        |

        |
  clean containerd stop

immutable Incus Seed revision
        |
      Incus clone
   (Btrfs COW when used)
      /    |    \
   Env A Env B Env C
```

## Ordinary Environment behavior

Seed membership is an optimization, not an OCI allowlist and not a replacement for normal nerdctl behavior.

If an image already exists in the Seed-derived containerd state, workloads can use it locally. If it is missing, the Environment may use ordinary direct registry access according to Hacocoon's network policy:

```text
nerdctl pull docker.io/library/python:3.14
nerdctl pull ghcr.io/example/tool:1.2
```

Hacocoon should not rewrite the normal command syntax merely to make Seed work.

Private-registry authentication is a separate authority problem. Host credentials must never be copied into arbitrary Environments automatically. Environment-owned credentials, standard nerdctl/Docker credential helpers, or a future Hacocoon credential-broker plugin may be used without making a Registry mandatory.

## Mandatory isolation rule

Hacocoon must never implement Seed storage savings by sharing one writable `/var/lib/containerd` across Environments.

Forbidden:

```text
shared writable /var/lib/containerd
        +--------+--------+
        |        |        |
      Env A    Env B    Env C
```

Required:

```text
immutable Seed filesystem
        |
   Incus storage clone
        +--------+--------+
        |        |        |
 independent   independent
 containerd    containerd
 state A       state B
```

Each Environment must remain independently deletable, corruptible, recoverable, and mutable without changing another Environment's logical containerd state.

## Host-side image acquisition

The component deciding what goes into a Seed is Hacocoon's trusted Host-side Seed Manager, not the Seed Builder and not a coding agent.

The Host may use a dedicated containerd namespace such as `hacocoon-seed` so downloads/content are isolated from unrelated host workloads:

```text
nerdctl --namespace hacocoon-seed pull <image>
```

The exact host implementation may evolve, but the authority boundary is fixed:

```text
Host seed acquisition     Internet/upstream: allowed by policy
Seed Builder              Internet/upstream: forbidden
Coding Environment        normal direct pull: governed separately
```

For authenticated upstreams, the Host uses Host-owned credentials or credential helpers. The resulting Seed contains image content and immutable digests, not registry credentials.

## Offline Seed Builder

The Seed Builder is deliberately simple and offline.

Required lifecycle:

1. resolve one logical Hacocoon Base to an immutable Base revision;
2. determine the explicit operator-approved Seed image set;
3. on the trusted Host, pull those images and resolve immutable OCI digests;
4. export/stream OCI content from the Host into a temporary Seed Builder;
5. create the builder from the pinned parent Base revision with no general network access, preferably no NIC;
6. import OCI content through supported containerd/nerdctl interfaces rather than copying containerd internals;
7. verify every requested digest is present and usable;
8. stop `containerd` cleanly;
9. stop the builder instance;
10. publish it as a new immutable Incus image revision;
11. persist a Seed manifest binding the Seed revision to the exact parent Base revision and OCI digests;
12. move the logical current-Seed pointer only after publication and validation succeed;
13. delete the temporary builder, surfacing recovery-required state if cleanup cannot be proven.

The builder must not fetch from Docker Hub, GHCR, a private registry, or a Hacocoon registry. It receives OCI content from the trusted Host side only.

The builder must not copy a live containerd metadata database using `cp`, `rsync`, tar of `/var/lib/containerd`, or a shared writable mount.

## Seed manifest

A Seed revision must retain metadata equivalent to:

```yaml
base:
  name: haco/ubuntu-26.04
  revision: sha256:<immutable-incus-base-fingerprint>

seed:
  revision: sha256:<immutable-published-seed-fingerprint>

images:
  - requested: docker.io/library/node:24
    digest: sha256:<digest>
  - requested: docker.io/library/golang:1.26
    digest: sha256:<digest>
  - requested: ghcr.io/example/private-tool:1.2
    digest: sha256:<digest>
```

Mutable OCI tags are input convenience only. Seed identity is based on immutable content digests plus the parent Base revision.

## Usage telemetry

Hacocoon should make Seed selection evidence-based without turning coding-agent activity into automatic Base mutation.

The first telemetry slice stores the **latest OCI image snapshot per Environment** on the trusted Host side. It samples through the provider-neutral Environment execution path using normal `nerdctl images` output and records only the image identity needed for Seed recommendations:

- Environment identifier;
- sample timestamp;
- repository;
- tag when present;
- immutable digest when observable.

It does **not** record command history, container output, registry passwords, tokens, credential-helper responses, or workspace contents.

The current first-slice commands are:

```text
haco plugin oci seed sample
haco plugin oci seed recommend
```

`sample` forces a current snapshot attempt for all known Environments.

`recommend` opportunistically refreshes stale snapshots before calculating results. The initial defaults are:

- snapshots newer than 6 hours are considered fresh and are not re-sampled;
- recommendations consider snapshots from the most recent 30 days.

A stopped/unavailable Environment may fail to sample without preventing recommendations from being produced from other recent valid snapshots. Failures are surfaced rather than silently treated as empty image sets.

## Recommendation semantics

Recommendation is based on how many recent Environment snapshots contain a specific `reference + immutable digest` pair.

Example:

```text
docker.io/library/node:24@sha256:aaa...      18 envs   90.0%
docker.io/library/golang:1.26@sha256:bbb...  15 envs   75.0%
postgres:18@sha256:ccc...                    12 envs   60.0%
```

Repeated sampling of the same Environment does not increase its weight because the store keeps one latest snapshot per Environment.

Images without an observed immutable digest may remain visible in telemetry state but are not eligible for Seed recommendation output. Hacocoon must not recommend a mutable tag as sufficient Seed identity.

Recommendation itself does not mutate an already-published Seed. Automatic top-10% selection is refined by `13B_v0.13_SEED_AUTO_PROMOTION.md`, and manual deletion tombstones in `13C_v0.13_OCI_IMAGE_DELETION.md` override automatic selection until explicitly superseded.

## Seed selection

A logical Base may have a current Seed pointer, but Environment creation must pin the selected immutable Seed image fingerprint before creation, just as v0.11 pins mutable Base aliases.

A Seed is compatible only when its recorded parent Base revision matches the currently resolved parent Base revision. If the logical parent Base moves, an old Seed must not silently become the starting point for the new Base revision.

Existing Environments remain on the exact revision they were created from.

## Btrfs/COW behavior

Hacocoon relies on Incus/storage-driver cloning rather than directly manipulating Btrfs subvolumes behind Incus.

When the selected Incus storage pool uses Btrfs, cloned Environment root filesystems should share unchanged physical blocks from the published Seed image until writes trigger copy-on-write.

The Hacocoon Core API must not expose Btrfs-specific path/subvolume operations. Btrfs remains a provider/storage optimization, not a new Core concept.

Non-COW storage drivers may still use the same Seed image for startup convenience but cannot claim equivalent physical-storage savings.

## Optional Local Registry

A Local Registry/proxy remains a possible later optimization for installations where repeated Seed misses cause excessive upstream downloads or where an operator wants a centralized OCI policy point.

It is not a prerequisite for:

- ordinary Environment-side `nerdctl pull`;
- Host-side Seed acquisition;
- offline Seed Builder operation;
- usage telemetry;
- Btrfs/COW Seed cloning.

If deployed, it must remain an optional adapter/infrastructure concern rather than becoming an accidental Core dependency.

## Capacity accounting

Documentation and status output must distinguish:

- Host seed-content/cache storage;
- immutable Seed image storage;
- logical Environment filesystem size;
- physical exclusive bytes where the backend can report them;
- shared/COW bytes where the backend can report them;
- optional Registry storage when one is configured.

Do not claim `N environments × image size` savings unless the active storage driver and measured physical usage actually prove it.

## Security requirements

- no shared writable containerd root between Environments;
- no host containerd/Docker socket inside the Seed Builder or a coding Environment;
- no Incus/Hacocoon control socket exposed to the Seed Builder workload;
- Seed Builder has no arbitrary upstream network path, preferably no NIC;
- networked Seed acquisition occurs on the trusted Host side;
- upstream credentials remain Host-owned during Seed acquisition and are not embedded into the Seed;
- telemetry records OCI identity, not secrets or arbitrary process/workspace data;
- malformed image references/digests and malformed persisted telemetry fail safely;
- mutable tags are never persisted as the only identity of Seed contents;
- containerd is stopped cleanly before publishing a Seed image;
- a failed/partial build never becomes the current Seed pointer;
- cleanup failure is surfaced as recovery-required state;
- GC prefers retaining data over deleting a Seed revision still required by an active/recoverable Environment.

## Implementation slices

### Implemented first slice — usage telemetry

1. Host-side persistent latest-snapshot store with process serialization and atomic replacement.
2. Provider-neutral sampling of `nerdctl images` for known Environments.
3. six-hour staleness guard for opportunistic sampling.
4. thirty-day recommendation window.
5. per-Environment weighting rather than raw sample-count weighting.
6. immutable-digest requirement for recommendation output.
7. explicit partial-failure reporting.
8. JSON and human-readable CLI output through `haco plugin oci seed sample|recommend`.

### Planned Seed build slice

1. explicit operator-approved Seed image list;
2. Host-side dedicated seed namespace/content cache;
3. Host-side authenticated/public upstream pull and digest resolution;
4. OCI export/stream into an offline Seed Builder;
5. clean containerd shutdown before publication;
6. immutable Incus Seed publication;
7. atomic current-Seed pointer movement only after validation;
8. compatible-Seed resolution during future Environment creation;
9. automatic COW benefit on Btrfs through normal Incus clone behavior;
10. fake-provider tests plus separate real Incus+Btrfs+containerd/nerdctl acceptance.

## Acceptance target

Repository/real-host acceptance should eventually prove:

1. telemetry samples two independent Environments without exposing credentials or workspace content;
2. repeated sampling of one Environment does not inflate recommendation weight;
3. malformed digests do not become Seed recommendations;
4. unavailable/stopped Environments are reported as sampling failures while valid recent snapshots remain usable;
5. a Host-side Seed acquisition can pull public and authenticated images without giving the builder those credentials;
6. the Seed Builder cannot reach arbitrary Internet destinations;
7. two Environments created from one Seed have independent containerd logical state;
8. existing Environments remain on an old Seed after a new revision is published;
9. a parent Base revision change makes the old Seed incompatible until rebuilt;
10. on Btrfs, measured physical storage demonstrates COW sharing for unchanged Seed-derived data;
11. on a non-COW backend, Hacocoon does not falsely report equivalent deduplication.

## Non-goals

- sharing one writable containerd content/snapshot database across Environments;
- requiring a Local Registry for Seed construction;
- requiring image-name rewriting for normal `nerdctl pull`;
- mutating existing Environments when the Seed changes;
- capturing an arbitrary developer/agent Environment as a reusable Seed;
- copying workspace contents or credentials into a Seed;
- making Seed membership an OCI allow/deny policy;
- automatically adding every observed image to the Seed;
- directly managing Incus-owned Btrfs subvolume internals from Hacocoon Core;
- promising physical deduplication on storage drivers that do not provide it.

> **Normal Environments keep normal nerdctl pull behavior. Hacocoon observes image usage on the trusted side, recommends common immutable image identities, acquires approved Seed content on the Host, feeds an offline Seed Builder, and relies on Incus/Btrfs COW without creating a shared writable containerd trust boundary.**
