# v0.13A — OCI Seed & Btrfs/COW Optimization

Status: **planned second slice of v0.13; not yet implemented on `main`.**

This document defines the storage-optimization companion to [`13_v0.13_LOCAL_OCI_REGISTRY.md`](13_v0.13_LOCAL_OCI_REGISTRY.md). The registry/cache gateway reduces repeated upstream downloads. OCI Seed reduces repeated per-Environment storage for commonly used unpacked container images.

## Goal

Preload selected OCI images into a stopped, immutable Hacocoon Incus Base revision and let Incus create future Environments from that revision using the storage driver's normal copy-on-write behavior.

The design must **not** share one live `/var/lib/containerd` between Environments. Each Environment keeps an independent containerd state tree; Btrfs/Incus COW may share underlying physical blocks until one Environment modifies them.

```text
allowed upstream OCI registries
            |
            v
Hacocoon Local Registry / cache gateway
            |
            | trusted Seed Builder pull path
            v
+------------------------------------+
| OCI Seed Builder                   |
| temporary trusted build instance   |
|                                    |
| containerd + nerdctl               |
| /var/lib/containerd                |
|   node / go / postgres / ...       |
+----------------+-------------------+
                 |
        stop containerd cleanly
                 |
        stop build instance
                 |
        publish immutable Incus image
                 v
+------------------------------------+
| Hacocoon Base + OCI Seed revision  |
+----------------+-------------------+
                 |
         Incus storage clone
          (Btrfs COW when used)
        +--------+--------+
        |        |        |
        v        v        v
      Env A    Env B    Env C
```

## Two-cache model

v0.13 intentionally has two different cache layers:

```text
Environment
    |
    | image already seeded
    v
OCI Seed / COW                 L1: startup/storage optimization
    |
    | miss
    v
Hacocoon Local Registry       L2: download/blob cache
    |
    | miss
    v
allowed upstream registry
```

- **Local Registry** avoids downloading the same OCI blobs from the Internet once per Environment.
- **OCI Seed** avoids storing the same preloaded containerd content as fully independent physical blocks in every freshly cloned Environment when the underlying Incus storage driver supports COW.

A registry hit does not by itself guarantee per-Environment disk deduplication. A seed hit does not replace the registry for images that were not preloaded.

## Mandatory isolation rule

Hacocoon must never implement this optimization by mounting one writable host or shared guest directory at `/var/lib/containerd` in multiple Environments.

Forbidden design:

```text
shared writable /var/lib/containerd
        +--------+--------+
        |        |        |
      Env A    Env B    Env C
```

Required design:

```text
immutable seed filesystem
        |
   storage-driver clone
        +--------+--------+
        |        |        |
 independent   independent
 containerd    containerd
 state A       state B
```

Each Environment must remain independently deletable, corruptible, recoverable, and mutable without changing another Environment's logical containerd state.

## Seed Builder lifecycle

The Seed Builder is a trusted Hacocoon-side build helper, not an ordinary coding-agent Environment.

The required lifecycle is:

1. resolve one logical Hacocoon Base to an immutable Base revision;
2. create a temporary Incus build instance from that pinned revision;
3. give the builder network reachability only to the Hacocoon Local Registry/cache gateway and other explicitly required trusted setup endpoints;
4. verify `containerd` and `nerdctl` are the expected managed runtime;
5. pull the configured seed image set using ordinary image references;
6. resolve and record immutable OCI digests for the pulled images;
7. verify the images are usable/unpacked as required by the selected containerd snapshotter;
8. stop `containerd` cleanly;
9. stop the builder instance;
10. publish it as a new immutable Incus image revision;
11. record a Seed manifest that binds the new revision to the parent Base revision and exact OCI digests;
12. delete the temporary builder; if cleanup cannot be proven, report recovery-required state rather than hiding leftovers.

The builder must not copy a live containerd metadata database with `cp`, `rsync`, tar, or a shared writable mount.

## Network boundary

The current `haco-sandbox` network intentionally fails closed for unmatched egress. OCI Seed must not weaken that boundary by temporarily granting a builder unrestricted Internet access.

The intended path is:

```text
Seed Builder
     |
     | only permitted registry path
     v
Hacocoon Local Registry
     |
     v
trusted upstream fetch path
```

Therefore the implementation order inside v0.13 is:

1. local registry/cache gateway;
2. transparent Environment-side registry routing;
3. a narrowly scoped Seed Builder registry path;
4. OCI Seed build/publish;
5. automatic use of a compatible current Seed during future Environment creation.

If the registry path is unavailable, Seed creation fails explicitly. It must not silently open unrestricted egress or fall back directly to Docker Hub/GHCR from the builder.

## Seed manifest

A Seed revision must have metadata equivalent to:

```yaml
base:
  name: haco/ubuntu-26.04
  revision: sha256:<immutable-incus-base-fingerprint>

seed:
  revision: sha256:<immutable-published-seed-fingerprint>

images:
  - requested: docker.io/library/node:24
    digest: sha256:<digest>
  - requested: docker.io/library/golang:1.26
    digest: sha256:<digest>
  - requested: docker.io/library/postgres:18
    digest: sha256:<digest>
```

Mutable OCI tags are input convenience only. Seed identity is based on immutable content digests plus the parent Base revision.

A rebuilt `node:24` that resolves to a different digest creates a different Seed revision.

## Seed selection

A logical Base may have a current Seed pointer, but Environment creation must pin the selected immutable Seed image fingerprint before `incus init`/creation just as v0.11 pins mutable Base aliases.

Conceptually:

```text
haco/ubuntu-26.04
      |
      +--> parent Base revision A
      |
      +--> current compatible Seed S2
                    |
                    v
             immutable fingerprint
                    |
                    v
              Environment
```

A Seed is compatible only when its recorded parent Base revision matches the currently resolved parent Base revision. If the parent Base moves from revision A to revision B, a Seed built from A must not silently remain the starting point for new B Environments.

Existing Environments stay on the exact revision they were created from.

## Btrfs/COW behavior

Hacocoon should rely on Incus/storage-driver cloning rather than directly manipulating Btrfs subvolumes behind Incus.

When the selected Incus storage pool uses Btrfs, cloned Environment root filesystems should naturally share unchanged physical blocks from the published Seed image until writes trigger copy-on-write.

The Hacocoon Core API must not expose Btrfs-specific path/subvolume operations. Btrfs is a provider/storage optimization, not a new Core concept.

Non-COW storage drivers may still use the same Seed image for startup convenience but cannot claim the same physical-storage savings.

## What happens when an image is not seeded

Seed membership is an optimization, not an allowlist.

Example:

```text
Seed contains: node, golang, postgres
Agent runs:    nerdctl pull python:3.14
```

Expected flow:

```text
Env containerd
      |
      | seed miss
      v
Hacocoon Local Registry
      |
   cache hit/miss
      v
allowed upstream
```

The Environment then owns its additional containerd data normally. Other Environments do not automatically gain the newly pulled image in their existing root filesystems.

A later Seed rebuild may include that image.

## Seed update policy

The first implementation must use an operator-controlled explicit seed list. It must not automatically grow the Base from arbitrary agent activity.

Future recommendation tooling may use aggregate cache/pull statistics to suggest candidates, for example:

```text
node:24       used by 84% of recent Environments
python:3.14   used by 72%
postgres:18   used by 61%
rare/tool     used by 2%
```

Recommendation is different from mutation. Automatic promotion into a new Seed requires a separate explicit policy decision.

## Capacity accounting

Documentation and status output must distinguish:

- registry blob storage;
- immutable Seed image storage;
- logical Environment filesystem size;
- physical exclusive bytes where the backend can report them;
- shared/COW bytes where the backend can report them.

Do not claim `N environments × image size` savings unless the active storage driver and measured physical usage actually prove it.

## Security requirements

- no shared writable containerd root between Environments;
- no host containerd/Docker socket inside a builder or coding Environment;
- no Incus/Hacocoon control socket exposed to the Seed Builder workload;
- builder upstream access goes through the Hacocoon registry path rather than unrestricted Internet egress;
- upstream credentials stay on the trusted registry side;
- all image references, digests, generated names, aliases, and returned fingerprints are validated before reuse;
- mutable tags are never persisted as the only identity of Seed contents;
- containerd is stopped cleanly before publishing a Seed image;
- a failed/partial build never becomes the current Seed pointer;
- cleanup failure is surfaced as recovery-required state;
- GC prefers retaining data over deleting a Seed revision still required by an active/recoverable Environment.

## First implementation slice

The v0.13 OCI Seed slice should include:

1. provider-owned Seed manifest types and strict validation;
2. an Incus Seed Builder that starts only after the Local Registry mediation path exists;
3. explicit configured seed-image list;
4. digest capture for every seed image;
5. clean containerd shutdown before image publication;
6. immutable Incus Seed publication;
7. atomic movement of a logical current-Seed pointer only after successful publication/validation;
8. compatible-Seed resolution during future Incus Environment creation;
9. automatic COW benefit when the Incus pool uses Btrfs, without direct Hacocoon manipulation of hidden Incus subvolumes;
10. fake-Incus unit/process tests plus real Incus+Btrfs+containerd/nerdctl acceptance as a separate supported-host gate.

## Acceptance target

At minimum, real-host acceptance should demonstrate:

1. build Seed S1 containing a public Docker Hub image through the Hacocoon Local Registry;
2. create two separate Environments from S1;
3. both Environments see/use the preseeded image without an upstream pull;
4. changing/removing image state in Env A does not change Env B;
5. a non-seeded image pull goes through Local Registry normally;
6. rebuilding the Seed with a changed tag digest produces a new immutable Seed revision;
7. existing Environments remain on the old revision;
8. a parent Base revision change makes the old Seed incompatible until rebuilt;
9. on a Btrfs Incus pool, measured physical storage demonstrates COW sharing for unchanged Seed-derived data;
10. on a non-COW backend, Hacocoon does not falsely report equivalent deduplication;
11. Seed Builder cannot reach arbitrary Internet destinations when only registry mediation is intended.

## Non-goals

- sharing one writable containerd content/snapshot database across Environments;
- mutating existing Environments when the Seed changes;
- capturing an arbitrary developer/agent Environment as a reusable Seed;
- copying workspace contents or agent credentials into a Seed;
- making seed membership an OCI allow/deny policy;
- automatically adding every cache hit to the Seed;
- directly managing Incus-owned Btrfs subvolume internals from Hacocoon Core;
- promising physical deduplication on storage drivers that do not provide it.

## Relationship to v0.11/v0.12/v0.13

```text
v0.11
logical Base -> immutable parent Base revision
                         |
                         v
v0.13A              OCI Seed build
                         |
               immutable Seed revision
                         |
                         v
                    Environment
                         |
                  v0.12 budgets
                         |
                  containerd/nerdctl
                         |
             v0.13 Local Registry
```

> **The Local Registry is the shared download cache; OCI Seed is the immutable preloaded runtime state that Incus/Btrfs can clone with copy-on-write. Hacocoon must gain the storage benefit without creating a shared writable containerd trust boundary.**
