# v0.13A — Optional OCI Plugin Seed, Usage Telemetry & Btrfs/COW Optimization

Status: **optional OCI-plugin usage telemetry/recommendation first slice implemented; Seed build/publish remains planned.**

This document defines the OCI plugin's Seed direction. OCI Seed is an optimization for installations that choose container tooling; it is not part of the minimum Hacocoon Core contract.

Hacocoon Core must continue to work when the OCI plugin is disabled and when `containerd`, `nerdctl`, and Docker are absent.

A Local Registry is **not required** for this design. Registry access, OCI image acquisition, image telemetry, Seed construction, and container CLI behavior are all optional OCI-plugin/profile concerns.

## Plugin boundary

The first implementation is enabled explicitly:

```text
HACO_PLUGIN_OCI=nerdctl
# or
HACO_PLUGIN_OCI=docker
```

When unset:

```text
HACO_PLUGIN_OCI=
```

Hacocoon does not compose OCI telemetry, does not run a container CLI, and does not require an OCI runtime in the Environment.

The project-maintained `nerdctl` profile may provide `containerd + nerdctl`. The Docker profile may use the genuine Docker CLI and, when needed, the plugin-owned Docker Engine compatibility units. These are profile decisions, not Core invariants.

## Goals

1. Keep Hacocoon Core independent from OCI/container tooling.
2. Preserve ordinary behavior of the selected OCI plugin profile inside Environments.
3. Learn which OCI images are common enough to deserve Seed space when telemetry is enabled.
4. Keep Seed selection separate from arbitrary agent authority.
5. Perform networked Seed acquisition only in a trusted plugin-side Host component.
6. Keep the Seed Builder offline, ideally with no NIC.
7. Publish immutable Seed state only after the selected OCI runtime has been stopped cleanly.
8. Use Environment/storage clone semantics so Btrfs can share unchanged Seed-derived blocks without sharing writable runtime state.


## Ordinary Environment behavior

Seed membership is an optimization, not an OCI allowlist.

The selected plugin profile should preserve the normal command semantics of the tool it exposes. For the project-maintained nerdctl profile, for example:

```text
nerdctl pull docker.io/library/python:3.14
nerdctl pull ghcr.io/example/tool:1.2
```

For a Docker CLI profile, ordinary `docker pull` semantics remain ordinary Docker semantics.

Hacocoon Core must not rewrite image names or container CLI syntax merely to make Seed work.

Private-registry authentication is a separate authority problem. Host credentials must never be copied into arbitrary Environments automatically. Environment-owned credentials, standard credential helpers, or a future credential-broker plugin may be used without making a Local Registry mandatory.

## Mandatory isolation rule

OCI-plugin storage savings must never share one writable runtime root across Environments.

For the project-maintained containerd profile, this is forbidden:

```text
shared writable /var/lib/containerd
        +--------+--------+
        |        |        |
      Env A    Env B    Env C
```

Required model:

```text
immutable Seed filesystem
        |
 Environment/storage clone
        +--------+--------+
        |        |        |
 independent   independent
 runtime       runtime
 state A       state B
```

Each Environment must remain independently deletable, corruptible, recoverable, and mutable without changing another Environment's logical OCI runtime state.

## Host-side image acquisition

The component deciding what goes into a Seed belongs to the trusted Host side of the OCI plugin, not to Hacocoon Core, the Seed Builder, or a coding agent.

A nerdctl/containerd plugin profile may use a dedicated Host namespace such as:

```text
nerdctl --namespace hacocoon-seed pull <image>
```

This is an implementation example for that plugin profile, not a Core API or requirement. Another OCI plugin driver may acquire/export content differently while preserving the same authority boundary:

```text
OCI plugin Host acquisition   Internet/upstream: allowed by policy
Seed Builder                  Internet/upstream: forbidden
Coding Environment            selected profile behavior, governed separately
```

For authenticated upstreams, the plugin Host component uses Host-owned credentials or credential helpers. The resulting Seed contains image content and immutable identities, never registry credentials.

## Offline Seed Builder

The Seed Builder is deliberately simple and offline.

Required lifecycle:

1. resolve one logical Hacocoon Base to an immutable Base revision;
2. determine the explicit or policy-selected Seed image set;
3. on the trusted OCI-plugin Host side, acquire those images and resolve immutable OCI digests;
4. export/stream OCI content from the Host into a temporary Seed Builder;
5. create the builder from the pinned parent Base revision with no general network access, preferably no NIC;
6. import OCI content through a supported plugin-profile interface rather than copying a live runtime database;
7. verify every requested digest is present and usable;
8. stop the selected OCI runtime cleanly;
9. stop the builder instance;
10. publish it as a new immutable Seed/Base revision through the Environment provider;
11. persist a Seed manifest binding the revision to the exact parent Base revision and OCI digests;
12. move the logical current-Seed pointer only after publication and validation succeed;
13. delete the temporary builder, surfacing recovery-required state if cleanup cannot be proven.

For a containerd profile, the builder must not copy a live `/var/lib/containerd` using `cp`, `rsync`, tar, or a shared writable mount. Equivalent rules apply to other mutable runtime databases.

## Seed manifest

A Seed revision retains metadata equivalent to:

```yaml
base:
  name: haco/ubuntu-26.04
  revision: sha256:<immutable-base-fingerprint>

seed:
  revision: sha256:<immutable-seed-fingerprint>

images:
  - requested: docker.io/library/node:24
    digest: sha256:<digest>
  - requested: docker.io/library/golang:1.26
    digest: sha256:<digest>
  - requested: ghcr.io/example/private-tool:1.2
    digest: sha256:<digest>
```

Mutable OCI tags are input convenience only. Seed identity is based on immutable content digests plus the parent Base revision.

## Usage telemetry

Telemetry is owned entirely by the optional OCI plugin.

The first slice stores the **latest OCI image snapshot per Environment** on the trusted Host side. Sampling uses Hacocoon's generic Environment execution path, but the concrete container command is selected by the plugin driver:

```text
HACO_PLUGIN_OCI=nerdctl
  -> nerdctl images --format ...

HACO_PLUGIN_OCI=docker
  -> docker images --digests --format ...
```

Core code must not contain either command as an invariant.

Telemetry records only:

- Environment identifier;
- sample timestamp;
- repository;
- tag when present;
- immutable digest when observable.

It does **not** record command history, container output, registry passwords/tokens, credential-helper responses, or workspace contents.

The current plugin commands are:

```text
haco plugin oci seed sample
haco plugin oci seed recommend
```

`sample` forces a current snapshot attempt for all known Environments.

`recommend` opportunistically refreshes stale snapshots before calculating results. Initial defaults remain:

- snapshots newer than 6 hours are considered fresh and are not re-sampled;
- recommendations consider snapshots from the most recent 30 days.

A stopped/unavailable Environment may fail to sample without preventing recommendations from being produced from other recent valid snapshots. Failures are surfaced rather than silently treated as empty image sets.

If the OCI plugin is disabled, no OCI telemetry is collected.

## Recommendation semantics

Recommendation is based on how many recent Environment snapshots contain a specific `reference + immutable digest` pair.

```text
docker.io/library/node:24@sha256:aaa...      18 envs   90.0%
docker.io/library/golang:1.26@sha256:bbb...  15 envs   75.0%
postgres:18@sha256:ccc...                    12 envs   60.0%
```

Repeated sampling of the same Environment does not increase its weight because the store keeps one latest snapshot per Environment.

Images without an observed immutable digest may remain visible in plugin telemetry state but are not eligible for Seed recommendation output.

The v0.13B plugin policy marks the top 10% of eligible recommendations for automatic inclusion in the next Seed input set. Selection never grants credentials or mutates an already-published Seed/Environment.

## Seed selection

A logical Base may have a plugin-managed current Seed pointer, but Environment creation must pin the selected immutable Seed revision before creation.

A Seed is compatible only when its recorded parent Base revision matches the currently resolved parent Base revision. If the parent Base moves, an old Seed must not silently become the starting point for the new revision.

Existing Environments remain on the exact revision they were created from.

## Btrfs/COW behavior

The OCI plugin relies on the Environment/storage provider's normal clone semantics rather than manipulating Btrfs subvolumes behind that provider.

When the active storage pool uses Btrfs, cloned Environment root filesystems may share unchanged physical blocks from the published Seed until writes trigger copy-on-write.

The Hacocoon Core API must not expose Btrfs-specific path/subvolume operations. Btrfs remains a provider/plugin optimization, not a new Core concept.

Non-COW storage drivers may still use the same Seed image for startup convenience but cannot claim equivalent physical-storage savings.

## Optional Local Registry

A Local Registry/proxy remains an optional OCI-plugin/infrastructure feature for installations where repeated misses cause excessive upstream downloads or where an operator wants a centralized OCI policy point.

It is not a prerequisite for:

- direct pulls in a selected OCI profile;
- Host-side Seed acquisition;
- offline Seed Builder operation;
- usage telemetry;
- Btrfs/COW Seed cloning.

If deployed, it must remain optional and must not become an accidental Core dependency.

## Capacity accounting

Documentation and status output must distinguish:

- plugin Host seed-content/cache storage;
- immutable Seed image storage;
- logical Environment filesystem size;
- physical exclusive bytes where the backend can report them;
- shared/COW bytes where the backend can report them;
- optional Registry storage when configured.

Do not claim `N environments × image size` savings unless the active storage driver and measured physical usage actually prove it.

## Security requirements

- the OCI plugin is opt-in; Core must work without it;
- no shared writable runtime root between Environments;
- no Host containerd/Docker socket inside a Seed Builder or coding Environment;
- no Incus/Hacocoon control socket exposed to plugin workloads;
- Seed Builder has no arbitrary upstream network path, preferably no NIC;
- networked Seed acquisition occurs only on the trusted plugin Host side;
- upstream credentials remain Host-owned and are not embedded into the Seed;
- telemetry records OCI identity, not secrets or arbitrary process/workspace data;
- malformed image references/digests and malformed persisted telemetry fail safely;
- mutable tags are never persisted as the only identity of Seed contents;
- the selected OCI runtime is stopped cleanly before publishing a Seed image;
- a failed/partial build never becomes the current Seed pointer;
- cleanup failure is surfaced as recovery-required state;
- GC prefers retaining data over deleting a Seed revision still required by an active/recoverable Environment.

## Implementation slices

### Implemented first slice — optional OCI plugin usage telemetry

1. plugin-owned Host-side latest-snapshot store with process serialization and atomic replacement;
2. explicit `nerdctl` and Docker inventory drivers;
3. generic Environment execution used only as the transport boundary;
4. six-hour staleness guard for opportunistic sampling;
5. thirty-day recommendation window;
6. per-Environment weighting rather than raw sample-count weighting;
7. immutable-digest requirement for recommendation output;
8. explicit partial-failure reporting;
9. JSON and human-readable output through `haco plugin oci seed sample|recommend`;
10. no plugin composition when `HACO_PLUGIN_OCI` is unset.

### Planned second slice — Seed build/publish

Seed build/publish is **not yet implemented as a complete end-to-end path on `main`**. The planned second slice includes:

1. policy-selected Seed image list;
2. plugin Host-side Seed namespace/content cache;
3. Host-side authenticated/public upstream acquisition and digest resolution;
4. OCI export/stream into an offline Seed Builder;
5. clean selected-runtime shutdown before publication;
6. immutable Seed publication;
7. atomic current-Seed pointer movement only after validation;
8. compatible-Seed resolution during future Environment creation;
9. COW benefit on Btrfs through normal provider clone behavior;
10. fake-provider tests plus separate real Environment+Btrfs+OCI-profile acceptance.

## Acceptance target

Repository/real-host acceptance should eventually prove:

1. Core initializes and operates with the OCI plugin disabled and container tooling absent;
2. `HACO_PLUGIN_OCI=nerdctl` samples through nerdctl only;
3. `HACO_PLUGIN_OCI=docker` samples through Docker CLI only;
4. repeated sampling of one Environment does not inflate recommendation weight;
5. malformed digests do not become Seed recommendations;
6. unavailable/stopped Environments are reported as sampling failures while valid recent snapshots remain usable;
7. Host-side Seed acquisition can use authenticated images without giving the builder those credentials;
8. the Seed Builder cannot reach arbitrary Internet destinations;
9. two Environments created from one Seed have independent logical runtime state;
10. existing Environments remain on an old Seed after a new revision is published;
11. a parent Base revision change makes the old Seed incompatible until rebuilt;
12. on Btrfs, measured physical storage demonstrates COW sharing for unchanged Seed-derived data;
13. on a non-COW backend, Hacocoon does not falsely report equivalent deduplication.

## Non-goals

- making OCI tooling part of Hacocoon Core;
- sharing one writable OCI runtime database across Environments;
- requiring a Local Registry for Seed construction;
- requiring image-name rewriting for normal plugin-profile pulls;
- mutating existing Environments when the Seed changes;
- capturing an arbitrary developer/agent Environment as a reusable Seed;
- copying workspace contents or credentials into a Seed;
- making Seed membership an OCI allow/deny policy;
- directly managing provider-owned Btrfs subvolume internals from Hacocoon Core;
- promising physical deduplication on storage drivers that do not provide it.

> **OCI Seed is an optional plugin optimization. Hacocoon Core stays container-tool-agnostic; the selected OCI plugin profile owns nerdctl/Docker behavior, telemetry, Seed acquisition, and runtime-specific storage handling.**
