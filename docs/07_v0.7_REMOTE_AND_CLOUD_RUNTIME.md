# v0.7 — Remote / Cloud Runtime & External Capabilities

Status: **roadmap contract implemented on `main`, with real AWS acceptance still pending.** The EC2 backend remains experimental and disabled by default. Hacocoon remains pre-1.0 and remote-provider configuration/behavior may change incompatibly.

## Goal

Extend the proven local Workspace/Environment boundary to remote/cloud execution without leaking provider-specific conditionals into Core.

## EC2 release status: experimental and disabled by default

The EC2 Environment Provider in v0.7 is **experimental**. Its implementation does not make EC2 a normal supported backend.

Default Hacocoon behavior remains local-first:

- the local Incus runtime remains available without any experimental setting;
- EC2 is disabled by default;
- selecting EC2 currently requires `HACO_RUNTIME_PROVIDER=runtime.ec2`;
- constructing the real EC2 provider additionally requires the explicit host/operator opt-in `HACO_EXPERIMENTAL_EC2=1`;
- AWS credentials, AWS environment variables, the AWS CLI, or cloud metadata must never implicitly enable EC2;
- when the EC2 gate is disabled, Hacocoon fails closed before real provider construction or any AWS CLI/network activity;
- upgrades must never silently enable EC2;
- CLI/help/status surfaces that expose EC2 must clearly label it as experimental;
- EC2 configuration and behavior may change incompatibly during the experimental period.

Disabling the gate must not destroy existing remote state. If an existing EC2-backed Environment needs lifecycle, cleanup, or recovery operations, the operator must explicitly re-enable the experimental gate before Hacocoon may contact AWS.

## Current v0.7 implementation

The repository currently contains:

- provider-neutral Environment routing;
- local `runtime.incus` as the default provider;
- experimental `runtime.ec2` routing behind explicit opt-in;
- S3-staged workspace transfer and SSM-driven EC2 execution;
- host-side brokered `aws.api` read operations;
- adapter-owned EBS replacement/recovery mechanics;
- fake-AWS process integration and CLI E2E coverage.

Real AWS/EC2/SSM/EBS acceptance remains a separate environment-dependent gate and must not be inferred from fake-provider tests.

## EC2/EBS provisioning design gate

The EC2/EBS implementation must preserve an explicit ownership boundary for:

- EC2 lifecycle;
- IAM role/credential scope;
- workspace movement;
- EBS creation/attachment/replacement;
- cleanup after failure;
- how host/manager authority stays outside the untrusted workload.

This is the **EC2/EBS provisioning design gate**. The detailed implementation contract is recorded in `REMOTE_CLOUD_PROVISIONING.md`.

## Experimental EC2 acceptance gate

The implemented path must continue to satisfy these invariants:

- a default installation cannot select or initialize the real EC2 Environment Provider;
- explicit operator opt-in enables EC2;
- a request for EC2 while disabled returns a clear error and performs **no AWS API call** or AWS CLI process invocation;
- local Incus behavior is unchanged whether the EC2 experimental gate exists or not;
- no existing config migration, AWS environment variable, credential file, instance role, or metadata source can implicitly enable EC2;
- tests cover both the disabled-by-default path and the explicit opt-in path;
- documentation and user-facing discovery consistently mark EC2 as experimental.

## Remote execution boundary

The initial remote implementation uses host-side AWS control-plane operations plus S3 staging and SSM rather than exposing inbound SSH by default.

Provider-specific runtime state remains opaque to Core. Core must not accumulate AWS fields or `if remote` / `if ec2` branches.

## AWS capability boundary

External AWS authority is separate from EC2 Environment lifecycle.

The first `aws.api` capability is deliberately narrow and host-side. Authority-sensitive target information must be visible to Policy/Approval/Audit rather than hidden in opaque parameters. A capability request must not vend a broad parent AWS credential into the Environment.

Additional mutating AWS operations require explicit capability actions and a reviewed authority model; they must not be smuggled through a generic escape hatch.

## Storage rule

Storage mechanics are provider/adapter details, not Core concepts unless a provider-independent invariant truly exists.

EBS cannot be shrunk in place; a smaller target requires replacement and verified migration. The source volume is not automatically deleted by the replacement transaction.

Local filesystem/image shrinking, if retained, belongs behind the relevant adapter and must never become a required Core runtime concept merely because historical storage code exists.

## Failure and recovery rule

Remote/cloud operations must remain conservative under partial failure:

- incomplete EC2 creation attempts cleanup and surfaces cleanup failure;
- read/write workspace sync-back failure must not silently terminate the only copy of uncollected data;
- ambiguous remote state becomes recovery-required rather than guessed;
- EBS replacement after an unsafe transition retains recoverable resources rather than performing an unprovable destructive rollback;
- policy/approval/audit failure must not execute unreviewed external authority.

## Core rule

Local Incus and remote EC2 meet the same higher-level Environment contract. Provider-specific implementation mechanics stay behind adapters.

## Compatibility note

EC2 is intentionally more unstable than the local default path. The opt-in variable names, remote image contract, staging mechanics, state representation, and provider details may change before a stable compatibility milestone. The **default-off, explicit-opt-in, fail-closed, no-ambient-parent-credential invariants** are the important security properties to preserve.
