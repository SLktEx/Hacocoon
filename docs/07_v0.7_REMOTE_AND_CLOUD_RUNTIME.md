The previous EC2 backend was **experimental and disabled by default**, and real AWS acceptance was still pending when it was deferred. Hacocoon remains pre-1.0; any future remote-provider configuration or behavior may change incompatibly from the historical implementation described below.

## Goal

Extend the proven local Workspace/Environment boundary to remote/cloud execution without leaking provider-specific conditionals into Core.

The goal remains valid even though the concrete cloud adapter is currently deferred.

## Historical EC2 release status: experimental and disabled by default

The v0.7 EC2 Environment Provider was **experimental**. Its implementation did not make EC2 a normal supported backend.

The historical contract was local-first:

- the local Incus runtime remained available without any experimental setting;
- EC2 was disabled by default;
- selecting EC2 required `HACO_RUNTIME_PROVIDER=runtime.ec2`;
- constructing the real EC2 provider additionally required explicit host/operator opt-in through `HACO_EXPERIMENTAL_EC2=1`;
- AWS credentials, AWS environment variables, the AWS CLI, or cloud metadata could never implicitly enable EC2;
- when the EC2 gate was disabled, Hacocoon failed closed before real provider construction or any AWS CLI/network activity;
- upgrades could not silently enable EC2;
- CLI/help/status surfaces exposing EC2 had to label it experimental;
- EC2 configuration and behavior were allowed to change incompatibly during the experimental period.

These environment variables are **not current supported runtime configuration** because the EC2 provider is not present in the active implementation tree.

## Current v0.7 implementation reality

The repository currently contains:

- provider-neutral Environment routing;
- local `runtime.incus` as the registered Environment provider;
- generic routing tests that keep the provider seam exercised without a cloud implementation.

The repository currently does **not** contain the previous:

- `runtime.ec2` implementation;
- S3-staged workspace transfer / SSM-driven EC2 execution;
- host-side `aws.api` capability implementation;
- EBS replacement/recovery implementation;
- cloud-specific fake-AWS E2Es.

Those pieces remain recoverable from Git history. Real cloud acceptance will be defined again when a cloud adapter is reintroduced.

## EC2/EBS provisioning design gate

If EC2/EBS support is restored, it must preserve an explicit ownership boundary for:

- EC2 lifecycle;
- IAM role/credential scope;
- workspace movement;
- EBS creation/attachment/replacement;
- cleanup after failure;
- how host/manager authority stays outside the untrusted workload.

This is the **EC2/EBS provisioning design gate**. The detailed historical implementation contract is recorded in `REMOTE_CLOUD_PROVISIONING.md`.

## Future cloud acceptance gate

A restored cloud implementation must continue to satisfy these invariants:

- a default installation cannot select or initialize a real cloud Environment Provider merely because cloud credentials or metadata are present;
- remote/cloud operation requires explicit operator opt-in;
- a disabled or unsupported cloud request fails before provider-side effects;
- local Incus behavior is unchanged by the presence or absence of a cloud adapter;
- no credential file, environment variable, instance role, or metadata source can implicitly grant cloud-runtime authority;
- tests cover disabled/default behavior and explicit opt-in behavior;
- documentation and user-facing discovery clearly identify experimental cloud support until it reaches a later support gate.

## Remote execution boundary

The historical EC2 implementation used host-side AWS control-plane operations plus S3 staging and SSM rather than exposing inbound SSH by default.

That mechanism is not a current compatibility promise. The durable architectural rule is that provider-specific runtime state remains opaque to Core. Core must not accumulate AWS fields or `if remote` / `if ec2` branches.

## External capability boundary

External cloud authority is separate from Environment lifecycle.

The historical `aws.api` capability was deliberately narrow and host-side. If an AWS or other cloud capability returns later, authority-sensitive target information must remain visible to Policy/Approval/Audit rather than hidden in opaque parameters. A capability request must not vend a broad parent cloud credential into the Environment.

Additional mutating cloud operations require explicit capability actions and a reviewed authority model; they must not be smuggled through a generic escape hatch.

## Storage rule

Storage mechanics are provider/adapter details, not Core concepts unless a provider-independent invariant truly exists.

The historical EBS helper followed the AWS rule that EBS cannot be shrunk in place: a smaller target required replacement and verified migration, and the source volume was not automatically deleted by the replacement transaction.

If a future cloud adapter uses different storage mechanics, those details stay behind that adapter. Local filesystem/image shrinking, if retained, likewise belongs behind the relevant adapter and must never become a required Core runtime concept merely because historical storage code exists.

## Failure and recovery rule

Remote/cloud operations must remain conservative under partial failure:

- incomplete remote creation attempts cleanup and surfaces cleanup failure;
- read/write workspace sync-back failure must not silently terminate the only copy of uncollected data;
- ambiguous remote state becomes recovery-required rather than guessed;
- storage replacement after an unsafe transition retains recoverable resources rather than performing an unprovable destructive rollback;
- policy/approval/audit failure must not execute unreviewed external authority.

## Core rule

Local Incus and any future remote/cloud adapter must meet the same higher-level Environment contract. Provider-specific implementation mechanics stay behind adapters.

## Compatibility note

The historical EC2 opt-in variable names, remote image contract, staging mechanics, state representation, and provider details are **not current compatibility commitments**. A future cloud adapter may be redesigned before it returns.

The durable properties to preserve are: **explicit opt-in, fail closed before provider-side effects, keep reusable credentials on the trusted side, and keep provider-specific details out of Core.**
