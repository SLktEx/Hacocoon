# v0.7 — Remote / Cloud Runtime & External Capabilities

## Goal

Extend the proven local Workspace/Environment boundary to remote/cloud execution without leaking provider-specific conditionals into Core.

## EC2 release status: experimental and disabled by default

The EC2 Environment Provider in v0.7 is **experimental**. Shipping v0.7 does not make EC2 a normal supported backend.

Default Hacocoon behavior must remain local-first:

- the local Incus runtime remains available without any experimental setting;
- EC2 must be disabled by default;
- selecting or initializing EC2 requires an explicit host/operator opt-in;
- the opt-in must be Hacocoon-owned configuration or an explicit CLI setting, not implicit AWS credential discovery;
- when the EC2 gate is disabled, Hacocoon must fail closed before provider initialization, credential acquisition, network access, or any AWS API call;
- upgrades must never silently enable EC2;
- CLI/help/status surfaces that expose EC2 must clearly label it as experimental;
- EC2 configuration and behavior may change incompatibly during the experimental period.

The exact configuration key or CLI spelling may be chosen during v0.7 implementation, but the **disabled-by-default and explicit-opt-in invariant is part of the v0.7 acceptance gate**.

Disabling the gate must not destroy existing remote state. If an existing EC2-backed Environment needs lifecycle or cleanup operations, the operator must explicitly re-enable the experimental gate before Hacocoon may contact AWS.

## In scope candidates

- `EC2 Environment Provider` (experimental, explicit opt-in only).
- AWS Capability provider.
- Provider-native short-lived AWS credential flow.
- Remote workspace transfer/synchronization/mount strategy.
- Network policy for remote environments.
- Storage-provider boundary where remote runtime requires it.
- EBS adapter and replacement/migration flow for shrink-like operations.
- Advanced local Btrfs/storage adapters only when justified by real runtime needs.

## EC2/EBS provisioning design gate

Before EC2/EBS implementation is accepted, document and test the exact ownership boundary for:

- EC2 lifecycle;
- IAM role/credential scope;
- workspace movement;
- EBS creation/attachment/replacement;
- cleanup after failure;
- how host/manager authority stays outside the untrusted workload.

This is the **EC2/EBS provisioning design gate**.

## Experimental EC2 acceptance gate

Before v0.7 is accepted:

- a default installation cannot select or initialize the EC2 Environment Provider;
- an explicit operator opt-in enables EC2;
- a request for EC2 while disabled returns a clear error and performs no AWS API call;
- local Incus behavior is unchanged whether the EC2 experimental gate exists or not;
- no existing config migration, AWS environment variable, credential file, or instance role can implicitly enable EC2;
- tests cover both the disabled-by-default path and the explicit opt-in path;
- documentation and user-facing discovery consistently mark EC2 as experimental.

## Storage rule

Storage mechanics are provider/adapter details, not Core concepts unless a provider-independent invariant truly exists.

EBS cannot be shrunk in place; a smaller target requires replacement and verified migration. Local filesystem/image shrinking, if retained, belongs behind the relevant adapter and must never be required for the v0.1 runtime path.

## Core rule

Local Incus and remote EC2 must meet the same higher-level Environment contract. Core should not accumulate `if remote` / `if ec2` branches.
