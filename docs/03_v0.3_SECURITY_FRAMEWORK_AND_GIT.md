# Hacocoon v0.3 - Security Framework and Git Specification

Status: Draft for implementation  
Requires: v0.2 Developer Workspace acceptance gate

## 1. One-sentence definition

Hacocoon v0.3 establishes the dedicated Security Framework: a Session requests an external Capability, the Hacocoon capability policy decides `ALLOW / ASK / DENY`, an exact Grant/Lease is created, and the first privileged Feature Plugin - Git - performs safe clone/fetch/push without exposing Manager credentials.

## 2. Why the mature security model moves here

Historical plans first built Git-specific policy and later generalized it. The rebaseline does the opposite: define the generic authorization objects now, then implement only the Git Provider in v0.3.

This prevents later AWS/GitHub/registry support from forcing a rewrite of approvals, audit, identity, or policy semantics.

## 3. Goals

1. Give every Session a cryptographically or OS-isolated Session identity for Manager IPC.
2. Define a canonical `CapabilityRequest` independent of raw CLI arguments.
3. Define provider-neutral capability policy using Principal, Action, Resource, Condition, Effect.
4. Define deterministic decision ordering.
5. Implement `ALLOW / ASK / DENY`.
6. Implement exact human approval and temporary Grant/Lease lifecycle.
7. Implement provider-neutral audit without secrets.
8. Implement safe Git transport as the first Provider.
9. Preserve normal `git clone/fetch/push` UX where practical.
10. Allow branch/org/repo/force/delete/tag policy.
11. Bind approved push to the exact source object/SHA and target ref.
12. Support an Agent waiting on an `ASK` request rather than requiring uncontrolled retries.

## 4. Non-goals

- broad `gh` API support;
- raw GitHub token injection;
- AWS credential delegation;
- Packer/Terraform integration;
- remote Gateway/EC2 deployment (v0.7);
- GUI device capabilities (v0.5).

The data model may represent these future capability kinds, but only Git must be complete.

## 5. Trust boundary

The normative security model is `00B_SECURITY_ARCHITECTURE.md`.

v0.3 does **not** add an enterprise human IAM/SSO layer. Authentication/Access Layer is outside Hacocoon. v0.3 authorizes what a Session principal may do across the sandbox boundary.

```text
Session [UNTRUSTED]
  git / agent / shell
       |
       | per-Session IPC
       v
Manager [TRUSTED]
  Session Identity
  Normalize
  Capability Policy
  Approval / Grants
  Git Provider
  Manager credential store/reference
       |
       v
Git host
```

Session root must not be able to impersonate a different Session by choosing an arbitrary `session_id` field. Identity is bound by the IPC transport/endpoint created for that Session.

## 6. Security Framework objects

### 6.1 CapabilityRequest

Conceptual representation:

```yaml
request_id: req_...
principal:
  session: sess_123
  actor: agent
provider: git
action: git.push
resource: git://github.com/my-org/my-repo/refs/heads/feature/x
conditions:
  force: false
  delete: false
  source_sha: abcdef...
payload_digest: sha256:...
created_at: ...
```

Raw `argv` is not the authorization object.

### 6.2 Capability Profile / Policy

A reusable Capability Profile may supply baseline sandbox intent, while individual policy rules provide fine-grained `ALLOW / ASK / DENY`. This is not an AWS-IAM clone and does not manage human identities.


```yaml
version: 1
policies:
  - name: feature-push
    effect: allow
    actions: [git.push]
    resources:
      - git://github.com/my-org/my-repo/refs/heads/feature/**
    conditions:
      force: false
      delete: false

  - name: main-needs-human
    effect: ask
    actions: [git.push]
    resources:
      - git://github.com/my-org/my-repo/refs/heads/main

  - name: force-push-deny
    effect: deny
    actions: [git.push]
    resources: [git://github.com/my-org/**]
    conditions:
      force: true
```

### 6.3 Decision ordering

Use:

```text
explicit DENY
  > matching ASK
  > matching ALLOW
  > default DENY
```

A temporary Grant never overrides an explicit deny.

### 6.4 Grant / Lease

A Grant is authorization to exercise an exact Capability under constraints.

```yaml
grant_id: gr_...
request_id: req_...
principal: session:sess_123
action: git.push
resource: git://github.com/my-org/my-repo/refs/heads/main
constraints:
  source_sha: abcdef...
  force: false
  delete: false
expires_at: ...
uses_remaining: 1
```

A Lease is the runtime realization when useful. For Git v0.3, the protocol operation itself may consume a one-use Grant without returning a reusable credential.

## 7. Approval semantics

### 7.1 Exact approval

Human approval binds to:

- Session principal;
- action;
- resource;
- normalized conditions;
- payload/source digest where relevant;
- expiry;
- allowed use count.

If any bound field changes after approval, the old approval cannot authorize the new operation.

### 7.2 Approval CLI

Required:

```bash
haco approvals
haco approve <request-id>
haco deny <request-id>
haco grants
```

Approval UI in VS Code, Windows notifications, or Gateway pages may be added later. They are clients; the Manager state is the authority.

### 7.3 Agent waiting

When a brokered operation receives `ASK`, the request becomes `pending`. An agent adapter may report `waiting-for-approval` and resume/retry the bound operation after approval.

Repeated identical retries should correlate/deduplicate rather than create a flood of approval requests.

## 8. Session IPC

Required properties:

- unique per Session;
- inaccessible to unrelated Sessions;
- Manager derives Session identity from endpoint context, not caller-provided text alone;
- supports request/response and pending result semantics;
- never returns Manager parent credentials;
- secret-aware logging/sanitization.

Unix sockets or an equivalent local transport are appropriate for local Manager/Incus environments.

## 8.1 CapabilityProvider boundary

v0.3 freezes the security-sensitive provider call order:

```text
raw provider request
      |
      v
CapabilityProvider.Normalize
      |
      v
Security Framework capability policy
      |
 ALLOW / ASK / DENY
      |
      v
Security Framework issues exact Grant
      |
      v
CapabilityProvider.Materialize / Execute
```

A provider may define how a request is normalized and how an approved Grant is realized. It may not implement the Capability Policy evaluator, mint Grants, consume approvals, or write authoritative approval state.

Git is the first Feature Plugin implementing the `CapabilityProvider` contract. The interface is introduced now so v0.4 can add AWS/GitHub/Registry without changing the Security Framework contracts.

Unknown provider namespaces or requests that cannot be normalized fail closed.

## 9. Git Provider

### 9.1 Strategy

Git uses `brokered-protocol` rather than delegated long-lived credentials.

Target UX:

```text
Session git
   ↓
git-remote-haco / credential-neutral transport
   ↓
per-Session IPC
   ↓
Git Provider
   ↓ normalize
Security Framework
   ↓
ALLOW / ASK / DENY
   ↓
Manager-side authenticated Git transport
   ↓
Git host
```

### 9.2 Repository reads

`git.clone` and `git.fetch` may be allow-by-default for configured repositories, subject to repo/network policy. Manager authentication remains outside the Session.

v0.2 Manager repo-cache ingestion may remain the preferred clone optimization; the Provider should use the same canonical repository identity rather than create a second incompatible identity model.

### 9.3 Push normalization

Normalize at least:

- host;
- owner/org;
- repository;
- target ref;
- source object/SHA;
- force flag;
- delete operation;
- tag vs branch;
- requested ref updates.

Multi-ref pushes should be evaluated safely. A simple first implementation may reject mixed decisions in a single push rather than partially applying an ambiguous set.

### 9.4 Exact source enforcement

For an approved push, the Provider must ensure the externally pushed source object is the source SHA that was evaluated/approved.

Do not approve only a human-readable branch name and then push whatever that branch happens to point to later.

### 9.5 Force/delete

Force push and ref deletion are separate high-risk conditions and should default to `ASK` or `DENY`, not silently inherit ordinary feature-branch allow rules.

## 10. Credential handling

Manager may use configured Git authentication sources such as:

- host `gh` login;
- external credential helper;
- GitHub App in environments where installation is possible;
- future provider-specific auth source.

The Session must not be able to run a command that extracts the underlying credential.

No GitHub PAT/SSH private key is copied into `/workspace`, environment variables, Session home, logs, or state DB.

## 11. Audit

Audit events should include:

```text
request.created
iam.decision
approval.requested
approval.approved / denied
grant.issued / consumed / expired / revoked
provider.operation.started / succeeded / failed
```

Useful fields:

- timestamp;
- Session ID;
- actor;
- provider/action/resource;
- normalized non-secret conditions;
- request/grant correlation IDs;
- decision and policy rule;
- result status.

Never log token values, private keys, AWS secrets, authorization headers, or credential-helper plaintext.

## 12. CLI additions

```bash
haco iam check ...            # optional debugging view
haco approvals
haco approve <request>
haco deny <request>
haco grants
haco audit [filters]
```

Git itself should remain the primary user command:

```bash
git fetch
git push origin feature/x
```

Avoid requiring `haco git push` as the permanent UX unless used only as a debugging fallback.

## 13. State additions

```text
policies / policy_sources
capability_requests
approvals
grants
audit_events
session_ipc
```

Credential values do not belong in generic Grant or Audit tables.

## 14. Migration from historical Git security code

Historical designs used publish/push-specific approval logic. Refactor that logic into:

```text
Git request normalization
        ↓
shared Security Framework decision
        ↓
shared approval/grant lifecycle
        ↓
Git Provider execution
```

Do not let `GitPolicyEngine` become the real authorization authority while a generic IAM layer merely mirrors it. Git should be a consumer of the Security Framework.

## 16. Security test matrix

| Scenario | Expected |
|---|---|
| Session reads Manager Git token | impossible |
| Session reads host SSH private key | impossible |
| allowed feature push, non-force | automatic allow |
| protected main push | ASK or DENY by policy |
| force push where explicitly denied | DENY even with unrelated grant |
| target ref changes after approval | old approval invalid |
| source SHA changes after approval | old approval invalid |
| expired grant reused | denied |
| consumed single-use grant reused | denied |
| Session A calls Session B IPC | denied/unreachable |
| malformed/unknown Git operation | fail closed |
| secret appears in provider error | sanitizer removes/redacts |

Plugin/security acceptance additions:

- Git Provider can be replaced by a fake CapabilityProvider in Security Framework tests.
- `Materialize` is never called before a valid Security Framework ALLOW/approved Grant exists.
- provider code cannot directly mark its own request approved in Security Framework state.
- a provider claiming an unconfigured capability namespace is rejected.

## 17. Acceptance criteria

- Session Git can fetch a configured private repository without receiving Manager credentials;
- normal `git push` reaches the Git Provider path;
- policy can allow an exact feature-branch pattern automatically;
- protected branch policy can produce `ASK`;
- human approval resumes only the exact approved action;
- source SHA mutation after approval is rejected;
- force/delete conditions are independently enforceable;
- explicit deny cannot be bypassed by a temporary Grant;
- audit correlates request -> decision -> approval/grant -> provider result;
- raw credentials do not appear in Session, SQLite, or logs;
- Agent can enter a waiting-for-approval state without uncontrolled retry spam.
