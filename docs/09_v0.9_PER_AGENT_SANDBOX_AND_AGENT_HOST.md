# v0.9 Per-Agent Sandbox & Agent Host Integration

**Status:** implementation foundation introduced on 2026-08-29  
**Compatibility:** pre-1.0; interfaces, adapters, and integration details may change incompatibly.

## Goal

v0.9 adds a second, agent-oriented use of the existing Hacocoon Environment lifecycle:

> A trusted client integration can bind each independent coding-agent session to its own isolated Hacocoon Environment, while the agent itself receives no Hacocoon or Incus control-plane authority.

The existing human/client workflow remains supported and unchanged:

```text
Human -> haco / haco-vscode -> Environment -> Incus
```

The new agent-host workflow is separate:

```text
VS Code Agents UI / another AHP client
                 |
       trusted client integration
                 |
        per-session broker
                 |
        +--------+--------+
        |                 |
  Environment A      Environment B
     Incus A            Incus B
        |                 |
   Agent Host A       Agent Host B
        |                 |
     Agent A             Agent B
```

Hacocoon remains a Secure Workspace Runtime. It does not become an AI orchestrator.

## Security boundary

The most important v0.9 rule is asymmetric authority:

```text
trusted host/control plane
  Hacocoon + Incus authority
              |
              | creates/binds
              v
+--------------------------------+
| isolated Environment           |
|                                |
| Agent Host + coding agent      |
| broad local workspace freedom  |
|                                |
+--------------------------------+
              X
              |
       no control-plane path
```

An agent Environment must not receive, merely for convenience:

- the `incus` Unix socket or equivalent Incus administrator authority;
- Hacocoon state files or a Hacocoon management/control socket;
- host-side Hacocoon credentials;
- broad GitHub, AWS, cloud, or host credentials;
- an expectation that the agent invokes `haco` to create, select, or delete its own sandbox.

The agent can be intentionally permissive **inside its Environment**. Authority outside that Environment remains controlled by the existing Hacocoon Policy/Capability boundary.

`haco` remains a human/operator interface. It is not the agent protocol.

## Session broker

v0.9 introduces an integration-layer broker outside Core.

Its conceptual input is:

```text
opaque external session identity
workspace path
access mode
```

Its output is a binding to one existing Hacocoon Environment:

```text
external session id
       |
       v
per-session binding
       |
       v
Environment
       |
Environment provider
       |
Incus by default
```

The broker deliberately reuses the existing `Environment`, `Workspace`, and `WorkspaceLease` lifecycle instead of introducing `Agent` as a Core concept.

### Binding properties

For the initial implementation:

1. an external session identity deterministically maps to one Environment name;
2. the raw external session identity is not used as an Incus instance name;
3. acquiring the exact same session/workspace/access-mode binding is idempotent;
4. attempting to reuse the same session identity for another Workspace or access mode fails closed;
5. releasing one session deletes only its bound Environment;
6. normal Workspace lease rules remain authoritative underneath the broker.

The deterministic name is an implementation detail, not a compatibility promise.

## Workspace and worktree behavior

Per-agent sandboxing does **not** mean multiple read/write Environments should mount the same host directory.

The existing v0.2 lease rule remains correct: conflicting read/write leases for the same canonical Workspace are rejected.

Parallel write-capable sessions should instead receive distinct workspaces, normally distinct Git worktrees:

```text
repository
  |
  +-- worktree/session-a -> Environment A -> Agent A
  |
  +-- worktree/session-b -> Environment B -> Agent B
```

Worktree creation remains outside Hacocoon Core. VS Code, an orchestrator, or another trusted integration may create/select the worktree and pass its path to Hacocoon.

This preserves two independent boundaries:

- Git worktrees provide code-change isolation between parallel tasks;
- Incus Environments provide OS/runtime isolation and the security boundary around the agent.

A worktree alone is not treated as a security sandbox.

## VS Code Agent Host / AHP placement

Current VS Code can run agent sessions in a standalone Agent Host and connect to remote Agent Hosts over the Agent Host Protocol (AHP). v0.9 uses that architecture as the preferred VS Code integration direction rather than making an AI process invoke the Hacocoon CLI.

The intended target is:

```text
VS Code Agents window
        |
      AHP/SSH
        |
trusted Hacocoon integration
        |
 session routing / allocation
        |
  +-----+------------------+
  |                        |
Incus A                  Incus B
  |                        |
code agent host A       code agent host B
  |                        |
Agent session A         Agent session B
```

The concrete AHP/VS Code adapter remains outside Core. AHP is still evolving, so its protocol/client version must be isolated and pinned at the adapter boundary rather than leaking AHP types into Hacocoon Core.

### Why hooks are not the sandbox transport

VS Code agent hooks can be useful as lifecycle signals where their semantics are suitable, but they are not the v0.9 execution boundary.

A lifecycle callback that runs after an agent session is already starting cannot, by itself, prove that all subsequent agent processes, tools, terminals, and filesystem operations have moved into another Incus Environment. Therefore:

- hooks may assist lifecycle observation or cleanup;
- hooks must not be treated as the mechanism that provides sandbox isolation;
- the execution host itself must be the isolated Environment, normally by running the Agent Host next to the Workspace inside that Environment.

## Top-level sessions and subagents

The initial v0.9 ownership unit is an **independently routable top-level agent session**.

If an agent harness creates internal subagents inside one Agent Host session, those subagents may share the parent's Environment unless the client/harness exposes them as separately routable sessions. v0.9 does not falsely claim one Incus instance for every hidden internal subagent.

If stronger subagent isolation is required later, it must be designed as an explicit protocol/lifecycle feature rather than inferred from chat UI concepts.

## Existing behavior remains

v0.9 does not replace these interfaces:

```text
haco create / exec / shell / delete
haco run
haco-vscode open / delete
```

They continue to use the existing Workspace/Environment model.

The per-agent broker is additive. A human can still create a long-lived Environment explicitly, and a generic external orchestrator can still use `haco run` when that is the appropriate integration.

## Failure and recovery rules

Per-agent allocation is control-plane state and must fail safely.

- If Environment creation fails, no successful binding is reported.
- If an existing deterministic Environment belongs to another Workspace/access mode, the broker refuses to rebind it.
- Existing Environment cleanup and `WorkspaceLeaseCleanupRequired` recovery semantics remain authoritative for partial runtime failures.
- A session release must not delete another session's Environment merely because client state is stale.
- Missing or malformed external session identities fail before Environment creation.
- A client disconnect alone must not silently grant the agent host authority or credentials it did not previously have.

Later AHP integration must preserve these rules across reconnect/replay behavior.

## v0.9 acceptance gate

The v0.9 gate is split between repository implementation and real-client/provider acceptance.

### Repository implementation gate

1. A per-session broker exists outside Core.
2. The broker reuses the existing Environment/WorkspaceLease lifecycle.
3. Distinct external session identities receive distinct Environment identities.
4. Exact repeated acquisition is idempotent.
5. Session rebinding to another Workspace/access mode fails closed.
6. Raw external session IDs are not used directly as runtime instance names.
7. Releasing one binding cannot select another binding by client-provided Environment name.
8. Existing `haco`, `haco run`, and `haco-vscode` behavior remains available.
9. Unit tests cover allocation, idempotence, rebinding rejection, lookup, release, access mode, path canonicalization, and malformed session IDs.
10. Build, vet, race, docs consistency, and existing tests remain green.

### Environment-dependent acceptance

The following requires a supported machine with real Incus and current VS Code Agent Host/AHP behavior and must be reported separately:

1. start two independent VS Code agent sessions;
2. allocate two distinct worktrees and two distinct Incus Environments;
3. run the Agent Host for each session inside its assigned Environment;
4. verify commands and edits from session A occur only in Environment/worktree A and likewise for B;
5. verify the agent cannot reach the Incus/Hacocoon control plane merely by being an agent;
6. verify disconnect/reconnect does not collapse two sessions into one Environment;
7. verify cleanup removes only the selected session's Environment.

Until this acceptance is run, repository code must not claim that end-to-end VS Code per-session routing has been proven on a real host.

## Non-goals

v0.9 does not make Hacocoon responsible for:

- model selection or model routing;
- prompt/task decomposition;
- retry/token/budget policy;
- AI chat UI;
- agent reasoning or tool-loop semantics;
- Git branch strategy;
- automatic merging or development approval;
- inventing a replacement for AHP;
- exposing Hacocoon/Incus management authority to the agent;
- one-Incus-per-hidden-subagent semantics that the client cannot actually route.

## One-sentence definition

> **v0.9 lets a trusted client integration give each independently routable coding-agent session its own Hacocoon Environment while keeping Hacocoon and Incus control authority outside the agent sandbox.**
