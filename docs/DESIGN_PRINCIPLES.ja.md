# Hacocoon 設計原則

日本語 | [English](DESIGN_PRINCIPLES.md)

この文書は製品が守る原則です。将来の機能や選択肢がすべて実装済みという意味ではありません。

## Incus を土台にする開発環境

Hacocoon は Incus に開発用の操作、データごとに異なる寿命、明示的な権限境界を加えます。Incus の既存機能を使い、Core を小さく保ちます。インターフェースは実際の責務分離やテストのために設けます。架空の将来バックエンドを理由に現在の実装を制約したり、復旧用の仕組みを増やしたりしません。

高速な作成、低い待機負荷、不変の Base、コピーオンライトによって、隔離環境を日常的に使いやすくします。ただし、物理的な共有や性能は実測して判断します。

## 信頼しない Environment 内での自由

コマンド、依存パッケージ、ビルドツール、コーディングエージェントは、Host の権限に対して信頼しません。一方、自分の Environment 内ではパッケージ導入、サービス起動、コンパイル、ファイル変更を行えます。バックエンドが境界を守れるなら Environment 内の root も許容します。設定した資源制限は適用します。現在公開している設定範囲は[資源制限](design/sandbox-resource-limits.ja.md)を参照してください。

書き込み可能な Workspace は作業データであり、エージェントから守られた保管庫ではありません。ファイルの変更・削除は可能です。必要に応じて読み取り専用、Git、明示的なスナップショット、レビューを使います。指定した Workspace を無関係な Host データへのアクセスへ広げません。

## 実行より長く残るデータ

Environment は使い捨てです。通常の削除でも Workspace／Git、保持する OCI データ、保存済みスナップショットは残します。未保存の実行状態を完全に復旧する必要はありません。再作成は現在の保持データ、スナップショット復元は保存時のデータを使います。詳細は[データの寿命](guides/data-lifetime.ja.md)と[スナップショット](design/environment-snapshots.md)に集約します。

使い捨ての実行環境でも、所有者の識別と削除完了の確認は必須です。停止中も利用権は保持します。後始末の結果が不明なら所有記録を残し、復旧が必要と報告します。

## 権限は境界の外に置く

Host の認証情報、HOME、SSH／クラウド設定、実行基盤の管理ソケット、保護された Hacocoon 状態、無関係なパスを Environment へ暗黙に公開しません。Windows ドライブやプロセス連携も、明示的に信頼した基盤だけに限定します。

```text
信頼しない Environment
  -> 対象を限定した要求
  -> Policy / Approval / Capability
  -> 許可された Host・外部サービス操作
```

承認を実際の対象、Environment の識別、関連する状態へ結び付けます。権限を使う直前に再確認し、古い承認、変更されたリポジトリ・接続先、権限の取り違えを拒否します。再利用可能な認証情報は信頼する側に置き、実行環境へコピーしません。

## 権限境界では安全側で拒否する

必要な Policy、承認、所有権、ネットワーク設定、資源制限を検証できない場合は操作を拒否します。便利機能だけが利用不能になることは許容できますが、安全性の検証失敗を暗黙の権限拡大へ変えてはいけません。後始末を試みたことを、削除完了とみなしません。

詳しい境界は[セキュリティ設計](security/security-architecture.md)、ライフサイクルの所有権を定めた理由は[ADR 0002](adr/0002-environment-lifecycle-ownership.md)に記載します。

## 実際の隔離保証を示す

現在の Incus システムコンテナは Host のカーネルを共有します。カーネル、Incus デーモン、Hacocoon の管理機構は信頼する基盤です。カーネルの脆弱性悪用、コンテナからの脱出、管理機構自体の侵害に対する防御を保証しません。

VM／microVM による隔離は将来の選択肢であり、現在選べる実装ではありません。バックエンドは保証できる範囲を示し、満たせない要求を拒否します。プラットフォームの差を理由に隔離や送信元偽装防止を省略しません。

## 契約と実装を分ける

Core はライフサイクル、Execution、Policy／Approval／Capability の意味を持ちます。Standard は Incus や実装済みの外向き通信プロキシなど、交換可能な既定実装を提供します。Plugin は任意の作業ツール連携を担当します。詳しい分類とパッケージ境界は[アダプター設計](design/plugin-architecture.md)に記載します。

外向き通信の権限は Core、HTTP／HTTPS の制御方式やネットワーク構成は実装側の責務です。Git・AWS 操作は、より狭い権限を専用 Capability で表します。

クライアントはエディター起動、秘密鍵、表示を担当します。オーケストレーターはタスク、モデル、予算を担当します。いずれも Core の必須依存にしません。Docker、nerdctl、Git、クラウドツールも、公式の構成例が利用しているだけでは必須になりません。
