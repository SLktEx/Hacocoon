# Hacocoon v0.6 - Local Web and Interaction Specification

Status: Draft for implementation  
Requires: v0.5 Local GUI and IDE acceptance gate

## 1. One-sentence definition

Hacocoon v0.6 adds a small local browser-facing interaction surface for Session control, approvals, notifications and an OSS Web IDE, while keeping the editor and authorization authority outside the UI.

## 2. Product boundary

Hacocoon Web UI is a **control/interaction client**, not a new IDE or chat runtime.

```text
Browser
  |
  +-> Hacocoon Web UI
  |     sessions/status
  |     approvals
  |     notifications
  |     interaction events
  |
  +-> code-server (Web IDE provider)
          |
          v
      Session /workspace
```

Security Framework remains authoritative for Capability decisions. Web UI may approve/deny a pending request only through the same Manager API/identity rules as CLI.

## 3. Notification policy

When Web UI exists:

```text
standard: Hacocoon Web UI + Browser Notification
optional: VS Code/code-server extension notification adapters
```

IDE extensions are never required for correctness and never become authorization authority.

## 4. Interaction API

Define a client-neutral interaction contract for:

- pending approval events;
- Session lifecycle status;
- agent waiting/completed/failed state;
- storage/doctor warnings;
- notification acknowledgement;
- links/endpoints for local Session access.

The API exposes normalized state/events, not raw provider secrets.

Possible event envelope:

```yaml
id: evt_...
type: approval.requested
session_id: sess_123
correlation_id: req_...
summary: "Push to protected branch main"
severity: action-required
created_at: ...
```

## 5. Local Web security

Default bind is localhost only.

```text
Browser -> 127.0.0.1 Hacocoon local web service -> Manager
```

Remote/Internet authentication is not a v0.6 requirement and must not be accidentally enabled. Remote TLS/OIDC/reverse-proxy/Gateway integration is v0.7.

Use CSRF/session protections appropriate to the chosen local web model; never trust arbitrary cross-origin requests solely because the service listens on localhost.

## 6. Approval UI

Required behavior:

```text
Security Framework -> pending request
          |
          v
Interaction API -> Web UI / Browser Notification
          |
          v
human opens exact request
          |
      approve / deny
          |
          v
Security Framework state transition
```

The UI displays the exact normalized resource/conditions that will be bound to approval. Changing source SHA/ref/resource after approval invalidates the old Grant as in v0.3.

## 7. Web IDE

Initial OSS provider: code-server is acceptable. The provider runs **inside Session** and opens the same `/workspace`.

Local flow:

```text
Browser
  -> localhost Hacocoon route/forward
  -> Session-private code-server port
  -> /workspace
```

Requirements:
- private Session bind;
- no direct LAN/public exposure by default;
- lifecycle tied to Session/access lease;
- WebSocket support;
- no Manager parent credentials in code-server environment;
- provider replaceable (e.g. future OpenVSCode Server).

## 8. Local previews

v0.2 localhost preview remains valid. v0.6 Web UI may list/open those mappings but does not automatically publish them.

A Session starting `:3000` is not permission to create a LAN/Internet route.

## 9. UX

```bash
haco web-ui
haco web <session>
haco approvals
haco approve <request>
haco deny <request>
haco interaction events
haco open <session> --ide web
```

Exact CLI names may evolve; semantics are normative.

## 10. State

Add provider-neutral records such as:

```text
interaction_events
notification_state
web_ide_instances
local_web_routes
```

Do not duplicate authoritative approval/grant state into the UI database.

## 11. Implementation order

1. Interaction API/event model;
2. localhost-only web service with a local origin/session token or equivalent CSRF-safe mechanism; this is not remote user authentication;
3. Session/status pages;
4. approval list/detail/action;
5. Browser Notification permission + event path;
6. code-server provider and private local route;
7. WebSocket smoke tests;
8. local preview listing/opening;
9. optional VS Code/code-server notification adapter;
10. restart/cleanup/security tests.

## 12. Security tests

| Scenario | Expected |
|---|---|
| arbitrary LAN host reaches local Web UI | impossible/default denied |
| cross-origin page submits approval | denied by web security controls |
| UI changes request fields before approve | Manager binds original normalized request; altered request not authorized |
| Web IDE reads Manager AWS/Git credential | impossible |
| Session listener appears in Web UI | may be listed only if Hacocoon knows mapping; never auto-public |
| Web UI unavailable | CLI approval still works |
| VS Code extension absent | Browser notification path remains usable |
| Session deleted | local Web IDE/routes cleaned |

## 13. Acceptance gate

- local Web UI shows Sessions and pending approvals;
- human can inspect and approve/deny the exact v0.3 request;
- Browser Notification can surface action-required events when permission is granted;
- authorization remains in Security Framework;
- code-server opens the Session workspace through a localhost/private route;
- Web UI/code-server receive no parent provider credentials;
- local mode requires no EC2/Gateway/OIDC setup;
- prior CLI/VS Code/GUI workflows remain functional without Web UI running.
