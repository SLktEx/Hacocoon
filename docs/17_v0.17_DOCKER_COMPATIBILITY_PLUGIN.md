# v0.17 — Docker Compatibility Plugin

Status: **foundation implemented; complete plugin integration remains follow-up.**

v0.17 defines Docker compatibility as an optional plugin/integration feature. Hacocoon Core continues to model Environments and execution; it does not make Docker Engine a Core runtime.

## Runtime direction

The standard container runtime inside Hacocoon Environments is:

```text
containerd + nerdctl
```

Docker compatibility is additive:

```text
normal path      -> nerdctl -> containerd
compatibility    -> genuine Docker CLI -> optional/on-demand dockerd -> existing containerd where supported
```

The goal is to support tools that insist on Docker CLI/Engine APIs without forcing every Environment to run a permanent second daemon or maintain a duplicate image store.

## Plugin boundary

- Docker/nerdctl-specific orchestration belongs outside Core behind the plugin/adapter boundary.
- Genuine Docker CLI may be installed for compatibility.
- `dockerd` must not become an always-on Hacocoon requirement.
- Engine startup should be explicit/on-demand for packages that actually require the Docker Engine API.
- Hacocoon should avoid duplicating OCI image layers merely to satisfy Docker compatibility.
- Docker compatibility must not grant coding agents Hacocoon/Incus host control authority.

## Current repository reality

The repository contains the initial Docker compatibility design and systemd packaging/socket-service foundation. That is not yet sufficient to call the full v0.17 plugin complete.

Completion requires the plugin boundary, lifecycle wiring, runtime validation, and supported-host tests to match this contract.

## Non-goals

- replacing containerd/nerdctl as the standard runtime;
- making Docker Engine mandatory;
- running dockerd permanently when no workload needs it;
- duplicating image stores without a demonstrated requirement;
- placing Docker-specific concepts into Hacocoon Core.
