# OCI Seedの理由と置き換わった方針

[English](oci-seed-retrospective.md) | 日本語

状態: **過去の（過去の設計）**。2026-08-31の「OCI application containerをIncus直下の
別instanceにする」提案は、現在の既定動作でも移行完了事項でもありません。
現行B4は[永続OCI Store](persistent-oci-store.md)と
[Host領域コピーの境界](../adr/0031-host-oci-area-copy.md)を使います。
残る[Seed実装](oci-seed-and-cow.ja.md)は旧方式の任意連携です。

SeedはEnvごとに独立したcontainerdを持つ構成で、OCIデータの重複を減らすための仕組みでした。
書込み可能な`/var/lib/containerd`の共有は隔離と独立削除を壊します。
代わりに資格情報を持たないオフラインビルダーが固定イメージを不変rootfsへ取り込み、
Incus/Btrfsのcloneで各Env専用の書込み領域を作りました。
ビルド・公開、固定・削除方針、回収、復旧、GCはその方式を保護していました。

過去のnative OCI提案は、Incusのライフサイクルと内部実行基盤のストレージをつなぐ処理を減らす意図でした。
一つのIncus daemonによる別々の実行対象管理、コントローラー経由の操作、
操作中だけのregistry資格情報を想定していました。
この提案だけでは機能や非公開 ECR認証の実装・検証は成立しておらず、
現行動作として説明してはいけません。

次の制約は提案の採否によらず維持します。

- ポリシー・再現性に必要な場面では、変化する入力名を不変IDへ解決する。
- 独立した稼働実行対象間で、一つの書込み可能実行基盤 rootを共有しない。
- registry資格情報、helper出力、Host セッションをイメージ・スナップショットへ入れない。
- CoreでIncusのsubvolumeを直接操作せず、COWとイメージ・ボリュームの寿命をIncusへ委譲する。
- 所有、alias、利用者、後始末完了が不明ならresourceを保持する。
- pull・ビルド・コピーの途中データを利用可能として公開しない。

将来native OCIを導入するなら、ライフサイクル・ネットワーク・公開接続、非公開 registryの資格情報保持、
物理ストレージ、失敗・再起動を個別に検証する必要があります。
現在のStore手順の前提ではありません。廃止した移行手順の全文はGit履歴へ残し、
この記録は判断理由を保持するだけで移行を予定しません。
