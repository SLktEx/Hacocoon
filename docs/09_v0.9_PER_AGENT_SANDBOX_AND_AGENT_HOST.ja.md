# v0.9 AgentごとのSandboxとAgent Host連携

**状態:** 2026-08-29 に実装基盤を導入  
**互換性:** pre-1.0。インターフェース、Adapter、連携方式は互換性なく変更される可能性があります。

## 目的

v0.9では、これまでのHacocoon Environmentをそのまま使いながら、AI Agent向けに次の使い方を追加します。

> 信頼されたClient連携層が、独立したAgent Sessionごとに専用のHacocoon Environmentを割り当てる。Agent自身にはHacocoonやIncusの管理権限を渡さない。

人間が使う従来経路はそのまま残します。

```text
Human -> haco / haco-vscode -> Environment -> Incus
```

Agent向けには別の経路を追加します。

```text
VS Code Agents UI / 別のAHP Client
                 |
          信頼された連携層
                 |
        SessionごとのBroker
                 |
        +--------+--------+
        |                 |
  Environment A      Environment B
     Incus A            Incus B
        |                 |
   Agent Host A       Agent Host B
        |                 |
     Agent A             Agent B
```

Hacocoonは引き続きSecure Workspace Runtimeであり、AI Orchestratorそのものにはなりません。

## 最重要のセキュリティ境界

v0.9では、管理側とAgent側の権限を明確に非対称にします。

```text
信頼されたHost / Control Plane
  Hacocoon + Incus管理権限
              |
              | 作成・割当
              v
+--------------------------------+
| 隔離されたEnvironment         |
|                                |
| Agent Host + Coding Agent      |
| 箱の中では広い自由を許容      |
|                                |
+--------------------------------+
              X
              |
       管理面への経路なし
```

Agent Environmentには、便利だからという理由で次のものを渡しません。

- `incus` Unix socketなどのIncus管理権限
- Hacocoonのstate fileや管理socket/API
- Host側のHacocoon認証情報
- 広いGitHub/AWS/Cloud/Host認証情報
- 自分のSandboxを作成・選択・削除するためにAgent自身が`haco`を実行する仕組み

AgentはEnvironmentの中ではかなり自由に動けます。一方、Environmentの外側の権限は既存のPolicy/Capability境界で管理します。

`haco`は人間・運用者向けのインターフェースとして残し、Agent Protocolにはしません。

## Session Broker

v0.9ではCoreの外側に、Agent SessionをEnvironmentへ割り当てるBrokerを追加します。

概念上の入力は次です。

```text
外部Clientが持つopaqueなSession ID
Workspace path
Access mode
```

これを既存のHacocoon Environmentへ割り当てます。

```text
external session id
       |
       v
per-session binding
       |
       v
Environment
       |
Environment provider
       |
標準ではIncus
```

`Agent`や`VS Code Session`をCoreの概念として増やすのではなく、既存の`Workspace`、`WorkspaceLease`、`Environment`をそのまま利用します。

初期実装では次を保証します。

1. 外部Session IDから1つのEnvironment名を決定する。
2. 生のSession IDをIncus instance名として使わない。
3. 同じSession/Workspace/Access modeの再取得はidempotentに扱う。
4. 同じSession IDを別Workspaceや別Access modeへ付け替えようとした場合はfail closedする。
5. SessionをReleaseしても、そのSessionに対応するEnvironmentだけを削除する。
6. 下位では従来のWorkspaceLeaseルールをそのまま適用する。

Environment名の具体的な生成方法は実装詳細であり、互換性保証ではありません。

## WorkspaceとGit worktree

AgentごとにIncusを分けても、複数のread/write Agentへ同じHost directoryを直接mountしてはいけません。

v0.2からあるWorkspaceLeaseの競合防止を維持します。同じcanonical Workspaceへの複数RW leaseは拒否します。

並列で変更するAgentには、通常は別Git worktreeを渡します。

```text
repository
  |
  +-- worktree/session-a -> Environment A -> Agent A
  |
  +-- worktree/session-b -> Environment B -> Agent B
```

worktreeの作成はCoreの責務にはしません。VS Code、外部Orchestrator、または信頼されたClient Adapterがworktreeを用意し、そのpathをHacocoonへ渡します。

この結果、次の2種類の隔離を分離できます。

- Git worktree: 並列タスク同士のコード変更を分ける
- Incus Environment: OS/runtimeとAgentのセキュリティ境界を分ける

worktree単体はセキュリティSandboxとはみなしません。

## VS Code Agent Host / AHPとの関係

現在のVS CodeはAgent Sessionを専用のAgent Hostで動かし、remote Agent HostへAgent Host Protocol (AHP)で接続できます。v0.9ではこの仕組みをVS Code連携の本命とし、Agent process自身にHacocoon CLIを実行させる方式にはしません。

目標構成は次です。

```text
VS Code Agents window
        |
      AHP/SSH
        |
信頼されたHacocoon連携層
        |
 Session routing / allocation
        |
  +-----+------------------+
  |                        |
Incus A                  Incus B
  |                        |
code agent host A       code agent host B
  |                        |
Agent session A         Agent session B
```

具体的なVS Code/AHP AdapterはCoreの外側に置きます。AHPは現在も発展中なので、AHP固有の型やバージョン依存をCoreへ漏らさず、Adapter境界で固定・吸収します。

### HooksだけをSandbox境界にはしない

VS Code Agent HooksはSession lifecycleの通知などには使えますが、v0.9のSandbox transportにはしません。

Agent Sessionがすでに開始される途中で呼ばれるcallbackだけでは、その後のAgent process、tool、terminal、filesystem operationがすべて別Incusへ移動したことを保証できないためです。

そのため、

- Hooksはlifecycle観測やcleanupの補助には使える。
- Hooks自体をSandbox隔離の根拠にはしない。
- 実際のExecution HostそのものをEnvironment内に置く。VS CodeではAgent HostをWorkspaceの近く、つまり対象Incus内で動かす方式を基本とする。

という境界にします。

## Top-level SessionとSubagent

v0.9初期版で1 Environmentを割り当てる単位は、**独立してroutingできるtop-level Agent Session**です。

Agent Harnessの内部でSubagentが作られ、そのSubagentが独立したremote sessionとして外部へ公開されていない場合、そのSubagentは親Sessionと同じEnvironmentを共有する可能性があります。

したがって初期v0.9では「内部Subagentも必ず1体1Incus」とは主張しません。必要になった場合は、Client/Harness側が独立routingできる明示的なlifecycleとして設計します。

## 既存機能は残す

v0.9でも次の既存経路は残します。

```text
haco create / exec / shell / delete
haco run
haco-vscode open / delete
```

これらは引き続き既存のWorkspace/Environmentモデルを使います。

Per-Agent Brokerは追加機能です。人間が長寿命Environmentを明示的に作る使い方も、外部Orchestratorが`haco run`を呼ぶ既存方式も削除しません。

## Failure / Recovery

Agent割当はControl Planeの処理として安全側に倒します。

- Environment作成に失敗した場合、成功したBindingとして返さない。
- deterministicに選ばれたEnvironmentが別Workspace/access modeに属していれば、付け替えず拒否する。
- Runtimeのpartial failureには既存のEnvironment cleanupと`WorkspaceLeaseCleanupRequired`の考え方を使う。
- Release時にClientからEnvironment名を自由入力させて別SessionのEnvironmentを削除する設計にしない。
- 空・不正なSession IDはEnvironment作成前に拒否する。
- Clientが切断しただけでAgentへ追加のHost権限やCredentialを渡さない。

将来のAHP reconnect/replay連携でもこのルールを維持します。

## v0.9 Acceptance Gate

### Repository内で確認するもの

1. Per-session BrokerをCoreの外側に実装する。
2. 既存のEnvironment/WorkspaceLease lifecycleを再利用する。
3. 別Session IDが別Environment identityになる。
4. 同一BindingのAcquireがidempotentになる。
5. 同一Sessionの別Workspace/access modeへのrebindをfail closedする。
6. 生Session IDをruntime instance名に使わない。
7. Release対象をClient指定のEnvironment名ではなくSession bindingから決める。
8. 既存の`haco`、`haco run`、`haco-vscode`を残す。
9. allocation、idempotence、rebind rejection、lookup、release、access mode、path canonicalization、不正Session IDをunit testする。
10. build、vet、race、docs consistency、既存testをgreenにする。

### 実機で別途確認するもの

実際のIncusと最新VS Code Agent Host/AHPが使えるHostで、次を別途Acceptanceします。

1. 独立したVS Code Agent Sessionを2つ開始する。
2. 2つのworktreeと2つのIncus Environmentが作られる。
3. 各Environment内で対応するAgent Hostを動かす。
4. Session Aのcommand/editがAだけ、Session BがBだけで実行されることを確認する。
5. AgentがAgentであるだけではIncus/Hacocoon Control Planeへ到達できないことを確認する。
6. disconnect/reconnectしても2 Sessionが1 Environmentへ混ざらないことを確認する。
7. cleanupが指定SessionのEnvironmentだけを削除することを確認する。

この実機Acceptanceが終わるまでは、VS CodeからIncusまでのend-to-end routingが実証済みとは記載しません。

## Non-goals

v0.9でもHacocoonは次を所有しません。

- model selection / model routing
- prompt/task decomposition
- retry/token/budget policy
- AI chat UI
- agent reasoning / tool loop
- Git branch strategy
- 自動mergeや開発レビュー
- AHPの独自置換Protocol
- AgentへのHacocoon/Incus管理権限の公開
- Client側がroutingできないhidden subagentまで1 Incusにするという架空の保証

## 一文で言うと

> **v0.9は、独立してroutingできるCoding Agent Sessionごとに専用Hacocoon Environmentを割り当てつつ、HacocoonとIncusの管理権限をAgentの外側に置き続けるためのバージョンです。**
