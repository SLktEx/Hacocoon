# v0.11 Sandbox Resource Limits

**Status:** roadmap / design contract  
**Compatibility:** pre-1.0。interface、default、provider mapping は互換性なく変更される可能性があります。  
**Implementation:** 未実装。

## 目的

v0.11 では Hacocoon Environment に明示的な resource budget を追加します。

coding agent や developer tool は Environment 内では広く自由に動けますが、CPU、memory、process 数、root filesystem 容量は host/operator が決めた上限の中でのみ消費できます。

```text
VS Code / coding agent / tool
            |
            v
      Environment
   sandbox 内では自由
 resource budget の範囲内
            |
     ---- boundary ----
            |
        Hacocoon
  Policy / Capability / Audit
            |
   GitHub / AWS / Host
```

Resource limit は Capability ではありません。

```text
Capability
  -> Environment の外へどの authority を使えるか

Resource Budget
  -> Environment の中でどれだけ resource を使えるか
```

たとえば:

```text
Capability:
  「この Environment は Hacocoon 経由で GitHub push を要求できるか」

Resource Budget:
  「この Environment は CPU/RAM/PID/root disk をどこまで使えるか」
```

## なぜ Hacocoon に必要か

Hacocoon は coding agent を隔離された Environment 内では permissive に動かす設計です。

ただし isolation があっても resource exhaustion までは防げません。

例:

- runaway build/test が CPU を使い切る;
- fork storm で PID を枯渇させる;
- memory pressure で host 全体を swap/OOM に追い込む;
- package cache/build output/log が root filesystem を埋める;
- parallel agent Environment が workstation 全体を圧迫する。

そのため trusted host が untrusted Environment の resource 消費上限を保持します。

## 最初の scope

最初の v0.11 slice では次を対象にします。

- CPU;
- memory;
- process / PID count;
- provider が安全に enforce できる場合の Environment root-storage size。

概念上の入力:

```text
EnvironmentSpec
  Name
  Workspace
  AccessMode
  ResourceBudget
```

利用イメージ:

```bash
haco create \
  --cpu 4 \
  --memory 8GiB \
  --pids 1024 \
  --root-size 40GiB \
  --workspace . dev
```

flag 名や configuration schema は pre-1.0 であり、この document では固定しません。

## Resource Budget model

Hacocoon は provider-neutral な resource concept を公開し、Incus native key は adapter の内部に閉じ込めます。

概念例:

```go
type ResourceBudget struct {
    CPU      CPUResourceLimit
    Memory   ByteLimit
    PIDs     ProcessLimit
    RootDisk ByteLimit
}
```

これは必須 Go API ではなく、domain boundary の説明です。

Core/public architecture に `limits.cpu` のような Incus 固有名を持ち込みません。

## Default と precedence

resource limit は「指定し忘れた結果たまたま unlimited」にならないよう deterministic に扱います。

概念上の優先順位:

```text
CLI override
    > project configuration
    > user/global default
    > Hacocoon default budget
```

未指定値には一つの明示的な意味を持たせます。Provider 側の暗黙 default に security-relevant な判断を任せません。

pre-1.0 の移行中に compatibility のため explicit `unlimited` を許すことはできますが、「未指定」と「unlimited」を暗黙に同一視しません。

## Provider boundary

resource enforcement は Environment provider adapter が担当します。

```text
Workspace
   |
EnvironmentSpec + ResourceBudget
   |
Environment provider
   +-- runtime.incus
   +-- runtime.ec2 (experimental)
```

provider はどの resource dimension を enforce できるか表現します。

```text
ProviderResourceCapabilities
  cpu: supported
  memory: supported
  pids: supported
  root_disk: supported
```

user が明示的に request した limit を provider が enforce できない場合、silent ignore せず fail closed します。

## Incus mapping

default Incus provider では provider-neutral limit を Incus の native configuration に adapter 内部で mapping できます。

対象例:

```text
CPU quota / CPU count
memory limit
process limit
root disk size
```

具体的な Incus command/key は adapter detail であり、public contract ではありません。

resource setting は agent/client が Environment に access できる前に適用されなければなりません。

一瞬 unlimited で起動してから後付けで limit を掛ける create flow は避けます。

推奨 flow:

```text
resolve Workspace
  -> acquire WorkspaceLease
  -> validate ResourceBudget
  -> create stopped provider Environment
  -> apply resource limits
  -> attach Workspace
  -> start Environment
  -> verify requested limits where practical
  -> persist Environment metadata
```

limit の適用に失敗した場合は既存の cleanup/recovery semantics に従い、「制限付き Environment 作成成功」とは扱いません。

## Persistence

Environment 作成時に確定した effective ResourceBudget を persist します。

default を後で変更しても既存 Environment の budget は勝手に変わりません。

```text
Day 1
  default memory = 8 GiB
  Environment A create

Day 2
  default memory = 12 GiB
  Environment B create

A = 8 GiB のまま
B = 12 GiB
```

persist された resource metadata は diagnostics、reconciliation、future recovery にも利用できます。

## Runtime mutation

最初の v0.11 では creation-time budget を優先し、running Environment の任意 live resize は scope 外とします。

CPU/memory の live update は provider ごとの semantics と failure mode があるためです。

将来 update command を追加する場合は ownership、persistence、rollback、provider semantics を先に明確化します。

## Workspace storage との区別

`/workspace` は host-owned Workspace の mount であり、Environment root filesystem とは別物です。

```text
Host Workspace
    |
    +-- /workspace

Environment root filesystem
    |
    +-- OS
    +-- packages
    +-- caches
    +-- logs
```

`--root-size` は arbitrary host Workspace の容量 quota を意味しません。

Workspace growth は別の storage feature が明示的に管理しない限り、host filesystem/worktree 側の責任です。

## Parallel Agent

v0.10 の per-agent Environment と v0.11 はそのまま合成できます。

```text
Agent session A -> Environment A -> ResourceBudget A
Agent session B -> Environment B -> ResourceBudget B
Agent session C -> Environment C -> ResourceBudget C
```

per-Environment limit は一つの agent の暴走を抑えますが、host 全体の aggregate capacity scheduling までは扱いません。

将来 admission control を追加し、requested budget の合計が operator-defined host allocation を超えた場合に create を拒否することはできますが、最初の v0.11 scope 外です。

## Resource exhaustion

resource budget を超えることは sandbox 内の expected behavior です。

例:

- memory limit で allocation が失敗する;
- PID limit で process creation が失敗する;
- root disk full で write が失敗する;
- CPU work が throttle される。

Hacocoon は configured limit を status/diagnostic で説明できるようにしますが、kernel/provider level のすべての resource failure の原因 process を必ず特定する責任までは持ちません。

## Status / diagnostics

status/inspection path から effective budget を確認できるようにします。

概念例:

```text
Name: dev
State: running
Workspace: /home/user/src/project
Access: rw
Provider: runtime.incus
Resources:
  CPU: 4
  Memory: 8 GiB
  PIDs: 1024
  Root disk: 40 GiB
```

machine-readable output も Incus native key ではなく Hacocoon concept を返します。

## Capability との関係

CPU/memory/PID/root-size の通常 selection を v0.4 Capability service に流しません。

```text
Environment configuration
  -> sandbox の形と resource ceiling

Capability policy
  -> sandbox boundary を越える privileged operation
```

将来「caller がどの size を request してよいか」を policy で制限することはできますが、それは runtime resource model とは別の admission policy です。

## Base との関係

v0.11 は v0.9 Base と合成します。

```text
Base revision
      |
      v
Environment + ResourceBudget
```

Base は guest filesystem/runtime contents を決めますが、image metadata から host-selected resource limit を引き上げたり無効化したりできません。

Custom Base は引き続き untrusted input です。

## Agent Host との関係

v0.10 broker は ResourceBudget を指定して Environment を request できます。

ただし Environment 内の coding agent には、自分の host-enforced limit を Hacocoon/Incus control-plane 経由で引き上げる authority を渡しません。

## Failure / recovery

Resource configuration も通常の Environment create recovery の一部です。

対象 failure:

- invalid resource value;
- unsupported provider dimension;
- provider が limit を拒否;
- resource config 成功後に Workspace attach が失敗;
- start failure;
- Environment start 後の persistence failure;
- provider create と state commit の間で process crash。

requested limit が正しく適用されたと証明できない場合、successful constrained creation として返しません。

cleanup は potentially-running Environment の ownership metadata を黙って消すより、識別可能な stopped resource を残して recovery を要求する方を優先します。

## Validation

resource value は provider command 実行前に Hacocoon が parse/validate します。

最低限:

- explicit semantics のない zero/negative value を reject;
- integer overflow を reject;
- ambiguous unit format を reject;
- trailing garbage を reject;
- practical upper bound が必要なら設定;
- operator intent を effective persisted value に正確に残す。

provider command construction は shell interpolation ではなく argv execution を継続します。

## Acceptance gate

最初の v0.11 implementation acceptance:

- provider-neutral ResourceBudget representation;
- Incus CPU limit;
- Incus memory limit;
- Incus PID/process limit;
- selected Incus storage path が安全に enforce 可能なら root-storage limit、そうでなければ explicit unsupported;
- deterministic default/override resolution;
- effective creation-time budget persistence;
- status / machine-readable inspection;
- requested-but-unsupported limit は fail closed;
- agent/client access 前に resource setting 完了;
- partial create failure は既存 cleanup/recovery semantics に従う;
- WorkspaceLease safety unchanged;
- v0.9 Base が resource limit を引き上げられない;
- v0.10 agent binding が agent に resource-control authority を渡さない;
- parsing / precedence / persistence / unsupported provider / failure cleanup の unit test;
- race / vet / build / docs consistency / maintained host-independent integration test green。

Real Incus acceptance では:

- CPU restriction;
- memory restriction;
- PID restriction;
- supported storage path で root-size restriction;
- normal Environment access から limit を引き上げられないこと;
- delete/recreate 後も Workspace/resource ownership semantics が保たれること

を確認します。

## Non-goals

最初の v0.11 scope 外:

- AI scheduler / model budget;
- task/DAG orchestration;
- aggregate workstation/cluster scheduling;
- automatic overcommit;
- live autoscaling;
- Kubernetes-style request/limit scheduling semantics;
- host Workspace quota management;
- arbitrary Incus configuration passthrough;
- coding agent 自身が limit を上げる capability;
- Base image metadata による resource authority change。

## Future follow-ons

creation-time budget が安定した後の候補:

- aggregate host admission control;
- `small` / `default` / `large` resource profile;
- per-project default budget;
- explicit live resize;
- resource usage observation / warning;
- idle Environment stop/suspend policy;
- stale Environment cleanup/reconciliation;
- resource metadata を保持する checkpoint/restore。

これらは v0.11 acceptance gate には自動的に含めません。

## 一文でいうと

> **v0.11 は各 Hacocoon Environment に host-enforced resource budget を持たせ、developer tool や coding agent を sandbox 内では自由に動かしつつ、共有 host resource を無制限に消費できないようにする。**
