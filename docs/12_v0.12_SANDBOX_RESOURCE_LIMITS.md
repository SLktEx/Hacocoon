# v0.12 Sandbox Resource Limits

**Status:** first implementation slice implemented  
**Compatibility:** pre-1.0; interfaces, defaults, and provider mappings may change incompatibly.  
**Implementation:** provider-neutral budgets, strict CLI parsing, Incus creation-time enforcement/verification, persistence/status, and fail-closed unsupported-provider behavior are implemented. Real supported-Incus enforcement acceptance remains pending.

## Goal

v0.12 adds explicit resource budgets for Hacocoon Environments so permissive coding agents and developer tools can consume CPU, memory, processes, and local root-storage only within operator-selected bounds.

```text
VS Code / coding agent / tool
            |
            v
      Environment
  broad local freedom
  within resource budget
            |
     ---- boundary ----
            |
        Hacocoon
  Policy / Capability / Audit
            |
   GitHub / AWS / Host
```

Resource limits are not capabilities. A capability controls authority across a trust boundary; a ResourceBudget limits consumption inside an Environment.

## Implemented first slice

The current CLI supports creation-time limits on both persistent and ephemeral Environments:

```bash
haco create \
  --cpu 4 \
  --memory 8GiB \
  --pids 1024 \
  --root-size 40GiB \
  --workspace . dev

haco run --cpu 2 --memory 4GiB --workspace . -- go test ./...
```

Each dimension accepts a finite value or `unlimited`. Byte-sized values use explicit binary-unit strings such as `512MiB`, `8GiB`, and `40GiB`; ambiguous forms such as `8G`, decimal fractions, signs, trailing garbage, zero finite values, overflow, and values beyond Hacocoon's practical bounds are rejected before provider execution.

The current provider-neutral model records:

```text
ResourceBudget
  CPU
  MemoryBytes
  PIDs
  RootBytes
```

Each resource limit is represented as finite or unlimited. An omitted dimension is resolved by Hacocoon to an explicit effective `unlimited` value rather than being left to an unspecified provider default. The effective ResourceBudget is persisted on the Environment and exposed by `haco status` / `haco status --json`.

## Incus enforcement

For the default Incus provider, finite limits are adapter-owned implementation details mapped internally to Incus settings. The current implementation applies and reads back the requested values before the Environment is started.

Conceptually:

```text
resolve Workspace
  -> acquire WorkspaceLease
  -> validate ResourceBudget
  -> resolve/pin v0.11 Base revision
  -> create stopped Incus Environment
  -> apply CPU/memory/PID/root limits
  -> read back and verify requested limits
  -> attach Workspace
  -> start Environment
  -> persist Environment metadata
```

A failed apply or read-back mismatch does not become successful constrained creation. The Environment follows the existing cleanup/recovery discipline, and Hacocoon must not knowingly expose a briefly-unlimited running Environment for a request that required finite limits.

The concrete current Incus mapping uses adapter-native CPU, memory, process-count, and root-device size settings. Those Incus keys are not part of the Core/public architecture contract.

Real supported-Incus acceptance must still verify that CPU, memory, PID, and root-storage restrictions actually constrain workloads and cannot be raised through ordinary Environment access.

## Provider boundary and fail-closed behavior

Resource enforcement belongs to the Environment provider adapter.

```text
Workspace
   |
EnvironmentSpec + ResourceBudget
   |
Environment provider
   +-- runtime.incus
   +-- runtime.ec2 (experimental)
```

If a finite limit is requested and the selected provider cannot prove that it enforces that dimension, creation fails closed rather than silently ignoring the request.

The current experimental EC2 provider does not yet claim equivalent finite ResourceBudget enforcement. Hacocoon therefore rejects finite budgets on that path before calling the wrapped provider, which keeps the request from creating AWS resources and only afterward discovering that the requested ceiling was not enforced.

EC2 remains experimental and disabled by default independently of v0.12.

## Defaults and precedence

The first implementation resolves direct CLI input and omission deterministically. Omission has one explicit meaning: `unlimited` for that dimension in the persisted effective budget.

Future project/user/global default layers may add precedence such as:

```text
CLI override
    > project configuration
    > user/global default
    > Hacocoon default budget
```

Those additional configuration layers are not required by the first implemented slice. They must not reintroduce ambiguous provider-owned defaults when added.

## Persistence and identity

An Environment records the effective resource budget selected at creation time. Changing a later default must not silently rewrite the budget recorded for an existing Environment.

Provider-returned creation metadata is checked against the requested effective finite budget. A provider cannot silently acknowledge one budget while materializing another and still be reported as successful.

## Runtime mutation

The first v0.12 slice supports creation-time budgets, not arbitrary live mutation.

Changing CPU or memory limits on a running Environment can have provider-specific semantics and failure modes. Live resizing is intentionally deferred.

## Workspace storage is separate

The mounted Workspace is host-owned state and is not the same thing as the Environment root filesystem.

```text
Host Workspace
    |
    +-- mounted at /workspace

Environment root filesystem
    |
    +-- OS
    +-- packages
    +-- caches
    +-- logs
```

`--root-size` limits the Environment root filesystem where the provider can enforce it. It is not a promise to quota an arbitrary host Workspace mount.

## Parallel-agent safety

v0.9 can allocate one Environment per independently routable coding-agent session, and v0.10 prepares that Environment for the VS Code Agent Host path. v0.12 composes with those boundaries:

```text
Agent session A -> Environment A -> ResourceBudget A
Agent session B -> Environment B -> ResourceBudget B
Agent session C -> Environment C -> ResourceBudget C
```

Per-Environment limits reduce the damage from one runaway sandbox, but they do not solve aggregate host capacity or scheduling. Aggregate admission control remains future work.

## Policy relationship

Resource limits are not Hacocoon `CapabilityRequest`s.

```text
Environment configuration
  -> defines sandbox shape and resource ceiling

Capability policy
  -> mediates privileged operations across the sandbox boundary
```

The coding agent inside an Environment must not receive Hacocoon/Incus control-plane authority that lets it raise its own host-enforced ceiling.

## Base-image relationship

v0.12 composes with v0.11 Bases.

```text
immutable Base revision
          |
          v
Environment + ResourceBudget
```

A custom Base controls guest filesystem/runtime contents. It does not raise, disable, or rewrite host-selected resource limits through image metadata.

## Failure and recovery semantics

Resource configuration participates in normal Environment creation recovery.

Relevant failures include invalid input, unsupported provider dimensions, provider rejection, apply/read-back mismatch, Workspace attach/start failure after resource configuration, persistence failure, and crashes between provider creation and state commit.

When Hacocoon cannot prove that a requested finite budget was applied correctly, it must not report successful constrained creation.

Cleanup should prefer a clearly identifiable recovery-required resource over silently forgetting ownership of a potentially running Environment.

## Validation

The implemented parser and Core validation reject at least:

- zero finite limits;
- negative or signed values;
- integer overflow;
- ambiguous byte units and trailing garbage;
- decimal/fractional values in the current integer-only format;
- values above practical Hacocoon bounds;
- malformed finite/unlimited mode/value combinations.

Provider command construction remains argv-based rather than shell-interpolated.

## Repository acceptance

The first implemented v0.12 slice is expected to keep these repository checks green:

- provider-neutral ResourceBudget representation;
- CPU, memory, PID, and root-storage creation flags;
- explicit unlimited effective values for omitted dimensions;
- persistence and status output of the effective budget;
- Incus finite settings applied and verified before start;
- apply/verification failure uses cleanup/recovery semantics;
- unsupported finite provider behavior fails closed before provider side effects;
- v0.11 Base selection cannot raise resource limits;
- v0.9/v0.10 agent integration does not grant agents resource-control authority;
- unit tests for parsing, bounds, provider mismatch, unsupported behavior, ordering, and cleanup;
- fake-Incus CLI E2E for create/run/status and provider-native application;
- race, vet, build, docs consistency, and release packaging checks.

Environment-dependent acceptance remains separate and requires a real supported Incus host.

## Non-goals

The first v0.12 slice does not add AI scheduling/model budgets, aggregate workstation/cluster scheduling, automatic overcommit, live autoscaling, Kubernetes-style scheduler semantics, host Workspace quota management, arbitrary Incus config passthrough, or a capability for coding agents to raise their own limits.

## One-sentence definition

> **v0.12 gives each Hacocoon Environment an explicit host-selected resource budget and fails closed when a requested finite ceiling cannot be proven before the sandbox becomes available.**
