# v0.12 Sandbox Resource Limits

**Status:** roadmap/design contract  
**Compatibility:** pre-1.0; interfaces, defaults, and provider mappings may change incompatibly.  
**Implementation:** pending.

## Goal

v0.12 adds explicit resource budgets for Hacocoon Environments so permissive coding agents and developer tools can consume CPU, memory, processes, and local root-storage only within operator-selected bounds.

The security model becomes:

```text
VS Code / coding agent / tool
            |
            v
      Environment
  broad local freedom
  within resource budget
            |
     ---- boundary ----
            |
        Hacocoon
  Policy / Capability / Audit
            |
   GitHub / AWS / Host
```

Resource limits are not capabilities. A capability controls authority across a trust boundary; a resource budget limits consumption inside an Environment.

```text
Capability:  "May this Environment ask Hacocoon to push to GitHub?"
Resource:    "How much CPU/RAM/PIDs/root storage may this Environment consume?"
```

## Why this belongs in Hacocoon

Hacocoon intentionally allows coding agents to be permissive inside an isolated Environment. Isolation alone does not prevent an Environment from exhausting shared host resources.

Examples include runaway compiler/test processes, fork storms, memory pressure, root-disk exhaustion, and many parallel agent Environments overwhelming a workstation.

The host remains trusted and must retain control over how much shared capacity an untrusted Environment can consume.

## Scope

The first v0.12 slice should support explicit limits for:

- CPU;
- memory;
- process/PID count;
- Environment root-storage size where the selected provider can enforce it safely.

Conceptual creation input:

```text
EnvironmentSpec
  Name
  Workspace
  AccessMode
  ResourceBudget
```

Example user interaction:

```bash
haco create \
  --cpu 4 \
  --memory 8GiB \
  --pids 1024 \
  --root-size 40GiB \
  --workspace . dev
```

The exact flag names and configuration schema are pre-1.0 and are not frozen by this document.

## Resource budget model

Hacocoon should expose provider-neutral resource concepts and keep backend-native keys behind adapters.

Conceptually:

```go
type ResourceBudget struct {
    CPU      CPUResourceLimit
    Memory   ByteLimit
    PIDs     ProcessLimit
    RootDisk ByteLimit
}
```

This is illustrative rather than a required Go API.

The Core/domain contract must not expose Incus-native configuration names such as `limits.cpu` as public architecture. The Incus adapter may map the Hacocoon resource budget to those backend-native settings internally.

## Defaults

v0.12 must distinguish deliberately configured limits from accidental unlimited execution.

The implementation should support deterministic precedence, conceptually:

```text
CLI override
    > project configuration
    > user/global default
    > Hacocoon default budget
```

A missing value must have one documented meaning. Do not let provider defaults silently decide security-relevant resource behavior.

During pre-1.0 development, Hacocoon may initially preserve compatibility with an explicit `unlimited` value where necessary, but omission and unlimited authority must not be conflated accidentally.

## Provider boundary

Resource enforcement belongs to the Environment provider adapter.

```text
Workspace
   |
EnvironmentSpec + ResourceBudget
   |
Environment provider
   +-- runtime.incus
   +-- runtime.ec2 (experimental)
```

A provider should report which resource dimensions it can enforce. If the user explicitly requests a limit that the selected provider cannot enforce, creation must fail closed rather than silently ignore the requested limit.

## Incus mapping

For the default Incus provider, v0.12 may map provider-neutral limits to Incus configuration internally, including CPU quota/count, memory limit, process limit, and root-disk size.

The precise Incus commands and keys remain adapter details.

Resource settings must be applied before the Environment is made available to the client/agent. A create flow must not expose a briefly-unlimited running Environment and then apply limits afterward.

Preferred shape:

```text
resolve Workspace
  -> acquire WorkspaceLease
  -> validate ResourceBudget
  -> create stopped provider Environment
  -> apply resource limits
  -> attach Workspace
  -> start Environment
  -> verify requested limits where practical
  -> persist Environment metadata
```

Partial failure must use the existing cleanup/recovery discipline and must not leave a running unlimited Environment when the requested constrained Environment failed to materialize.

## Persistence and identity

An Environment must record the effective resource budget that was selected at creation time.

Changing a default later must not silently change the budget of an existing Environment.

Persisted resource metadata is needed for diagnostics, reconciliation, and future recovery behavior.

## Runtime mutation

The first v0.12 slice should prefer creation-time budgets over arbitrary live mutation.

Changing CPU or memory limits on a running Environment can have provider-specific semantics and failure modes. Live resizing is therefore not required for the first gate.

## Workspace storage is separate

The mounted Workspace is host-owned state and is not the same thing as the Environment root filesystem.

```text
Host Workspace
    |
    +-- mounted at /workspace

Environment root filesystem
    |
    +-- OS
    +-- packages
    +-- caches
    +-- logs
```

`--root-size` must not be represented as a promise to limit the size of an arbitrary host Workspace mount.

## Parallel-agent safety

v0.9 can allocate one Environment per independently routable coding-agent session. v0.10 adds the active VS Code Remote Agent Host Adapter integration. v0.12 composes with those paths rather than replacing them.

```text
Agent session A -> Environment A -> ResourceBudget A
Agent session B -> Environment B -> ResourceBudget B
Agent session C -> Environment C -> ResourceBudget C
```

Per-Environment limits prevent one agent from consuming unbounded resources, but they do not by themselves solve aggregate host capacity. Aggregate admission control remains a later concern.

## Status and diagnostics

The existing status/inspection path should expose the effective budget using stable Hacocoon concepts rather than backend-native key names.

Example conceptual output:

```text
Name: dev
State: running
Workspace: /home/user/src/project
Access: rw
Provider: runtime.incus
Resources:
  CPU: 4
  Memory: 8 GiB
  PIDs: 1024
  Root disk: 40 GiB
```

## Policy relationship

Resource limits are not Hacocoon `CapabilityRequest`s.

```text
Environment configuration
  -> defines sandbox shape and resource ceiling

Capability policy
  -> mediates privileged operations across the sandbox boundary
```

An operator may eventually restrict which budgets a caller is allowed to request, but such admission policy is separate from the runtime resource model itself.

## Base-image relationship

v0.12 composes with v0.11 Bases.

```text
Base revision
      |
      v
Environment + ResourceBudget
```

A Base controls guest filesystem/runtime contents. It must not be able to raise, disable, or rewrite host-selected resource limits through image metadata.

Custom Base contents remain untrusted input.

## Agent-host relationship

v0.12 also composes with the v0.9 agent-session binding and v0.10 adapter boundary.

The trusted broker/adapter may request an Environment with a configured budget, but the coding agent inside that Environment must not receive authority to raise its own host-enforced limits through Hacocoon or Incus control-plane access.

## Failure and recovery semantics

Resource configuration participates in normal Environment creation recovery.

Relevant failures include invalid resource values, unsupported provider dimensions, provider rejection, Workspace attach/start failure after resource configuration, persistence failure, and crashes between provider creation and state commit.

When creation cannot prove that the requested limits were applied correctly, it must not report successful constrained creation.

Cleanup should prefer leaking a clearly identifiable stopped resource over silently releasing ownership metadata for a potentially running Environment.

## Validation

Resource values must be parsed and validated by Hacocoon before provider execution.

At minimum:

- reject zero/negative limits where they do not have an explicit documented meaning;
- reject integer overflow and absurd byte-size conversions;
- reject ambiguous unit formats and trailing garbage;
- place practical upper bounds on inputs where needed;
- preserve exact operator intent in persisted effective values;
- keep provider command construction argv-based rather than shell-interpolated.

## Acceptance gate

Repository acceptance for the first v0.12 implementation requires:

- provider-neutral resource budget representation;
- explicit CPU, memory, and PID/process limit support for Incus;
- root-storage limit support where safely enforceable, otherwise explicit unsupported behavior;
- deterministic default/override resolution;
- persistence and inspection of the effective creation-time budget;
- requested-but-unsupported limits fail closed;
- resource settings applied before client/agent access;
- partial create failure follows existing cleanup/recovery semantics;
- WorkspaceLease safety remains unchanged;
- v0.11 Base selection cannot raise resource limits;
- v0.9/v0.10 agent integration cannot grant agents resource-control authority;
- unit tests for parsing, precedence, persistence, unsupported-provider behavior, and failure cleanup;
- race, vet, build, docs consistency, and maintained host-independent integration tests green.

Environment-dependent acceptance requires a real supported Incus host and should verify CPU, memory, PID, and supported root-size restrictions, plus that normal Environment access cannot raise those limits.

## Non-goals

The first v0.12 slice does not add AI scheduling/model budgets, aggregate workstation/cluster scheduling, automatic overcommit, live autoscaling, Kubernetes-style scheduler semantics, host Workspace quota management, arbitrary Incus config passthrough, or a capability for coding agents to raise their own limits.

## One-sentence definition

> **v0.12 gives each Hacocoon Environment an explicit host-enforced resource budget so permissive developer tools and coding agents can run freely inside the sandbox without consuming unbounded shared host capacity.**
