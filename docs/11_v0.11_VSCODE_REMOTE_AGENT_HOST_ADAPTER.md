# v0.11 VS Code Remote Agent Host Adapter

**Status:** implementation introduced on 2026-08-29  
**Compatibility:** pre-1.0; CLI and client-integration details may change incompatibly.  
**Real client acceptance:** real Windows/WSL + Incus + VS Code Agents window remote-SSH acceptance pending.

## Goal

v0.11 turns the v0.10 trusted session-to-Environment binding into a practical VS Code Agents-window entry point without implementing the Agent Host Protocol (AHP) inside Hacocoon.

```text
Windows VS Code Agents window
          |
      Remote -> SSH
          |
 Hacocoon-managed SSH alias
          |
  loopback-only host port
          |
     Incus Environment
          |
      /workspace
          |
 VS Code CLI / Agent Host
  (started by VS Code)
```

Hacocoon owns the isolated Environment and the safe connection preparation. VS Code owns the Agent Host, AHP, coding-agent UI, agent lifecycle above the prepared remote host, and protocol-version compatibility.

## CLI

v0.11 adds:

```text
haco-agent-host prepare
haco-agent-host release
```

Prepare one trusted remote slot:

```bash
haco-agent-host prepare --session <opaque-id> /path/to/worktree
```

The command:

1. validates the client SSH private/public key pair before preparing access;
2. acquires the v0.10 persisted session-to-Environment binding;
3. requires the assigned Environment to be running;
4. prepares a loopback-only SSH connection through the existing client-access boundary;
5. writes a Hacocoon-owned SSH host entry under `~/.ssh/hacocoon/`;
6. derives the SSH alias from a hash rather than exposing the raw session identity;
7. opens the VS Code Agents window with `code --agents` unless `--no-launch` is used;
8. prints the SSH alias to select from **New -> Remote -> SSH** in the Agents window.

Release the remote slot:

```bash
haco-agent-host release --session <opaque-id>
```

Release uses the v0.10 persisted binding proof. It does not accept an arbitrary Environment name.

## Why SSH instead of implementing AHP

Current VS Code supports remote Agent Hosts over SSH. When the Agents window connects to a remote SSH target, VS Code installs/starts its own remote CLI/Agent Host and then owns AHP communication.

Hacocoon intentionally does not:

- implement AHP JSON-RPC/WebSocket framing;
- manage VS Code Agent Host connection tokens;
- pin internal VS Code Agent Host process flags as a Hacocoon API;
- leak AHP types or version details into Core;
- replace the VS Code Agents UI.

This keeps an evolving external protocol at the client boundary.

## Isolation unit

The v0.11 guarantee is:

> **one prepared Hacocoon session slot -> one persisted v0.10 binding -> one Environment.**

The adapter receives an opaque `--session` identity from a trusted caller. It does not currently receive VS Code's internal top-level agent-session UUID automatically.

Therefore, if a user deliberately connects to the same prepared SSH alias and creates multiple VS Code agent sessions on that remote host, those sessions share the same Environment.

v0.11 must not claim automatic one-Incus-per-hidden-or-internal-VS-Code-session semantics that the client does not expose to Hacocoon.

For independent write-capable sessions, prepare independent slots and independent worktrees:

```text
session-a -> worktree/a -> Environment A -> SSH alias A
session-b -> worktree/b -> Environment B -> SSH alias B
```

## Security boundary

The private SSH key remains on the client side. Hacocoon passes only the public key through its existing SSH-access path.

The managed SSH target is loopback-only:

```text
VS Code / Windows OpenSSH
          |
      127.0.0.1:<port>
          |
       Hacocoon
          |
       Incus:22
```

The coding agent does not receive:

- the Incus Unix socket;
- Hacocoon management state/control authority;
- the client SSH private key;
- broad host/cloud credentials merely to manage the sandbox.

`prepare` setup failures do not automatically release the session Environment. The persisted binding remains available for safe retry, avoiding a race where one concurrent client could delete a binding another trusted client just acquired. Newly created SSH forwarding is revoked when adapter setup fails after forwarding was created.

Only explicit `release` deletes the bound Environment.

## Connection reuse and rotation

The adapter persists only client SSH configuration under the Hacocoon-owned SSH config directory.

On repeated `prepare`:

- an existing matching SSH connection is reused when alias, identity, and requested port are compatible;
- a changed identity or explicit changed port causes a new connection to be prepared;
- the previous managed SSH connection is revoked only after the new configuration is active;
- failure to revoke the old connection is surfaced as recovery-required rather than hidden.

## Windows / WSL behavior

When Hacocoon runs in the dedicated WSL environment while VS Code runs on Windows, the adapter follows the same v0.8 client-filesystem rule as `haco-vscode`: it resolves the Windows user profile and writes the SSH configuration used by the Windows desktop client.

The dedicated Hacocoon WSL 2 + systemd requirement remains unchanged.

## Relationship to earlier versions

v0.11 is additive:

```text
v0.8  haco-vscode       -> normal VS Code Remote-SSH workspace
v0.9  Base contract     -> future immutable Environment starting point
v0.10 session broker    -> trusted session ownership / dedicated Environment
v0.11 haco-agent-host   -> VS Code Agents-window remote-SSH adapter
```

The v0.11 adapter calls v0.10 rather than duplicating Environment ownership logic.

## Acceptance gate

Repository acceptance requires:

1. `haco-agent-host prepare/release` exists as a separate client adapter;
2. raw session IDs are not exposed in managed SSH aliases;
3. private keys remain client-side and only public keys enter the Environment access path;
4. repeated compatible preparation can reuse the managed SSH connection;
5. stale/rotated connections are replaced before old access is revoked;
6. setup failure revokes only newly prepared connection state and does not implicitly delete a v0.10 binding;
7. release uses v0.10 binding proof;
8. WSL client filesystem resolution targets Windows desktop SSH configuration;
9. release archives and the Linux installer include `haco-agent-host`;
10. build, vet, race, workflow policy, release packaging, docs consistency, and existing tests remain green.

Real-client acceptance additionally requires a suitable Windows/WSL/Incus/VS Code machine and must verify:

1. prepare slot A and slot B on distinct worktrees;
2. select alias A and alias B from the VS Code Agents window remote-SSH flow;
3. VS Code successfully installs/starts its remote Agent Host in each Environment;
4. agent commands and edits remain in the assigned Environment/worktree;
5. disconnect/reconnect preserves the intended slot;
6. explicit release removes only the corresponding v0.10 binding/Environment;
7. no Hacocoon/Incus administrator authority becomes available merely through the remote Agent Host.

Until that run succeeds, the repository must not report real VS Code Agent Host end-to-end acceptance as passed.

## One-sentence definition

> **v0.11 lets the VS Code Agents window use a v0.10 isolated session Environment through standard remote SSH while leaving Agent Host/AHP ownership to VS Code.**
