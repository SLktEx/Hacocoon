# Hacocoon v0.7 - Remote and EC2 Specification

Status: Draft for later implementation  
Requires: v0.6 Local Web and Interaction acceptance gate

## 1. One-sentence definition

Hacocoon v0.7 takes the already-working local Session/Security/Interaction model to remote Linux and AWS without changing Core semantics: remote host/access adapters, an optional EC2-native Runtime, EBS lifecycle support, and a Gateway adapter behind the deployment-owned Access Layer.

## 2. Principle: remote is an implementation expansion

The following must remain unchanged:

```text
Session identity and lifecycle meaning
CapabilityRequest / ALLOW-ASK-DENY / Grant
Git/GitHub/AWS capability semantics
workspace model
Interaction API semantics
```

v0.7 adds concrete implementations behind existing seams.

## 3. Two remote compositions

### A. Remote Linux + Incus

Useful for a Linux workstation/server:

```text
remote Linux host
  Hacocoon Manager
  runtime.incus
  native/managed Btrfs storage
  Sessions
  local/private Web IDE endpoints
  Gateway adapter
```

### B. EC2-native Runtime

AWS-specific composition may replace Incus entirely:

```text
Hacocoon Manager
       |
       v
runtime.ec2
       |
       v
one Hacocoon Session = one EC2 instance
       |
       +-- AMI/base image
       +-- systemd
       +-- containerd/nerdctl
       +-- /workspace
       +-- agent / Web IDE
       +-- EBS storage
```

This is a Runtime implementation, not a new Session concept.

The Manager/control-plane process may run on a suitable trusted host/service; its hosting choice must not become Core semantics.

## 4. Trust-domain rule

Default deployment principle:

> one trust domain = one Hacocoon host boundary; for the EC2-native composition, one Session/EC2 is the natural strong infrastructure boundary.

Do not claim mutually distrusting human tenants can safely share one privileged Manager/host merely because their Sessions differ.

For remote Linux + Incus, multiple Sessions are acceptable only inside the same intended trust domain.

## 5. Access Layer remains outside Hacocoon

Hacocoon does not become enterprise SSO/TLS/WAF/VPN.

Deployment may supply:

```text
TLS termination
OIDC/SSO
VPN
bastion
reverse proxy
WAF/source-IP policy
```

Hacocoon consumes a verified `IdentityContext` from the deployment Access Layer and performs Session access authorization. Hacocoon does not validate arbitrary Internet identity headers by itself. Browser access never implies GitHub/AWS capability authorization.

## 6. Gateway adapter integration

```text
Internet/user
  -> deployment Access Layer
  -> Hacocoon Gateway/access adapter (routing only)
  -> authorized Session route
       +-- Web UI/Interaction
       +-- Web IDE
       +-- private preview
```

Rules:
- Session services bind private by default;
- public exposure is an explicit Hacocoon capability/action;
- Gateway holds no GitHub/AWS parent credential for ordinary routing;
- route binds to exact Session identity;
- WebSocket support is required for Web IDE;
- Session delete cleans routes.

## 7. EC2 Runtime contract mapping

`runtime.ec2` implements the same Runtime semantics:

| Runtime semantic | EC2 mapping |
|---|---|
| Probe | region/account/network/AMI prerequisites |
| Create | `RunInstances` with approved profile/config |
| Start/Stop | EC2 start/stop |
| Delete | terminate instance + Session-owned resource cleanup |
| Exec | SSH/SSM or approved remote execution adapter |
| Inspect | instance state/health/IP/identity |
| snapshot/base | AMI/EBS snapshot mechanisms where appropriate |

Do not spread `if runtime == ec2` branches through Core.

## 8. EC2 IAM model

Infrastructure IAM is provisioned outside Hacocoon, for example by organization tooling/Terraform.

Hacocoon selects pre-created profiles/roles and should need only the minimum control-plane permissions, such as EC2 lifecycle and tightly scoped `iam:PassRole` where required.

Hacocoon does not create/edit organization IAM policies as a product feature.

Inside the Session, AWS developer access still uses the v0.4 Capability Provider. EC2 instance-profile/IMDS credentials are Host/Session runtime authority and must not silently become an unrestricted bypass.

## 9. Cloud metadata

For remote Linux hosts with a host identity, block Session access to host metadata credentials by default.

For EC2-native one-Session-per-instance composition, any instance role attached to that Session is explicit Session authority and must be selected/scoped intentionally. Do not attach broad Manager credentials to the Session instance.

## 10. EC2/EBS provisioning design gate

The v0.1 local composition can prepare its Incus/Btrfs storage before creating a Session. An EC2-native composition may need different ordering because instance placement and EBS attachment can depend on the created EC2 instance/AZ.

Therefore v0.7 must **not** copy the v0.1 creation order and must **not** add `if runtime == ec2` branches throughout Core. Before implementing EC2-native storage, choose the smallest real composition boundary that satisfies both concrete implementations. Acceptable outcomes include a narrow provisioning-plan/composition object or a runtime-specific EBS collaborator. The choice is a v0.7 design decision backed by tests, not a speculative v0.1 abstraction.

The identifier `storage.ebs` is therefore **not a frozen v0.1-v0.6 contract**. EBS-specific code stays outside Core regardless of the final v0.7 package shape.

## 11. EBS lifecycle

For the EC2-native composition, EBS lifecycle code is a v0.7 infrastructure implementation. It may initially live with `runtime.ec2` or behind a narrow v0.7-only collaborator until a real reusable Storage boundary is demonstrated.

### Grow

EBS can grow in place; order remains outer-to-inner:

```text
modify/grow EBS volume
 -> wait for usable state
 -> rescan block device
 -> grow filesystem
 -> verify
```

### Shrink

EBS does not support in-place volume shrink. Hacocoon therefore models shrink as **replacement**, not resize:

```text
1. plan target and quiesce Session/storage
2. create smaller replacement EBS volume
3. create filesystem/storage target
4. migrate data/snapshots/subvolumes using a verified filesystem-level method
5. attach replacement
6. verify Session/storage integrity
7. switch stable Hacocoon storage reference to replacement
8. retain old volume until verification/rollback window is satisfied
9. delete old volume only after successful commit
```

Never call an unsupported imaginary `shrink EBS` API and never delete the source before verification.

The exact migration strategy may use Btrfs send/receive or another validated method; it must preserve snapshot/workspace semantics that the selected Storage profile promises.

## 12. AMI/base image

The EC2 runtime may map the local base-image concept to AMIs:

```text
Hacocoon base image concept
  local runtime.incus -> Incus image/snapshot
  runtime.ec2         -> AMI + configured EBS layout
```

AMI/EBS IDs remain runtime/storage implementation state, not Core product fields.

## 13. Remote Web/Preview

Reuse v0.6 Web/Interaction semantics. v0.7 changes transport/deployment, not UI authority.

Recommended default:

```text
Web IDE: authenticated private route
Preview: authenticated private route
Public preview: explicit policy/approval only
```

A process listening on `3000` does not automatically get a public URL.

## 14. Host profiles

Examples:

```yaml
host:
  mode: remote-linux
runtime:
  backend: incus
storage:
  backend: btrfs-native
```

```yaml
host:
  mode: aws
runtime:
  backend: ec2
  volume_backend: ebs   # provisional v0.7 runtime composition detail
```

Host profiles are metadata/configuration, not a new programming DSL.

## 15. CLI additions

Illustrative:

```bash
haco host doctor
haco remote status
haco gateway status
haco gateway routes
haco expose <session> <port> --visibility private
haco unexpose <session> <port>
# EBS replacement command shape is intentionally not frozen until the v0.7 provisioning design gate is resolved.
```

EC2/provider-specific knobs should live in configuration/provider namespaces rather than dozens of top-level commands. Do not freeze an EBS-specific top-level CLI before the owning module boundary is decided.

## 16. Implementation order

### Phase 1 remote-linux parity
1. `HostAdapter remote-linux`;
2. run v0.1-v0.6 regression suite on a remote Linux host;
3. private Web/Interaction access;
4. metadata/host-private endpoint isolation.

### Phase 2 remote Gateway adapter integration
1. route model;
2. verified IdentityContext handoff from the deployment Access Layer;
3. reverse proxy + WebSocket;
4. private previews;
5. access audit/cleanup.

### Phase 3 runtime.ec2
1. EC2 probe/config;
2. pre-created IAM/profile selection;
3. create/start/stop/delete/inspect;
4. base AMI;
5. exec/access strategy;
6. Session identity mapping and cleanup.

### Phase 4 EC2/EBS lifecycle
1. create/attach/detach/inspect;
2. grow;
3. snapshot integration;
4. replacement-based shrink POC;
5. interrupted migration recovery;
6. old-volume deletion only after commit.

### Phase 5 hardening
1. route isolation;
2. credential/IMDS tests;
3. Manager failure recovery;
4. orphan EC2/EBS reconciliation;
5. cost/resource leak doctor checks.

## 17. Security/negative tests

| Scenario | Expected |
|---|---|
| unauthenticated browser reaches Session route | denied |
| Session A changes route to Session B | denied |
| remote Session reads Manager parent credential | impossible |
| remote-linux Session hits host IMDS | blocked |
| EC2 Session gets broad Manager instance role | forbidden configuration/test failure |
| Web route compromise grants GitHub/AWS capability | no; separate Security authority |
| Session listener starts | remains private until explicit exposure |
| EBS replacement validation fails | old volume retained; switch not committed |
| Manager crashes during EBS migration | operation reconciles; source is not blindly deleted |
| EC2 creation fails halfway | orphan resources discovered/cleaned by reconciliation |

## 18. Acceptance gate

- local v0.1-v0.6 remains functional without remote packages/services;
- remote-linux composition passes shared Session/Security tests;
- authenticated browser can reach remote Web UI/Web IDE through private routing;
- unauthenticated/direct Session ports are not Internet-reachable;
- `runtime.ec2` satisfies the shared Runtime contract without Core branches;
- EC2 base Session runs systemd/containerd/nerdctl and agent/workspace flows;
- AWS developer capabilities still use v0.4 security semantics;
- EBS grow works and verifies filesystem growth;
- EBS shrink is implemented only as verified replacement or clearly reported unsupported, never in-place fiction;
- failed EBS replacement retains the old source;
- no provider parent credential is exposed to Session;
- resource cleanup/reconciliation detects orphan EC2/EBS/Gateway resources.
