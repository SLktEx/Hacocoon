# 操作を止める検証と外部情報の取得

日本語 | [English](validation-and-probes.md)

インストール、セットアップ、ユーザー操作を止める検証を追加・変更するときの
開発・レビュー規則。検証の必要性と、その判断に使う情報の取得方法を一緒に確認する。
検証処理自身の不具合によって、動作する環境を拒否することもある。

## 拒否する理由を示す

具体的な前提条件と、それを満たさずに続行した場合の影響を、機能を所有する設計文書か
変更説明に記載する。バージョン制限には、必須 API、既知の不具合、または理由を明示した
意図的な互換性の境界を結び付ける。あるバージョンだけをテストしたことは、他の
バージョンが非互換だという証拠にはならない。LTS という名前も、既存の制限も、
この判断の代わりにはならない。

通常の製品操作で前提条件を確認でき、対処可能なエラーを返せるなら、その経路を優先する。
別の事前検証は、具体的に危険な操作や大きな無駄を防ぐ場合、または早い段階での診断が
必要な場合に追加する。既に存在するという理由だけで重複した検証を維持しない。

## 取得方法の契約を確認する

自動判定には、文書化された API や機械向け出力を使う。読み取り処理を書く前に、
提供元の実際のスキーマ、フィールドの型、コマンドの終了時の振る舞い、対象バージョンを
確認する。インストールと CI が同じ情報を必要とする場合は、provider や共通ヘルパーに
取得処理をまとめる。

人向けのラベル、表、翻訳されたメッセージは表示形式である。言語を固定するだけでは
安定したインターフェースにならない。構造化された取得方法がない場合は、代替手段の
前提を記録し、対応する言語や書式の違いをテストしてから利用する。

前提条件を満たしていないと確認できた場合と、タイムアウト、権限エラー、不正な応答などで
確認できなかった場合を区別する。それぞれの停止、回数・時間を制限した再試行、警告の
扱いを、操作への影響に応じて定める。認可、所有権、隔離の不明状態は引き続き
[セキュリティ原則](../DESIGN_PRINCIPLES.ja.md)に従って拒否する。
取得失敗を、非互換や不存在が確認できたかのように報告してはならない。

## 取得処理と判定処理をテストする

操作を止める検証を変更する際は、次の3点をレビューの根拠として揃える。

- 拒否する理由と、前提条件や互換性の契約へのリンク。
- 取得方法の契約と、その根拠となる提供元の仕様、または秘密情報を除いた実際の応答。
  テストデータを評価できるように、出典やバージョンも示す。
- 対応する入力では成功し、不正な入力や取得失敗では意図した結果になる回帰テスト。

モックやテストデータは、その独立した根拠から作る。実装が期待する文字列だけを根拠に
作ってはならない。変更する境界に応じて、言語、省略可能な項目、JSON の書式、対応する
パッチバージョンなど、正常な入力の違いを含める。項目の欠落や型違い、コマンドの異常終了も
検証し、失敗したコマンドがもっともらしいデータを出す場合も扱う。テストは不具合を忠実に
再現できる最も小さな層に置き、該当する通常のユーザー経路の E2E も維持する。
モックの成功は、実際の provider での受入成功を意味しない。

[Incus インストーラーの設計判断](../adr/0064-shared-incus-lts-installation.md)が具体例となる。
英語の `Server version` ラベルを読む実装と、常にそのラベルを返すモックでは、日本語出力の
不具合を検出できなかった。JSON API の利用でその取得方法の問題は解消できるが、
バージョン制限自体が必要かどうかは別にレビューする。
